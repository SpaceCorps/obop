## 3. Discuss, chat, channels, video

- **Odoo design [V].** Real-time transport is the `bus` module: `pg_notify` on an `imbus` channel, a WebSocket endpoint, 24 h message GC (https://github.com/odoo/odoo/blob/20.0/addons/bus/models/bus.py). Calls are browser WebRTC: mesh by default, with an optional external **SFU** (a Node.js project, LGPL-3, 28 stars: https://github.com/odoo/sfu) and TURN/ICE servers configured via Twilio (https://www.odoo.com/documentation/19.0/applications/productivity/discuss.html). Guests (`mail.guest`) can join calls without accounts. Users choose "handle by email" or "handle in Odoo" for notifications.
- **Build vs integrate.** The chatter/thread model is the core of obop's "one platform" promise (every record has messages, followers, activities), so it must be first-party and tied to the record model. Chat transport is small: axum WebSocket + Postgres `LISTEN/NOTIFY` (payload limit is 8000 bytes, so send IDs, not bodies) mirrors Odoo and scales to a few thousand concurrent users per node [I].
- **Matrix is not a good core [I].** Tuwunel (Rust Matrix homeserver, Apache-2.0, v1.9.3, 2026-09-25, primarily Swiss-government sponsored: https://github.com/matrix-construct/tuwunel) and matrix-rust-sdk (Apache-2.0, 0.19.1) are healthy, but Matrix's room/event/federation model duplicates the record-bound thread model. Offer a Matrix *bridge* later, not a dependency. Synapse moved to `element-hq/synapse` under AGPL-3.0 (the `matrix-org` repo is archived).
- **Video.** Use LiveKit (Go, Apache-2.0, v1.13.7, `livekit-client` 2.22.3 on npm) as an optional SFU for rooms above about 4 participants; keep WebRTC mesh for small calls like Odoo. Rust options: `str0m` 0.24.0 (sans-IO, MIT/Apache, 2026-09-25) and `webrtc` 0.21.0 (MIT/Apache-2.0) are credible for building an SFU, but that is months of work for no functional gain over LiveKit [I]. TURN: coturn (actively maintained, last push 2026-09-28; GitHub reports no single SPDX because the LICENSE file bundles several notices and opens with a Citrix BSD-style header, so treat as BSD-style and review before shipping [V for header, U for full terms]).

## 4. Email gateway

### How Odoo does it [V, from `mail_thread.py` 20.0 and docs]

1. **Inbound sources:** (a) IMAP/POP fetch by cron (`fetchmail.server`, searches `UNSEEN`, marks `\Seen` only after success), (b) mail-gateway script piped from the MTA, (c) redirect/DNS so the MTA delivers to an HTTP endpoint (https://www.odoo.com/documentation/19.0/applications/general/email_communication/email_servers_inbound.html).
2. **Routing order in `message_route`:** bounce detection first; then threading by matching `References`/`In-Reply-To` against `mail.message.message_id` (only the **last 32** references are queried, because queries degraded at 100+); then alias lookup on `To/Cc/Delivered-To`; then fallback model. Catchall only accepts replies (direct mail to catchall is bounced). `mail.catchall.domain.allowed` whitelists domains.
3. **Alias policy:** `alias_contact` = everyone / authenticated partners / followers only; per-alias defaults JSON; `alias_force_thread_id` to pin to one record.
4. **Outbound:** Reply-To is the model alias or catchall; Return-Path is the **bounce** alias; bounces are parsed (`multipart/report`, `message/rfc822`) and propagate to `email_normalized` on blacklist-enabled models and to the originating message as a "red envelope".
5. **Loop protection:** counts recent records/messages per sender (`LOOP_THRESHOLD`) and drops floods with a notice.
6. **Deliverability:** SPF is evaluated on the bounce address domain; DKIM via a CNAME `odoo._domainkey`; DMARC guidance only (https://www.odoo.com/documentation/19.0/applications/general/email_communication/email_domain.html). Odoo 19/20 lets users connect Gmail/Outlook via OAuth for sending.

### External constraints that shape the build [V]

- Gmail bulk-sender rules (since 2024-02-01): everyone needs SPF or DKIM, TLS, valid PTR, spam rate under 0.3% (aim under 0.10%); senders above 5,000/day need SPF, DKIM and DMARC plus one-click unsubscribe (`List-Unsubscribe-Post`, RFC 8058); DKIM keys of at least 1024 bits, 2048 recommended (https://support.google.com/a/answer/81126).
- Gmail IMAP/SMTP OAuth (XOAUTH2) requires the `https://mail.google.com/` scope and app verification (https://developers.google.com/workspace/gmail/imap/xoauth2-protocol). Google's page mentions app verification (and the Google API Services User Data Policy) but never a security assessment; that `https://mail.google.com/` is a *restricted* scope needing a paid security assessment is [U] (unverified); verify before promising hosted Gmail IMAP.
- Microsoft disabled Basic auth for IMAP/POP/EAS/EWS (plus RPS, OAB, Autodiscover) in all tenants ("Basic authentication is now disabled in all tenants"); OAuth 2.0 is mandatory, and Basic auth for SMTP AUTH is being retired on an updated timeline whose dates I could not fetch (the Learn page defers to https://techcommunity.microsoft.com/blog/exchange/updated-exchange-online-smtp-auth-basic-authentication-deprecation-timeline/4489835, which is JavaScript-rendered) (https://learn.microsoft.com/en-us/exchange/clients-and-mobile-in-exchange-online/deprecation-of-basic-authentication-exchange-online). Plan on Microsoft Graph `sendMail` or XOAUTH2 only.

Use its MIT/Apache *libraries*, offer the server as an optional integration.

**Recommended design [I]:** one `obop-mail` crate implementing: provider-agnostic `MailAccount` (IMAP+XOAUTH2, Gmail API, Graph), an inbound pipeline (parse → bounce/DSN detect → thread by `References` last-32 → alias route → loop guard → ACL policy), `mail_mail`-style durable outbound queue (Postgres-backed, `FOR UPDATE SKIP LOCKED`), VERP-style bounce addresses, per-domain DKIM signing with `mail-auth`, and one-click unsubscribe headers for marketing. Keep Odoo's alias/catchall/bounce vocabulary so Odoo users feel at home.

## 5. Calendar and contact sync

- **Odoo model [V]:** `calendar.event`, `calendar.attendee`, `calendar.recurrence` (uses Python `dateutil.rrule`; UI recurrence types forever / end date / count), `calendar.alarm` + `calendar_alarm_manager`, `calendar.filter`, `calendar.event.type`, and a new `calendar.calendar` model in 20.0 (multiple calendars); sync modules `google_calendar` (`google_sync.py`, `google_event_sync.py`, `calendar_recurrence_rule.py`) and `microsoft_calendar` in Community. Appointments (booking pages) is Enterprise.
- **Standards:** iCalendar RFC 5545, iTIP/iMIP (RFC 5546/6047) for email invitations, CalDAV RFC 4791 + scheduling RFC 6638, CardDAV RFC 6352, vCard RFC 6350, JSCalendar RFC 8984, JSContact RFC 9553, JMAP Contacts RFC 9610 (cited in Stalwart's README); JMAP Calendars is still an IETF draft (`draft-ietf-jmap-calendars-31` on 2026-10-01, IESG state "RFC Ed Queue", i.e. approved but not yet published as an RFC) [V: https://datatracker.ietf.org/doc/draft-ietf-jmap-calendars/].
- **Google [V]:** incremental sync via `syncToken`/`nextSyncToken`; HTTP 410 means wipe and full-resync; sync tokens restrict query params (https://developers.google.com/workspace/calendar/api/guides/sync). Push: `events.watch` channels are **per calendar**, HTTPS with valid cert, **no payload** (you must re-sync), not auto-renewed, "a small percentage" of messages can be dropped (https://developers.google.com/workspace/calendar/api/guides/push). So: push is only a hint; keep a poll fallback.
- **Microsoft Graph [V]:** `calendarView/delta` needs a fixed start/end window and returns opaque `deltaLink` tokens; `$select` unsupported; a delta over a calendar *not* bound to a date range exists only in the beta API (https://learn.microsoft.com/en-us/graph/delta-query-events). Outlook message/event/contact subscriptions live at most **10,080 minutes** (1,440 with resource data) and need renewal; `lifecycleNotificationUrl` (reauthorizationRequired / subscriptionRemoved / missed) is optional for Outlook resources (required only for Teams resources with lifetimes over 1 hour) but recommended (https://learn.microsoft.com/en-us/graph/api/resources/subscription).
- **Rust libs:**

| Crate | Version / date | Verdict |
|---|---|---|
| `calcard` (Stalwart) | 0.3.14 / 2026-09-15, Apache-2.0 OR MIT | **Best fit**: iCalendar, vCard, JSCalendar, JSContact, conversion between them, RRULE expansion, IANA tz. Young (22K recent downloads) |
| `icalendar` | 0.17.14 / 2026-09-29, MIT/Apache | Good builder/parser; no expansion |
| `rrule` | 0.14.0 / **2025-04-20**, repo last push the same day | Popular (496K recent downloads) but **17 months without a release** [V]; wrap behind a trait so it can be swapped for calcard |
| `libdav` | 0.11.0 / 2026-09-05, ISC | CalDAV/CardDAV client; the only serious one |

- **Recommendation [I]:** store events like Odoo (RRULE string + base event + per-occurrence exception rows keyed by `recurrence_id`), expand on read with a hard cap, store timestamps as UTC + IANA tzid (never offsets), and model attendee state with `PARTSTAT`. Provide iCal feeds (read-only `.ics` subscription URL) and iMIP email invites first; a CalDAV/CardDAV *server* is a later differentiator (Odoo has none), achievable by integrating Stalwart or building on `dav-server` + `calcard`.

## 6. Documents / DMS

- **Odoo Documents (Enterprise) [V, docs]:** workspaces Company / My Drive / Shared with me / Recent / Trash; folders + tags; shortcuts; file versions and lock; PDF split/merge; document *requests* with placeholders and reminders; "actions on select" server actions; per-folder automation rules (needs Studio); folder email aliases that ingest attachments; share links with access rights; **trash retention default 30 days** (adjustable); "file centralization" auto-files attachments from Accounting (per journal) and HR (per employee); AI auto-sort and digitization need the AI app and IAP credits; 64 MB upload cap on Odoo Online (https://www.odoo.com/documentation/19.0/applications/productivity/documents.html). Use **OCRmyPDF** (MPL-2.0, v17.13.0, 2026-09-28) + Tesseract (Apache-2.0, 5.5.3) as a sidecar container producing searchable PDF/A, exposed through a job queue; keep the engine behind a trait so a cloud OCR or `ocrs` can be swapped in.
- **Open-source DMS references:** Paperless-ngx v3.2.1 (GPL-3.0, Python) is the feature benchmark (consumption folders, tags/correspondents/types, matching rules); do not embed (GPL, separate datamodel) but study its workflow.

## 8. E-signature

- **What Odoo Sign provides [V]:** its own legal page states Odoo generates **simple electronic signatures** (SES) only, supported by evidence: email/SMS validation, optional itsme identity proof, timestamped IP/geo access logs, and tamper detection via cryptographic proofs (https://github.com/odoo/documentation/blob/19.0/content/applications/productivity/sign/validity.rst; the 20.0 and master branches of that page say the same). **Caveat for Odoo 20 [V]:** the Odoo 20 release notes (https://www.odoo.com/odoo-20-release-notes) add "Qualified Electronic Signature via itsme" in over 30 European countries, so signers can now be asked for a third-party QES with handwritten-equivalent legal effect under eIDAS; Odoo's own signature remains SES and the validity page has not been updated. Features: templates with drag-and-drop fields, roles, envelopes bundling several documents, auto-complete fields from the database, SMS/Aadhaar eSign/itsme authentication, delegation, signing from chatter or Documents.
- **eIDAS levels [V/I]:** Regulation (EU) 910/2014 defines simple, advanced (AdES) and qualified (QES) signatures; QES has the legal effect of a handwritten signature and needs a qualified certificate issued by a QTSP (listed on EU trusted lists) and a qualified signature creation device (often remote). Regulation (EU) 2024/1183 ("eIDAS 2.0") is dated 11 April 2024 and has entered into force (the 20 May 2024 entry-into-force date is from memory [U] (unverified); the Commission page only says "has entered into force"); Member States are mandated to provide EU Digital Identity Wallets by the end of 2026, and creating qualified eSignatures for non-professional use will be free (https://digital-strategy.ec.europa.eu/en/policies/eudi-regulation; https://commission.europa.eu/strategy-and-policy/priorities-2019-2024/europe-fit-digital-age/european-digital-identity_en; https://ec.europa.eu/digital-building-blocks/sites/spaces/EUDIGITALIDENTITYWALLET/pages/694487738/EU+Digital+Identity+Wallet+Home). Exact article text was not retrievable (EUR-Lex blocked) [U for clause numbers].
- **PAdES (ETSI EN 319 142-1 V1.2.1, 2024-01) [V]:** baseline levels B-B (signature), B-T (+ trusted signature time-stamp token, RFC 3161), B-LT (+ all material needed to validate the signature embedded in the document), B-LTA (+ renewable electronic time-stamps for long-term validation). The Signature Dictionary must use SubFilter `ETSI.CAdES.detached` (https://www.etsi.org/deliver/etsi_en/319100_319199/31914201/01.02.01_60/en_31914201v010201p.pdf).
- **Open-source products [V]:** DocuSeal 3.3.0 (AGPL-3.0 **plus Section 7(b) additional terms**, Ruby, 2026-09-28; Pro features paid), Documenso v2.19.0 (AGPL-3.0, TypeScript, no longer accepting external PRs; uses MIT `@libpdf/core` for PDF signatures), OpenSign (AGPL-3.0 with per-directory exceptions). All copyleft; none are embeddable without AGPL consequences, but all are useful feature benchmarks.
- **Rust PAdES libraries [V] - nascent:**

| Crate | Version | License | Evidence of maturity |
|---|---|---|---|
| `underskrift` | 0.1.4 (2026-06-01) | BSD-2-Clause | PAdES B-B..B-LTA, RFC 3161, OCSP/CRL, DSS, **three-phase remote signing** (prepare hash, sign externally in HSM/KMS, finalize); 13 GitHub stars, ~1.4K recent downloads |
| `pdf_signer` | 0.3.2 (2026-09-25) | **GPL-3.0-or-later** | B-B..B-LTA; 0 stars; GPL blocks use in a permissive core |
| `tsp-ltv` | 0.5.0 (2026-09-28) | BSD-2-Clause | shared RFC 3161 + OCSP/CRL/trust-store code, 163K recent downloads (mostly transitive) |
| Building blocks | `cms` 0.2.3, `x509-cert` 0.3.0 (RustCrypto), `rasn-ocsp` 0.28.15, `lopdf` 0.45.0 | MIT/Apache | solid primitives for an in-house implementation |

- **Java reference:** EU DSS 6.5 (LGPL-2.1, 2026-08-28; PAdES, XAdES, CAdES, JAdES, ASiC; trusted-list validation modules) is the European Commission's own library (https://github.com/esig/dss). It is the realistic engine for *validation* of foreign QES/AdES until Rust catches up.
- **Recommendation [I]:** ship Sign in tiers: (1) **SES** like Odoo (evidence bundle + hash chain + sealed PDF with an obop-held certificate, i.e. an "advanced seal" of the document rather than of the person); (2) **AES/QES through pluggable QTSP connectors** using remote-signing (Cloud Signature Consortium-style three-phase flow, which `underskrift` already models). Do not claim eIDAS "advanced" or "qualified" status for self-managed crypto. Audit trail entity set: `sign_request`, `sign_envelope`, `sign_document`, `sign_item` (field placements), `sign_role`, `sign_signer`, `sign_event` (append-only, hash-chained: viewed, OTP sent/verified, signed, declined, delegated, IP, user-agent, geolocation if consented), `sign_certificate`.

## 11. Studio / low-code

- **Odoo [V, docs]:** Studio (Custom plan only) adds no-code editing of fields, views, models/apps ("app builder"), automation rules (incl. webhooks), PDF reports, approval rules and security rules (https://www.odoo.com/documentation/19.0/applications/studio.html). - **obop architecture [I]:**
  - **Metadata-first core (MUST):** every entity, field, view, action, menu, rule and report is a row in the metadata model, including the built-in ones; "custom" is just another module (`origin = user`). This is the only way Studio can edit everything.

## Implications for obop

**MUST**
1. **MUST** model chatter as a first-party, record-polymorphic thread system mirroring Odoo (`message`, `follower`, `subtype`, `notification`, `activity`, `alias`, `alias_domain`), with Postgres `LISTEN/NOTIFY` + WebSocket as the realtime bus. Everything else in this document hangs off it.
2. **MUST** build the email gateway in-house on Stalwart's permissive libraries (`mail-parser`, `mail-builder`, `mail-auth`) plus `lettre` and `async-imap`; replicate Odoo's routing order (bounce, References/In-Reply-To last 32, alias, fallback), catchall/bounce aliases, loop guard and alias contact policy. Do **not** make the Stalwart server (AGPL-3.0 + proprietary SELv2) a hard dependency.
3. **MUST** support OAuth-only mailbox access (Gmail XOAUTH2/API, Microsoft Graph) from day 1, and ship SPF/DKIM/DMARC diagnostics plus one-click unsubscribe headers, because Gmail's deliverability rules (Yahoo's parallel rules not re-checked, unverified) and Microsoft's Basic-auth retirements make plain SMTP passwords non-viable.
4. **MUST** adopt a metadata-first core (fields, views, actions, menus, rules, reports as data) so Studio, custom fields and approvals can edit built-in behaviour; retrofitting is prohibitively expensive.
5. **MUST** use Yjs (13.6.x client) + `yrs` 0.28 for collaborative documents, pinned together, with a CI cross-implementation test for the known Yjs/Yrs divergence (y-crdt#632); write your own thin y-protocol WebSocket layer rather than depending on stale `yrs-axum`/`yrs-warp`/`y-sweet`.
6. **MUST NOT** depend on copyleft-only components in the core: HyperFormula (GPL-3.0), BlockNote XL (GPL-3.0), `pdf_signer` (GPL-3.0+), Documenso/DocuSeal/Metabase/ParadeDB (AGPL). Keep an automated licence gate in CI.
7. **MUST** treat e-signature honestly: ship SES with a tamper-evident audit trail (like Odoo) and never label self-managed crypto "advanced/qualified"; where a QES is needed, delegate to a QTSP connector (Odoo 20 does this with itsme).

**SHOULD**
