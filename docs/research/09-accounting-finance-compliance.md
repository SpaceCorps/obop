## 1. Odoo as the reference

### 1.1 Status and licensing
- Odoo 20 was released September 2026 (previous: 19 in September 2025, 18 in October 2024) [V] https://www.odoo.com/page/release-notes . The `20.0` branch is the default on GitHub; `odoo/release.py` declares `LGPL-3`, Python 3.12-3.14 and `MIN_PG_VERSION = 16` [V] https://github.com/odoo/odoo/blob/20.0/odoo/release.py (addons/account read at branch 20.0; GitHub API `default_branch` = `20.0`, re-verified 2026-10-01).
- **Community vs Enterprise matters for scope.** The Community repo contains `account` (marketed as "Invoicing"), `account_edi_ubl_cii`, `account_peppol`, `payment_*` providers (adyen, stripe, mollie, paypal, razorpay, redsys, worldline, xendit, etc.), `hr_expense`, `analytic`, and **229 `l10n_*` directories** including e-invoicing modules (`l10n_fr_pdp`, `l10n_es_edi_verifactu`, `l10n_pl_edi`, `l10n_hr_edi`, `l10n_in_edi`, `l10n_sa_edi`, `l10n_it_edi`, `l10n_ro_edi`, `l10n_gr_edi`) [V, directory listing]. There is **no** `account_reports`, `account_asset`, `account_budget`, consolidation, follow-up or bank-sync module in that listing [V by absence, re-checked against the 20.0 tree on 2026-10-01]. Nuance: the declarative report **data model** (`account.report`, `.line`, `.expression` with engines domain / tax_tags / aggregation / account_codes / external / custom, `.column`, `.external.value`) and the "Generic Tax report" (used for OSS) *do* live in Community `addons/account/models/account_report.py` and `data/account_reports_data.xml` [V source]; what is absent is the financial-statement catalogue and viewer. The EDI/tax connectors for Mexico (`l10n_mx_edi`), Brazil (`l10n_br_edi`, `l10n_br_avatax`), Turkiye (`l10n_tr_nilvera*`), US/global Avalara (`account_avatax`) and the German TSE (Fiskaly) are also absent from the Community tree although documented, i.e. presumably Enterprise [V by absence; the Enterprise repo itself is unreadable]; Greece is served in Community by `l10n_gr_edi` plus `l10n_gr_edi_e_invoo` ("myDATA E-invoicing through e-invoo", built on `account_edi_proxy_client`) [V source]. ## 2. Finance-core requirements (Odoo stance vs what obop should do)

| Topic | Odoo reference | Real-world requirement / recommended stance |
|---|---|---|
| Chart of accounts | Templates per country, company default accounts, per-company codes | Keep templates; accounts carry type, reconcilable flag, deprecated flag, tag set for statutory reports. Allow hierarchical parents (Odoo 20 direction). |
| Journals and entries | Journal per flow; moves draft/posted/cancel | Append-only ledger after posting; corrections only by reversal; explicit `fiscal_year` table [I] (SAF-T, FEC, DATEV need period attributes; Odoo's absence forces computed years). |
| Lock dates | Five dates plus exceptions | Adopt the same model (soft global/tax/sales/purchase + irreversible hard lock + expiring exceptions) but enforce in DB trigger. |
| Taxes | Section 1.3 | Model price-included/excluded, groups, fixed, "division", cash-basis, withholding, non-deductible VAT, reverse charge via fiscal position + repartition tags. Effective-dated rates. |
| Invoices/credit notes | `account.move` types; credit notes reverse | One document model for out/in invoice, credit note, debit note, receipt; credit note links to original; cumulative credit cannot exceed original. |
| Payment terms/cash discount | Instalments + EPD with tax effect | EPD must adjust VAT base (EU rule); keep three computation modes. |
| Reconciliation | Partial/full, exchange diff, CABA | Partial reconciliation rows with amounts in both currencies; exchange-difference entries are system-generated and flagged. |
| Multi-currency | balance + amount_currency + rate stored on line | Store the rate actually used; never re-derive history. Add period-end revaluation and CTA for consolidation. |
| Multi-company/consolidation | Shared accounts, per-company codes, interco sync; consolidation Enterprise | Company_id on every row; composite FKs; consolidation as a separate reporting layer with translation rate types. |
| Analytic/budgets | `analytic_distribution` JSON on lines, plans, distribution models; budgets Enterprise/19 analytic budgets | Keep analytic as side ledger with plans; budgets per analytic account + account group + period. |
| Assets/deferrals | Enterprise; linear/degressive, prorata; Odoo 20 depreciation models | Both are schedule generators that emit ordinary entries; deferral dates on entries (Odoo 19 added deferral dates on misc entries). |
| Reports | Declarative `account.report` data model and engines live in Community `account` (used for tax reports); the financial-statement catalogue/viewer is Enterprise [V source + absence of `account_reports`] | Declarative report definitions (expression over account tags/domains), not hard-coded SQL per report. |
| Audit | Hash chain + restrictive trail | Section 4. |

## 3. Tax engine facts

- **EU VAT/OSS [V]:** A single EU-wide threshold of EUR 10,000 (combined supplies; it existed from 1 Jan 2019 for B2C TBE services and was extended to intra-EU B2C distance sales of goods on 1 Jul 2021, when the OSS took its current form) applies to cross-border B2C distance sales of goods and TBE services (below it, VAT *may* stay at origin); OSS returns are quarterly for Union/non-Union schemes and monthly for Import OSS (goods up to EUR 150) https://vat-one-stop-shop.ec.europa.eu/index_en , https://vat-one-stop-shop.ec.europa.eu/one-stop-shop_en . Odoo implements this as generated fiscal positions/taxes per destination country and an OSS report (Sales / Imports) exported as PDF/XLSX/XML, not auto-filed [V] https://www.odoo.com/documentation/19.0/applications/finance/accounting/taxes/eu_distance_selling.html . Odoo also offers VIES VAT number validation and tax units.
- **ViDA [V]:** Directive (EU) 2025/516, Regulation (EU) 2025/517, Implementing Reg. 2025/518; adopted 11 Mar 2025, in force 14 Apr 2025; from then Member States may mandate domestic e-invoicing without a derogation; 1 Jul 2028 platform deemed-supplier (Member States may postpone it to 1 Jan 2030) and Single VAT Registration/extended OSS; **1 Jul 2030** Digital Reporting Requirements (intra-EU B2B); 1 Jan 2035 alignment of domestic real-time systems https://taxation-customs.ec.europa.eu/taxation/vat/vat-digital-age-vida_en . Design consequence: every invoice must retain EN 16931 structured data, 10-day issuance rules for intra-EU supplies apply from 2030 [S].
- **US sales tax [V]:** every state with sales tax has economic-nexus rules; the common trigger is USD 100,000 in sales (some add 200 transactions; California, Texas and New York use USD 500,000; Alabama and Mississippi USD 250,000); Illinois dropped the transaction prong 1 Jan 2026, Kentucky 1 Aug 2026; four states have no state sales tax (DE, MT, NH, OR) https://www.salestaxinstitute.com/resources/economic-nexus-state-guide (chart as of 2026-08-01). Rates vary by thousands of local jurisdictions and product taxability [U]; building an in-house rate engine is not realistic, so integrate a tax-calculation service behind a trait. Odoo uses Avalara AvaTax (`account_avatax` per https://www.odoo.com/documentation/19.0/applications/finance/fiscal_localizations/united_states.html source; no such module is in the Community 20.0 tree) [V docs; V by absence]; its Brazil integration also runs through Avalara (`l10n_br_edi`) [V https://www.odoo.com/documentation/19.0/applications/finance/fiscal_localizations/brazil.html ]. Stripe Tax calculates for 100+ countries, supports non-Stripe payments through its API, and files in 90+ countries via partners https://stripe.com/tax , https://docs.stripe.com/tax/supported-countries .
- **Reverse charge / withholding / non-deductible VAT:** Odoo 20 supports withholding tax on payment (amount due / withhold due / net due split) and non-deductible tax line types [V]. Design these as repartition-line and `display_type` features, not special cases.

## 4. Audit trail and immutability

- **Odoo's hash chain [V source]:** each posted move in a hashing journal gets `inalterable_hash = sha256(previous_hash + canonical_json)` where the JSON (sorted keys, no whitespace) covers `name, date, journal_id, company_id` plus per-line fields; monetary values are formatted with the currency's decimals (hash version 3+), and version 4 prefixes the hash as `$4$<hex>`; a gap-free `secure_sequence_number` is kept; an integrity report recomputes the chain. Modifying hashed fields raises an error. France's anti-fraud module (cash register software, CGI art. 286 I-3 bis, since Jan 2018; fine EUR 7,500) relies on exactly this plus a vendor-issued conformity certificate [V] https://www.odoo.com/documentation/19.0/applications/finance/fiscal_localizations/france.html . Odoo 20 extends hashing to cash journals.
- **Spain Veri*Factu (RRSIF, RD 1007/2023) [V]:** every invoice generates a *registration record* or *cancellation record* carrying a hash code built from parts of the immediately preceding record (SHA-256 [V]: Ministerial Order HAC/1177/2024, annex list L12 value "01" = SHA-256; hash inputs include issuer tax ID, invoice series/number, issue date, invoice type, total tax, total amount, previous record's hash and generation timestamp, art. 13.1; exact calculation detail is in an AEAT technical document) https://www.boe.es/buscar/act.php?id=BOE-A-2024-22138 ; non-Veri*Factu mode adds an electronic signature; the system keeps a tamper-evident **event log**; every invoice carries a QR code; two modes: Veri*Factu (records sent to AEAT in near real time) or local retention; producers must self-certify https://sede.agenciatributaria.gob.es/Sede/en_gb/iva/sistemas-informaticos-facturacion-verifactu/cuestiones-generales.html . Deadlines were postponed by Royal Decree-Law 15/2025 of 2 Dec: before 1 Jan 2027 for corporate-income-tax payers and before 1 Jul 2027 for others https://sede.agenciatributaria.gob.es/Sede/en_gb/iva/sistemas-informaticos-facturacion-verifactu/nota-informativa-ampliacion-plazo-adaptacion-facturacion.html .
- **Germany GoBD [S/U]:** Odoo's `l10n_de` enables the audit trail by default "to ensure compliance with GoBD" [V]. Invoices must be retained eight years, counted from the end of the calendar year of issue (section 14b(1) UStG [V] https://www.gesetze-im-internet.de/ustg_1980/__14b.html ) and, for e-invoices, **the structured XML is the legally decisive record and must be kept in the received format** [S] https://www.vatupdate.com/2025/10/03/germany-e-invoicing-b2b-mandate-timeline-and-compliance/ . Cash registers: KassenSichV TSE (Odoo uses the Fiskaly cloud TSS) [V]; a draft bill of 23 Sep 2026 proposes digital receipts and mandatory electronic registers above EUR 100,000 turnover from 2028 [S].
- **France:** the PA/PPF e-invoicing reform (section 5) is separate from the anti-fraud certification regime for cash software (NF525/LNE or self-attestation) [U on the certification mechanics; Odoo treats it as a module plus vendor certificate]. FEC export is a statutory accounting file (Odoo supports import and export) [V].
- **Portugal, Italy, Poland, Norway etc.:** certified software/ATCUD/SAF-T(PT) (first mandatory annual SAF-T accounting file for FY2026, filed in 2028 [S]); SAF-T is an OECD-standard XML audit export, so obop should treat "audit file export" as a plug-in family (SAF-T, FEC, DATEV, GoBD, JPK).

### 5.3 How Odoo delivers it and what that teaches
Odoo builds EN 16931 documents in `account_edi_ubl_cii` with format classes for UBL BIS3, XRechnung, NLCIUS, EFFF, SG, AU/NZ, PINT and Factur-X CII, and relays Peppol through its own IAP proxy (`account_edi_proxy_client`, `account_peppol`, 21 countries listed) [V source]. Country-authority connections are frequently **outsourced to certified intermediaries**: mojeRaCun (Croatia), Nilvera (Turkiye), PAC (Mexico), Avalara (Brazil), e-invoo (Greece), Fiskaly (German TSE), Odoo's own PA (France) [V docs/source; the Mexico, Brazil, Turkiye and Fiskaly modules are not in the Community 20.0 tree]. KSeF, Veri*Factu, ZATCA and SDI are direct integrations: Odoo builds FA(3) XML, submits, polls status, fetches vendor bills every 3 hours and stores the UPO receipt (Poland) [V] https://www.odoo.com/documentation/19.0/applications/finance/fiscal_localizations/poland.html .

### 5.4 Peppol economics for an open-source project
Becoming a Peppol Access Point needs OpenPeppol membership: for 1-50 employees, Access Point only is EUR 1,050 sign-up + EUR 1,850/yr + EUR 1,500 certification (one-time, at first certification); with SMP the fee depends on size: 1-10 employees EUR 1,800 + 2,750/yr + 2,500, 11-50 employees EUR 2,100 + 3,700/yr + 2,500 (fees for members joining from 1 Jul 2025; earlier members pay these from 1 Jan 2026; the joining-year annual fee is pro-rated) [V] https://peppol.org/join/fees/ . A sensible OSS posture: ship a `PeppolTransport` trait, bundle an adapter to open-source AS4 (phase4 is Java; no production Rust AS4 stack found [I]) and let adopters or a commercial hosting arm hold the AP certification.

## 7. Which jurisdictions first

Rationale: a single EN 16931 engine plus Peppol BIS 3.0, UBL/CII and Factur-X covers the largest share of mandated markets (BE, DE, FR via PA, NL, Nordics, LU, IE, SK, AU/NZ/SG/UAE/OM via PINT). Authority-specific adapters are second-layer plug-ins.

1. **Wave 0 (core, no country):** EN 16931 model + validation, UBL/CII/Factur-X/XRechnung, Peppol transport trait, SAF-T-style audit export, generic chart.
2. **Wave 1:** **Germany** (largest EU economy, no authority connection, deadlines 1 Jan 2027/2028, SKR03/SKR04, DATEV export, GoBD), **Belgium** (Peppol only, already live, small chart PCMN), **France** (Sept 2026 live, Sept 2027 SMEs; connect to a PA via API, FEC, PCG; do not become a PA), **United States** (English baseline, no e-invoicing, sales-tax service integration, 1099/NACHA) and **Netherlands** (Peppol, NLCIUS, RGS).
3. **Wave 2 (authority adapters with open specs):** **Poland KSeF** (API said to be free (unverified), mandatory for all since 1 Apr 2026 with the PLN 10,000/month tolerance to 31 Dec 2026), **Spain Veri*Factu** (hash chain + QR, 1 Jan/1 Jul 2027), **Italy SDI**, **Croatia** (via intermediary), **Romania**, **Saudi ZATCA** (published SDK and spec (unverified)), **UAE/Oman** (Peppol PINT).
4. **Wave 3:** India (IRP), Brazil and Mexico (PAC/SEFAZ, very large tax rulesets; partner with local certifiers), Turkiye, Greece, Slovakia, Malaysia/Singapore.

## 8. Pluggable localization architecture (proposal [I])

**Localization pack** = a versioned, signed bundle with a manifest (`country`, `valid_from/valid_to`, `depends`, `capabilities`) containing data plus optional Rust code behind traits. Patterned on Odoo's `account.chart.template` (templates registered by code such as `de_skr03`, per-model CSV files `account.account-de_skr03.csv`, `account.tax-...`, `account.fiscal.position-...`, `account.tax.group-...`, `account.depreciation.model-...`, plus `res.company` defaults like `receivable_account_id`, `income_currency_exchange_account_id`) [V].

| Layer | Form | Contents |
|---|---|---|
| Chart template | declarative data | accounts (code, name, type, reconcile, tags), parents, journal defaults, company default accounts, template inheritance |
| Tax template | declarative data, effective-dated | taxes, groups, repartition lines + tags, exigibility, fiscal positions, withholding, OSS mappings |
| Report definitions | declarative expressions over tags/accounts | VAT return, balance sheet, P&L, statutory annual accounts, aged balances |
| Statutory exports | code plug-ins | FEC, DATEV, SAF-T variants, JPK, Modelo 303/347/349, UStVA, Intrastat, EC Sales List |
| Document format plug-ins | trait `DocFormat { id, version, build, parse, validate }` | UBL-BIS3, CII, Factur-X, XRechnung, FA(3), FatturaPA, HR-FISK, ZATCA UBL, PINT-xx, CFDI, NF-e |
| Transport/clearance plug-ins | trait `EDocTransport { send, poll, receive, cancel }` with status state machine | Peppol AP, KSeF, SDI, AEAT, ZATCA, IRP, PAC adapters; credentials vault; retry/idempotency |
| Integrity profiles | policy data | gapless-sequence scope, hash-chain fields+version, QR spec, lock defaults, retention years |
| Validators | sidecar or compiled | Schematron (KoSIT validator as test oracle), business-rule crate |

Rules: core never imports a country; packs register via a registry at startup; pack upgrades are migrations keyed by `template_version`; tax rates and codelists ship as data releases independent of core (EC code lists change every May and November [V]); each e-document keeps **raw XML + SHA-256 + authority receipt** immutably.

## 9. Data-integrity invariants to enforce in the database

1. **Balanced entry:** for every posted entry, `SUM(debit)=SUM(credit)` in company currency, checked by a `DEFERRABLE INITIALLY DEFERRED` constraint trigger at commit. (Odoo checks only in the ORM [V].)
2. **Line rules:** `debit>=0 AND credit>=0 AND debit*credit=0`; sign of `balance` equals sign of `amount_currency`; `amount_currency=balance` when currency equals company currency; non-accountable (section/subsection/note) lines have no account/amounts [V: Odoo 20.0 has exactly these SQL CHECKs on `account.move.line`: `credit*debit=0`, sign agreement of `balance` and `amount_currency`, account required on accountable lines, nulls on non-accountable lines; the `>=0` and same-currency equality rules are obop proposals [I]].
3. **Exact money:** `NUMERIC`/integer minor units only, never floating point; per-currency scale enforced by CHECK; the rate used is stored on the line.
4. **Posted immutability:** triggers reject UPDATE/DELETE of posted moves and lines (amounts, accounts, dates, partner, currency, taxes); corrections only by reversal; `DELETE` revoked from the app role.
5. **Gapless numbering:** sequence allocated at post time inside the same transaction from a locked counter row per (company, journal, period scope), `UNIQUE(company, journal, name)`; Postgres sequences are not gapless. (Odoo only flags gaps after the fact [V]; several regimes, e.g. France anti-fraud and Veri*Factu chains, expect no gaps.)
6. **Hash chain:** per (company, journal/sequence scope) `hash = SHA-256(prev_hash || canonical(fields))`, versioned prefix (`$4$`), append-only, periodic verifier; needed for Veri*Factu-style and French anti-fraud regimes.
7. **Lock dates in DB:** reject inserts/updates with `date <= hard_lock_date` always, and `<= soft lock` unless an unexpired `lock_exception` exists for the user; tax lock on lines carrying taxes.
8. **Account rules:** account code unique per company; receivable/payable are reconcilable; type change forbidden once posted; off-balance accounts only with off-balance accounts, no tax, no reconciliation [V]; no posting to parent/deprecated accounts.
9. **Reconciliation:** `SUM(partials)` on a line never exceeds its absolute amount in both currencies; same account, company and (where required) partner; full reconcile only at zero residual; exchange-difference entries flagged system-generated.
10. **Tax configuration:** repartition factors per tax and document type sum to 100; base/tax lines point to tax and repartition line; tax validity periods non-overlapping using PostgreSQL's temporal constraints (`PRIMARY KEY ... WITHOUT OVERLAPS`, `FOREIGN KEY ... PERIOD`, available since PostgreSQL 18.0, released 2025-09-25; the non-temporal key columns need the `btree_gist` extension unless they are range types; temporal foreign keys support only `NO ACTION`) [V https://www.postgresql.org/docs/release/18.0/ , https://www.postgresql.org/docs/18/sql-createtable.html ]; fiscal years also non-overlapping per company.
11. **Multi-company isolation:** `company_id` on every table; composite foreign keys `(company_id,id)`; Row-Level Security policies on company.
12. **Documents:** credit notes reference their original and cumulative credit cannot exceed it; totals equal line sums; e-invoice artefact row stores canonical XML hash and cannot change after issuance; status transitions enforced by a transition table.
13. **Bank/payment idempotency:** `UNIQUE(journal, provider_transaction_id)` on statement lines; webhook events deduplicated by provider event id; bank-account entries only via statement lines [V Odoo 20 behaviour].
14. **Append-only audit log:** separate `audit_event` table (actor, time, table, key, old/new) writable only by trigger, no UPDATE/DELETE grants, optionally hash-chained.
15. **Retention guard:** delete and anonymise operations blocked until the jurisdiction's retention period passes (Germany eight years for invoices, section 14b(1) UStG [V]; Croatia 11 years for e-invoice XML [S]; Belgium seven years per Odoo's Belgium page [S]; India 6+ years [S]; other periods [U]).

Platform facts: PostgreSQL 18.6 is current stable (2026-08-13); PG 19 Beta 4 shipped 2026-09-24; PG 18 (18.0 released 2025-09-25) adds `uuidv7()`, virtual generated columns (now the default) and async I/O [V https://www.postgresql.org/ , https://www.postgresql.org/docs/release/18.0/ ]. Rust stable is 1.98.1 (2026-09-03) [V GitHub releases].

## Implications for obop

**MUST**
1. **MUST enforce ledger integrity in Postgres, not just Rust:** deferred balanced-entry trigger, posted-row immutability triggers, lock-date triggers, gapless per-journal numbering with a unique index, RLS by company. Odoo's ORM-only balance check is the anti-pattern (section 9).
2. **MUST implement a per-journal hash chain** (versioned, canonical serialization, verifier job) and a separate append-only audit table from day one; Veri*Factu (deadlines 1 Jan/1 Jul 2027) and French anti-fraud regimes both require it, and retrofitting is painful.
3. **MUST store the authoritative structured e-invoice (raw XML + hash + authority receipt) as an immutable artefact;** PDFs are renderings (German rule: the structured part is the legal record [S]).
4. **MUST build the finance core on EN 16931** as the internal invoice semantic model with UBL and CII serializers and KoSIT/CEN validation in CI, then layer Factur-X/XRechnung/Peppol BIS 3.0 on top. Track the May/November artefact cycle (next effective 16 Nov 2026).
5. **MUST model taxes like Odoo's repartition-line design** (amount types group/fixed/percent/division, price-included, base-affecting, cash-basis exigibility, tags, fiscal positions, withholding), effective-dated via PG18 temporal constraints.
6. **MUST keep multi-currency exact:** store rate used, generate exchange-difference entries, add CTA/translation support for consolidation; never use floats.
7. **MUST NOT copy Odoo Enterprise or OCA (AGPL) code;** treat Enterprise-tier features (reports engine, bank reconciliation UX, assets, deferrals, consolidation, bank sync) as clean-room from docs and behaviour.
8. **MUST ship the localization-pack architecture (section 8)** so country logic never leaks into core.

**SHOULD**
9. **SHOULD prioritise DE, BE, FR, US, NL first, then PL, ES, IT, HR, RO, SA, AE** (section 7). France: integrate with a PA over API rather than seek PA accreditation.
10. **SHOULD add explicit `fiscal_year` (and optional period) tables** with non-overlapping temporal constraints, instead of Odoo's day/month-only setting.
11. **SHOULD use Odoo 20's lock model** (fiscal-year, tax, sale and purchase soft dates + irreversible hard lock + expiring `account.lock_exception`; source-verified in 20.0, its introduction in 19 could not be confirmed from the 19 release notes), and its 20 changes: parent accounts, bank-origin-only bank entries, payment status "Paid" vs "Reconciled", single consolidated exchange-difference line.
12. **SHOULD abstract transports behind traits and lean on intermediaries** (Peppol APs, Fiskaly-style TSE, PACs), as Odoo does for Croatia, Turkiye, Mexico and Brazil; budget OpenPeppol fees (up to about EUR 4.4k in the first year for a small AP incl. certification; the joining-year annual fee is pro-rated [V]) only if obop runs a hosted service.
13. **SHOULD treat Rust e-invoicing crates as accelerators only** (en16931 is about two months old, ksef about seven, verifactu about eleven; zugferd is older but still 0.1.x) and keep KoSIT validator, Mustang and phase4 as external oracles/sidecars.
14. **SHOULD abstract sales-tax calculation** (Stripe Tax / Avalara / in-house table) behind a `TaxProvider` trait for the US; do not build a jurisdiction-rate database.
15. **SHOULD pin PSP API versions per connector** (Stripe is now `2026-09-30.endive` with breaking changes) and make webhook handling idempotent with provider-event-id uniqueness.
16. **SHOULD parse camt.053 and MT940 first, OFX second, CSV mapping UI third,** and define a `BankFeed` trait with adapters for Enable Banking and GoCardless; expect PSD3/PSR to change access rules.

**COULD**
17. **COULD** use WASM-sandboxed third-party localization packs for community contributions.
18. **COULD** add an optional TigerBeetle-backed projection for high-volume POS ledgers; keep Postgres as system of record.
19. **COULD** offer a hosted Peppol AP/PA-connector service as the commercial arm (certification cost small relative to value), and a free self-serve KSeF/Veri*Factu/ZATCA gateway.
20. **COULD** add SAF-T, FEC, DATEV, JPK exports as a shared "audit file" plug-in family since all are projections of the same ledger.
