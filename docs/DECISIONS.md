# obop decision register

**Status:** Draft 0.1 for owner ratification. **As of:** 2026-10-01, called month 0 (M0). **Scope:** product and architecture. Nothing here is legal advice; items marked "counsel" need a lawyer.

## 0. Front matter and how to read

This register is authoritative for every other obop document. Where a research note (R01-R28, index R00) disagrees with it, this file wins. Where it is silent, the research stands and later notes outrank earlier ones (R23, R24 and R26 outrank the rest). Module-level design rules (the MUST lists of R09-R16 on ledger, stock, pricing, subscriptions, POS, payroll, services) are not repeated here; module design documents must restate them and cite the R-tag. [CONVENTIONS.md](CONVENTIONS.md) fixes the spelling of names that cross documents (events, permission groups, data classes, states, ports); where it differs from this register, this register wins, and it never settles an owner question. Nothing is built yet.

| Status | Meaning | Rule for writers |
|---|---|---|
| FIXED | Owner-mandated | Never changes without the owner |
| BINDING | Research-resolved technical decision | State as fact; changing it needs a new ADR (next free D-ID; the old record is marked "Superseded by") |
| PROPOSED | Needs explicit owner ratification | Write "Proposed (Dn)" wherever you rely on it |
| DEFERRED | Decide later, with a trigger | Do not design around a guess; cite the trigger |

Conventions. "R23 DR-1" means decision record 1 in research note 23 (section 9 maps tags to files). Dates are ISO-8601, money is EUR ex VAT, "M9" is month 9 after M0. Reversibility is "one-way door" (cannot be undone cheaply once data, licences or outsiders depend on it) or "two-way door". The owner ratifies a PROPOSED record by saying so in chat; the record then gains a "Ratified" line and becomes BINDING. Documents must never write "GA" bare; see D26. Wave (W0-W4), release-number and calendar references inside a BINDING record are placements under D25 and D26, which are PROPOSED: the technical rule is BINDING, the placement stays Proposed until those are ratified. Where a record's own clause rests on a Proposed item (D15 and D23 on I-4 and I-3, D24 on its renames), the record says so.

## 1. Fixed constraints

| ID | Constraint |
|---|---|
| F1 | Backend: exclusively the latest stable Rust, edition 2024. |
| F2 | Frontend and tooling: exclusively the latest Vite+ (`vite-plus`). Every JS/TS task runs through the `vp` CLI. pnpm is the only package manager; `npm`, `npx`, `yarn` and `bun` are never used (CLIs, CI, docs, examples) and `package-lock.json`, `yarn.lock`, `bun.lock` are never committed. pnpm still installs from the public npm registry, so naming the registry or a package is fine. Research passages saying Vite+ supports several package managers describe the tool, not policy. |
| F3 | Clean-room relative to Odoo. Odoo is the functional reference. No Enterprise code or assets, no copied Community code, views, translations or assets, no OCA code. | F4 | Open source: the core product is OSI-approved open source. Which licence is D1. |

Interpretations, all Proposed (Q10):

- **I-1.** "Backend exclusively Rust" governs code obop authors and ships. Programs obop only runs or tests against (PostgreSQL, PgBouncer, pgBackRest, OCR engines, LiveKit, Weblate, and validators such as KoSIT, Mustang, phase4 as CI oracles) are dependencies. obop authors no Java, Python or Node server code; off-the-shelf sidecars stay optional and out of the default install.
- **I-2.** "`vp` only" means every JS/TS build, test, lint, format, task and environment command is `vp`; `vp install`, `add` and `remove` reach pnpm, as do the typed `vp pm` subcommands (`audit`, `approve-builds`, `publish`, `stage` and others). `vp pm` is a closed command set, not raw forwarding (checked against vite-plus v1.0.0, source and the installed `vp`, 2026-10-01). Direct `pnpm` is allowed only where `vp` has no wrapper: `vp pm sbom` and `vp pm licenses` do not exist, and `vp pm audit signatures` is rejected and must be written `vp pm audit -- signatures`. The JavaScript SBOM and licence scan therefore run as `pnpm sbom` and `pnpm licenses list` through the vp-managed pnpm, invoked as `vp env exec pnpm sbom ...` or inside a `vp run` task; whether that counts as "`vp` only" is the owner's ruling (Q10) and stays open. Ad-hoc fetch-and-run is `vp dlx`, never in CI. The CI lint fails on any other JavaScript package-manager lockfile (the Rust `Cargo.lock` is committed and is not in scope), naming `package-lock.json`, `npm-shrinkwrap.json`, `yarn.lock`, `bun.lock` and `bun.lockb` (F2 lists the first, third and fourth; this is the same rule in full).
- **I-3.** "Latest" means the newest release that passes the pin policy below. Until the owner ratifies this (Q10), the project intentionally runs up to about three weeks behind the newest release, which is one release behind the literal F1 and F2 wording (Rust 1.98.1 while 1.99.0 was published on 2026-10-01).
- **I-4.** The nightly exit drill (section 1.1) is a named exception to "`vp` only": a rehearsal on a throwaway copy of the tree that never ships and is never an obop build path. It is the one place upstream Vite, Vitest, Oxlint and Oxfmt run without `vp`, through pnpm scripts. Shipped builds, CI gates and developer commands always use `vp`.

### 1.1 Pin policy: what "latest" means (D23)

**Status.** PROPOSED with I-3 and I-4 (Q10), applied provisionally from 2026-10-01. It turns the word "latest" in F1 and F2 into dated rules and deliberately runs up to about three weeks behind the newest release until the owner ratifies it.

**Rust.** `rust-toolchain.toml` carries an exact `channel = "x.y.z"` on every branch, with rustfmt and clippy; builds use `--locked`; release builds set `overflow-checks = true`. A release is eligible when it is x.y.1 or later, or x.y.0 at least 14 days old with no open stable-to-stable regression. Adopt within 7 days of eligibility, so the maximum lag is about three weeks. Reason: 1.96.1, 1.97.1 and 1.98.1 each fixed a miscompilation. Skip list: 1.98.0 (vtable regression, rust-lang/rust#161441). A compiler or std advisory overrides the waiting period on every branch. LTS branches keep a per-branch toolchain in a digest-pinned builder image and change it only for such an advisory.

- **Today (2026-10-01): pin 1.98.1 (Proposed, D23; Q10).** Rust 1.99.0 was published on 2026-10-01 (blog post dated that day; `channel-rust-stable.toml` serves it, manifest Last-Modified 12:38 UTC, after a 404 at about 10:10 UTC). The pin stays 1.98.1 because of the rule above (x.y.0 plus 14 days), not because the channel lacks 1.99.0. Adopt 1.99.x between 2026-10-15 (1.99.0 plus 14 days) and 2026-10-22, or at 1.99.1 if that comes first, once debug and release-mode CI pass. 1.99 turns incremental compilation off when `CI` is set. Expect 1.100.0 about 2026-11-12 (eligible 2026-11-26, or at 1.100.1); it brings `wasm32-wasip3` to stable (Tier 3 in 1.99.0; promoted to Tier 2 by rust#161940, milestone 1.100.0).
- **Re-check:** a weekly Renovate toolchain group, a nightly beta canary, and a manual look every six-week release Thursday.

**Vite+.** `vite-plus` is a project-local dependency at an exact version (no range). The exact pnpm is pinned with `vp env pin pnpm@<x.y.z> --target package-manager` (without `--target`, Vite+ 1.0 writes `devEngines.packageManager` instead of the top-level `packageManager` field that the CI guardrails expect), Node in `.node-version`, and `pnpm-lock.yaml` is the only JavaScript lockfile committed (the Rust `Cargo.lock` is committed as well); CI runs `vp install --frozen-lockfile` with `voidzero-dev/setup-vp` at an exact release or SHA (never `v1`) or a digest-pinned image. "Latest Vite+" means the newest `vite-plus` that is at least 7 days old and passes: the exit drill, a LICENSE/NOTICE diff, exactly one Vite and one Vitest copy (`vp why`), and the test suite. One Renovate group moves `vite-plus`, the `vite` alias to `@voidzero-dev/vite-plus-core` and the `vitest` pin in lockstep.

- **Today (Proposed, D23; Q10):** `vite-plus` 1.0.0 (2026-09-28, MIT) becomes eligible 2026-10-05. Its bundle is the toolchain of record: Vite 8.3.1, Rolldown 1.2.11, Vitest 5.0.1, Oxlint 1.85.0, oxlint-tsgolint 7.0.2003, Oxfmt 0.70.0, tsdown 0.23.0. Upstream is already newer (Vite 8.3.2, Rolldown 1.2.12, Vitest 5.0.3, Oxlint 1.86.0, Oxfmt 0.71.0); that lag is accepted and the bundle is not overridden piecemeal. Exception: a published advisory in a bundled component with no Vite+ release within 7 days permits a logged, temporary override.
- **Node:** 24 LTS now; move to Node 26 (LTS from 2026-10-28) by 0.2 (2027-02-02) and before any LTS branch is cut. Node 24 ends 2028-04-30.
- **pnpm version:** one exact `x.y.z` (never a range or dist-tag), pinned with `vp env pin pnpm@<x.y.z> --target package-manager`, under the same 7-day age rule; a new major is adopted only after the settings below are verified on it. Registry state 2026-10-01 14:07 UTC: `latest` and `latest-12` = 12.8.1, `next-12` = 12.8.2, `latest-11` = 11.28.2, `next-11` = 11.28.3. pnpm 12 is the Rust port and the current major; pnpm 11 is the JS line and is still released. The six workspace keys of the settings bullet below were read without warning by pnpm 12.8.1 (checked 2026-10-01, a parse check only); behavioural verification is still on 11.x only. Under the 7-day rule the newest eligible version today is 12.6.0 or 11.27.1; 12.8.1 and 11.28.2 become eligible on 2026-10-05. Which major is the owner's call (Proposed; Q15).
- **pnpm settings:** `minimumReleaseAge` of at least 7 days (strict), `trustPolicy: no-downgrade`, `blockExoticSubdeps`, `strictDepBuilds` with an `allowBuilds` allow-list, and a scanner that reads both YAML documents of `pnpm-lock.yaml`.
- **Exit drill (Proposed exception, I-4; Q10):** a nightly job builds a throwaway copy of the tree with plain Vite 8, Vitest 5, Oxlint and Oxfmt, outside `vp`; a human reviews it quarterly. Until the owner records the exception, the drill is PROPOSED, not BINDING (D15, ruling 26). Tripwires that reopen the Vite+ risk (not the constraint): a licence or NOTICE change; remote cache or core `vp` features behind a paid service; a 1.x minor that breaks a CLI flag or config key; plan issue #2405 slipping a quarter.

**Other dependencies.** Versions live in `[workspace.dependencies]`. Renovate cooldowns: crates 7 days, JS packages 7 days, GitHub Actions pinned by SHA 3 days; security updates skip the cooldown but are reviewed by hand. cargo-deny blocks PRs; pre-1.0 vendor crates are pinned exactly; wasmtime follows D11.

### 2.2 Records

#### D1 Core licence, contributor terms, governance
**Status** PROPOSED. **Reversibility** one-way door. **Owner action** yes (Q1): ratify by 2026-10-20 and instruct counsel.

**Decision.** Core and first-party apps under AGPL-3.0-or-later (counsel may choose `-only`) plus an AGPL s7 Application Exception; Apache-2.0 for SDKs, WIT worlds, UI SDK and templates; a commercial `ee` tree in separate artefacts. The CLA is a licence grant (not an assignment) with a patent licence and an irrevocable "OSI licence forever" pledge. A company (CRA manufacturer, cloud, `ee`) plus an EU non-profit steward that holds the trademark and can veto leaving OSI licences.

**Why.** Passes NLnet, Sovereign Tech Fund and public-sector gates; protects against proprietary forks; keeps CRA free-software treatment. **Rejected.** FSL, BUSL, SSPL, ELv2 (not OSI); Odoo-style LGPL plus proprietary EE; permissive core; DCO only; assignment CLA. **Consequences.** Nothing public until counsel covers exception drafting, CLA text, mixed-licence repository, CRA roles, steward form, trademark, patents, dependency compatibility and funder terms (R17 s12). The default Q5 answer date (2027-06-01) falls after the latest public flip (2027-04-06, D26), so the owner must settle in Q16 whether "covers" means written counsel advice or formed entities, or move Q5 earlier. #### D7 Realtime and queue signalling
**Status** BINDING. **Reversibility** two-way door (low to medium). **Owner action** no.

**Decision.** `NOTIFY` is forbidden in business transactions; CI allows it only in `obop-bus-notifier`. Durable events are outbox rows plus per-subscriber delivery rows. #### D10 Authorization algebra and RLS
**Status** BINDING. **Reversibility** one-way door in practice (every module's seed access data). **Owner action** no.

**Decision.** Odoo 20's algebra: OR of permission rows, AND of restriction rows, compiled from the Domain AST to SQL, one path for list, by-id, export, webhook and AI reads. **Why.** RLS cannot express the algebra; Cedar cannot filter lists. **Rejected.** Default-allow `ir.rule`; ABAC engine; RLS primary. **Consequences.** A property test must give identical answers from list, by-id, export and RLS paths; benchmark the restrictive policy on 10M ledger rows. **Evidence.** R23 DR-4, R18 s3, R02.

**Why.** Studio-class customisation, APIs and agents are cheap only if built-in behaviour is metadata. **Rejected.** A static ORM as the core; EAV. **Consequences.** Compile times in a 100-plus crate workspace need a strict crate DAG and sccache. **Evidence.** R08, R06, R02, R23.

#### D30 Database-enforced integrity
**Status** BINDING. **Reversibility** one-way door. **Owner action** no.

#### D40 Mask-and-restore at the command boundary
**Status** PROPOSED. **Reversibility** two-way door. **Owner action** yes (Q21).

**Decision.** Every read surface of the typed command API (REST, MCP, CLI and the AI gateway) shapes its response through one masking policy, resolved per principal and per data class ([CONVENTIONS.md](CONVENTIONS.md) section 5) from registry metadata. Modes: `allow`, `mask` (a reversible token such as `PERSON_12`, stable inside a business and principal session), `redact` (irreversible) and `deny`. Defaults for agent principals: the three sensitive classes `deny`, other `personal_data` fields `mask`, `secret` never leaves the vault. On write, a token in a command input is resolved server-side only if the principal could read the underlying record under D10; an unresolvable token rejects the command. Token tables sit in the business database and are erased with the data subject (erasure, [spec/security-privacy.md](spec/security-privacy.md) 4.6). Masking is applied where the data leaves the permission path, so it cannot be skipped by a client, a module or a model route.

**Why.** Agents and external MCP clients send what they read to a model the business does not control; a block-or-allow egress rule (ai 4.5) either withholds too much to be useful or leaks too much. **Rejected.** Client-side masking; masking only inside the AI gateway (W3), which leaves W1 MCP unprotected; raw text-to-SQL. **Consequences.** The masking engine is a kernel component; a field without a data class cannot be masked, which D41 forbids. Whether token stability should span sessions is open (Q21). **Evidence.** D10, D18, D33, R16, R18 s12.

#### D41 Agent-ready module contract
**Status** PROPOSED. **Reversibility** one-way door once third parties publish. **Owner action** yes (Q21).

**Decision.** Everything a module adds is reachable by agents and operators through the same generated surfaces, and nothing is reachable without metadata. Every model, field, command, view and event declares a description, a permission group and a data class (or an explicit non-personal marker); REST, OpenAPI, MCP tools and `obop` CLI commands are generated from the registry, never hand-written, so a command exists on all four or on none. A module may narrow who may call a command (permission, `agent_readable`), not remove it from the surface. Its `obop.toml` also declares its network destinations and the data classes it will egress. The structural suite and the install gate reject a first-party or marketplace package that fails any of this.

**Why.** "Everything has AI and CLI access" and "agents are principals" (D18) only hold if no module can add a side door or an unclassified field. **Rejected.** Opt-in agent exposure; hand-written per-module CLIs. **Consequences.** Extends the structural checks of [ENGINEERING.md](ENGINEERING.md) section 1.4 and the package manifest of D32; raises the cost of writing a module slightly and removes a class of review work. **Evidence.** D18, D29, D31, D32, R21, R24.

#### D44 Storage backends: SQLite locally, PostgreSQL for deployments
**Status** BINDING (owner-directed in chat, 2026-10-16). **Reversibility** two-way door. **Owner action** no.

**Decision.** Local development and solo use run on SQLite (`sqlite://PATH`, the default is `obop.db`); every deployment, including hosted targets such as Sliplane (D43), runs on PostgreSQL 17 or 18 (`postgres://...`). The storage layer (`obop-storage`) is one small contract with memory, SQLite and PostgreSQL backends, selected by `--db` or `OBOP_DATABASE_URL`, and every backend must pass the same contract test; PostgreSQL is tested in CI and locally against a container. This supersedes the clause of D37 that SQLite is never the domain database and the embedded-PostgreSQL solo profile as the default; embedded PostgreSQL stays possible. **Why.** A zero-setup local start removes the biggest barrier for module authors and agents trying obop; PostgreSQL stays the production target. **Rejected.** SQLite everywhere (cannot meet D30); PostgreSQL required locally. **Consequences.** Migrations and the schema manager (`obop-schema`) target PostgreSQL first, so SQLite support for typed columns lags and may stay document-style; an export from SQLite to PostgreSQL is needed before any production use (Proposed); the SQLite backend must not appear in the compliance test matrix. **Evidence.** D6, D8, D30, D37.

#### D45 Installable declarative packages and the instance admin
**Status** BINDING (owner-directed in chat, 2026-10-16). **Reversibility** two-way door. **Owner action** no.

**Decision.** An instance administrator installs, upgrades and removes packages while the server runs, from an uploaded `obop.toml` or from a marketplace catalog. The first package tier is X1 (D11): models, fields with a data class and permission group, and state-transition actions, with no code. The install path parses the manifest, builds registry metadata, runs the D41 gate, checks for name collisions, and registers generated CRUD plus actions on the one dispatcher, so REST, MCP, the CLI, masking and agent approval apply to a new module with no further work. Model names must be the module id or start with `<id>_`; a package may not declare network destinations. Removal unregisters commands and keeps the data. Installing, upgrading and removing are `platform.admin` commands that agents may only propose (D18). The marketplace is a trait with a bundled catalog and an optional HTTP catalog (`OBOP_MARKETPLACE_URL`). `platform.admin` is a superuser group: it satisfies every group check for a human, while an agent's token scopes still list concrete groups. The control plane (`obop platform serve`) lets a person sign up and get their own instance; the owner's password hash seeds the instance's first admin.

**Why.** "Install modules, upload your own, download from a marketplace" needs code-free packages first: they are safe to install at runtime and already inherit every cross-cutting rule. **Rejected.** Native or Wasm packages as the first tier (X3 stays in D11 and comes later). **Consequences.** Package signing, publisher accounts, paid listings, schema migration on upgrade and custom commands beyond state transitions are not built; behaviour that needs code waits for X2 (CEL) and X3 (Wasm). **Evidence.** D11, D18, D32, D41.

#### D46 Registry-driven backoffice with floating panels and a Customize app
**Status** BINDING (owner-directed in chat, 2026-10-16). **Reversibility** two-way door. **Owner action** no.

**Decision.** The backoffice renders from `GET /api/meta`, which lists the modules, models, readable fields (with data class and personal-data flag) and actions the signed-in principal may use, so a module installed at runtime appears with no frontend change and a field a principal cannot read is never described to it. The design takes Odoo's concepts (app launcher, a control panel with breadcrumbs, search, group-by and a view switcher, list and kanban views, a form with a status bar and action buttons, a command palette on Ctrl or Cmd + K) and presents them as floating rounded panels on a tinted canvas, with the record opening in a side panel beside its list. **Why.** The first backoffice was a generic table and read as unfinished; the product promise is one platform whose apps all look and behave alike. **Rejected.** A per-module hand-written UI (breaks "install and it just works"); copying Odoo's visuals. **Consequences.** Views beyond list and kanban (calendar, pivot, graph, report), a view designer, inline editing, bulk actions, saved filters and the chatter are not built; field types were added afterwards by D47, so the UI no longer has to infer money or state from names. **Evidence.** [spec/ux.md](spec/ux.md) 4.1 to 4.6 and 4.9, [research/19-ux-design-system.md](research/19-ux-design-system.md) section 2, Odoo 18 and 19 documentation for Studio, views and search.

#### D47 Typed fields
**Status** BINDING (owner-directed in chat, 2026-10-16). **Reversibility** two-way door. **Owner action** no.

**Decision.** Every field has a kind, serialised lowercase in manifests and in `/api/meta`: `text` (the default, JSON string), `longtext` (string, multi-line), `number` (JSON integer), `money` (JSON integer in minor currency units, never a float or a numeric string), `date` (string `YYYY-MM-DD`, a real calendar date, leap years included), `bool`, `select` (string, one of `options`) and `ref` (string, the id of an existing record of model `to`). A field also has `required` (default false): a required field must be present and non-null on create and may not be set to null on update; null or absent is allowed for the others. The generated create and update commands validate every input against these kinds before anything reaches the store, with errors of the form `<model>.<field> must be <kind description>` (HTTP 400); a `ref` is looked up in the store, so a dangling reference is an error. Validation sees real values, because the dispatcher restores masked tokens before the handler runs (D40). In `obop.toml` a field gains `kind`, `options` (select only), `to` (ref only) and `required`; inconsistent combinations are refused at parse time. A `ref` target must be a model of the same package (checked at parse time) or an already registered model (checked at install time). A `select` named `state` is the conventional status field and its options are the status order; `from` and `to` of a transition action must be among the options. The D41 gate additionally refuses a select without options or with duplicates, a ref with no target, and a field named `id`. `GET /api/meta` adds `kind` and `required` to every field, plus `options` for a select and `to` for a ref.

**Why.** The UI guessed types from names (`_minor` for money, `state` for status); agents and views need a contract they can rely on, and bad data should be refused at the door on every surface. **Rejected.** Validation in the UI only; typed PostgreSQL columns now. **Consequences.** Column types in PostgreSQL stay JSONB documents until the schema manager exists (D44), so kinds are enforced by the command layer, not by the database, and direct store writes (seeds, the erase command) bypass them. Floats are not a kind. Existing records are not re-validated, and the CLI converts `number`, `money` and `bool` arguments from text using the metadata. **Evidence.** D29, D40, D41, D45, D46.

#### D48 Governed fields and implicit transitions
**Status** BINDING (owner-directed through the integration review, 2026-10-16). **Reversibility** two-way door. **Owner action** no.

**Decision.** A *governed field* is a `select` field that is the `field` of at least one declared action (a transition: `field`, optional `from`, `to`). Transitions are part of the registry metadata (`CommandDef.transition`), declared by manifests and by built-in modules alike (`lead.stage`, `sale_order.state`, `invoice.state`). The installer registers, from that metadata, guards on the one dispatcher: a guard is a pre-hook on one command that sees the principal and the restored input, may refuse, normalise the input, name extra groups and demand approval, and is re-run when a proposal is approved. (1) `create` accepts a governed field only omitted (it becomes the first option) or equal to the first option. (2) `update` accepts a change of a governed field from `a` to `b` only as an implicit run of a declared transition with `to = b` and `from` unset or `= a`: the caller must hold that action's group, an agent's update is turned into an approval plan when the action needs approval (the approver must hold the action's group), and approval runs the action's own handler, so its side effects happen; any other change is refused with the targets reachable from `a`. An unchanged value is not a change. Ordinary fields of the same call are validated before any action runs, so a mixed update is applied completely or not at all. (3) Running an action (explicitly or implicitly) requires the current value to equal `from` and every `required` field to be set; the error names the field. (4) Guarded calls run under one dispatcher-wide lock from check to write. Manifests: action names are unique per model and may not be a generated command name; an action's `field` must be a `select` (any, not only `state`); `from` and `to` must be options and must differ.

**Why.** An integration review showed that any holder of a model's `write_group` could set `state` to `posted` through `update`, skipping the stricter group and the approval flag of the action; a permission model that the generic command bypasses is not one. **Rejected.** Special cases per module in the handlers (every new package would have to repeat them); removing `state` from `update` (breaks the UI's kanban drag and status bar, which send `update`); a separate permission on the field alone (cannot express per-transition groups or approval). **Consequences.** Seeds and direct store writes are not checked (D47 says the same of kinds). The lock serialises one server; two servers on one PostgreSQL database can still race between check and write until the database enforces transitions (D30). Only a single `select` field per action; no guards on other fields, so a posted record's other fields remain editable. Records created before an action gained `required` fields may need them filled before they can move. **Evidence.** D18, D41, D45, D47, MODULES.md section 6.1.

#### D49 Delete and server-side search
**Status** BINDING (owner-directed through the integration review, 2026-10-16). **Reversibility** two-way door. **Owner action** no.

**Decision.** Every model gets two more generated commands. `<model>.delete {id}` needs the model's `write_group`, is marked `needs_approval` (an agent only proposes it) and removes the record through `Backend::delete`; it is refused while any registered model has a `ref` field pointing at the record, with the referencing models, counts and up to five ids in the error. `/api/meta` reports `can_delete` per model. `<model>.list` accepts the optional `filter` (conditions `{field, op, value}` with ops `eq`, `ne`, `contains`, `in`, `gt`, `gte`, `lt`, `lte`, `is_null`, ANDed, validated against the field kinds), `order` (`[{field, dir}]`), `limit` (1 to 5000, default unlimited) and `offset`, and still returns a bare array. `<model>.search` takes the same input and returns `{rows, total}` with `total` counted before `limit` and `offset`. Comparison is typed (integers, calendar dates, option order). Filtering and ordering happen before masking and withholding, so a field the caller cannot read in clear (no group, secret class, or personal or sensitive data for an agent, D40) is refused with the same error as a field that does not exist, which closes the inference channel of D10. The query is evaluated in the command layer over the records of the model on every backend (memory, SQLite and PostgreSQL); only the returned page is masked.

**Why.** The client held every record to filter, sort and group it, which neither scales nor lets an agent ask a narrow question; and there was no way to remove a record. **Rejected.** Pushing predicates into PostgreSQL JSONB now (the typed columns of the schema manager are the right place, D44; a strict field whitelist makes it safe but it would be thrown away); a soft delete (no tombstones before the audit log exists); cascading deletes; changing the shape of `list`. **Consequences.** Search reads the whole model from the store, so it is linear in the table size; `obop-schema` replaces this. `delete` is a hard delete and is not the erasure story: personal data is anonymised by the owning module's `erase` command (`party.erase`), which keeps references valid and needs the privacy officer; delete only works on unreferenced records, and an agent can never delete without a human. The ref check sees only installed models. **Evidence.** D10, D29, D40, D41, D44, D47, D48.

#### D50 Public exposure and the public site
**Status** BINDING (owner-directed, 2026-10-16). **Reversibility** two-way door. **Owner action** no.

**Decision.** A package may declare `[model.public]` (docs/MODULES.md 3.6): `read` with a `published_field` and a whitelist of `fields`, `submit` with `submit_fields` and a `rate_limit_per_hour`, and token `receipt` fields. The D41 gate refuses a public field that is not class `none` or `public_directory`, is personal data, or is restricted to a group; a form may not collect sensitive classes or a governed state. The public is not a principal: `obop_commands::PublicApi` is the only door, it never goes through `Dispatcher::call`, and no bearer token can act as it. Submissions run the same typed validation and governed first-state rule as `create`; refs a visitor supplies must point at published records of public models; fields the route computes (prices) are validated but never come from the visitor; batches (an order and its lines) are one transaction (`Backend::insert_many`). `obop-site` renders the public website and shop server-side; `obop serve --public-site` mounts it at `/` and moves the backoffice to `/admin/`. A page or post is public through its `state` select (`published_value`), not a second boolean, so the approval on `publish` also gates public visibility.

**Why.** Every instance should be able to serve a shop and site from its own data without a framework, a build step or a second system, and without widening what anonymous visitors can touch beyond what the package states. **Rejected.** A public bearer token (any holder is "the public" everywhere); a separate boolean next to `state` (an agent could flip it without the publish approval); client-side rendering (no SEO, no agents). **Consequences.** No payment provider and no images yet (docs/STOREFRONT.md, Known gaps). **Evidence.** `docs/STOREFRONT.md` threat model with a named test per finding.

#### D51 Hosted MCP
**Status** BINDING (owner-directed in chat, 2026-10-17). **Reversibility** two-way door. **Owner action** no.

**Decision.** Every instance serves the MCP Streamable HTTP transport at `POST /mcp` (also `DELETE /mcp`; `GET /mcp` answers 405 because there is no server stream). It speaks the handshake-based revisions `2025-11-25`, `2025-06-18` and `2025-03-26` (JSON-RPC batches only on the last, as in those specifications) and answers `application/json`, never SSE. It is a transport only: `obop-http` carries messages and `obop-mcp` holds the one implementation of `initialize`, `tools/list` and `tools/call` that `obop mcp` (stdio) uses too, over the one `Dispatcher`, so permissions, masking and approvals are those of REST. Rules: `Authorization: Bearer` on every request, resolved by `Authenticator` like REST (session and agent tokens); a missing or bad token is 401 with `WWW-Authenticate: Bearer resource_metadata="<origin>/.well-known/oauth-protected-resource"`; `/.well-known/oauth-protected-resource` (RFC 9728) names the resource and the two token endpoints and omits `authorization_servers`, because there is no OAuth authorization server. `initialize` issues an `Mcp-Session-Id` (256 random bits) bound to the token that opened it; the session holds the masking `Vault`, so mask tokens are stable and restorable inside a session and isolated between sessions (this is the default of ai.md open question 0); an unknown, expired (2 h idle) or foreign session is 404, `DELETE` ends it. An `Origin` header must match the allow-list (`OBOP_ALLOWED_ORIGINS`, `OBOP_PUBLIC_URL`, same-origin on a loopback host) or the request is 403. Limits: 1 MiB body, 600 requests per minute per token, 25 sessions per token, 10 000 in all. Tools: one per visible command, `<model>__<command>`, with an `inputSchema` and `outputSchema` generated from the registry (kinds per D47, `filter`/`order`/`limit`/`offset` per D49, governed fields per D48 left out of `create`), annotations that are hints and never enforcement, and one extra read-only tool `obop__meta`. A result is structured content plus text; an approval-required call is a normal result with `status: "approval_required"` and a `plan_id`; a refused input is `isError`; an unknown or hidden tool is the same `-32602`. Discovery: `/.well-known/mcp/server-card.json` (and `/mcp/server-card`, `/.well-known/ai-catalog.json`), `x-mcp` in the OpenAPI document and a `Link` header on `/api/meta`.

**Why.** An agent should connect to a hosted instance by URL and token, with no local binary and no database access; the is-agentic checks look for an MCP endpoint and manifest. **Rejected.** Waiting for `rmcp` and OAuth 2.1 (D18 and ai.md 4.1 plan both; neither is needed to ship a safe token-based endpoint, and the hand-written subset is small); the stateless `2026-07-28` revision now (its per-request model has no place for the session vault, so token stability would have to be keyed on the token as REST does; deferred, not refused); faking an authorization server in the metadata; SSE streaming (nothing to stream); `listChanged` notifications (module install changes the list; clients start a new session). **Consequences.** Clients that only authenticate through an OAuth browser flow (the connector dialogs of the Claude apps) cannot connect until the OAuth provider of [integrations](spec/integrations.md) 4.2 exists. The MCP Server Card is an extension still in incubation (SEP-2127; the earlier draft used `/.well-known/mcp/server-card.json`), so the document may change shape; the file says so. Sessions and rate limits are records and counters in the database since D59, so several processes may serve one database without sticky routing. `rmcp` still replaces the hand-written core when 2026-07-28 and OAuth arrive; the tool generation module stays. **Evidence.** D18, D29, D31, D40, D42, D45, D47 to D49, ai.md 4.1 and 4.3, MCP specifications 2025-11-25 (transports, authorization) and 2026-07-28 (versioning), RFC 9728, SEP-2127.
#### D52 Declarative translations
**Status** BINDING (owner-directed in chat, 2026-10-17). **Reversibility** two-way door. **Owner action** no.

**Decision.** A package may translate its own metadata. Translations are `[labels.<lang>...]` tables in the `obop.toml` document (module name and description; model name and description; field label and description; select option labels; action label and description), so one text is the unit that is validated, installed, upgraded, stored, served by a marketplace and removed. A package may keep them in sibling files (`<id>.labels.toml`, or the `labels/<lang>/<id>.toml` layout of the bundled catalogue) that tooling concatenates. English remains the manifest itself; a field has no English `label` (the client derives one from the name) and a language entry overrides it. Language codes match `^[a-z]{2,3}(-[A-Z]{2})?$`; every key must name something the package declares; values are plain text (non-empty, trimmed, one line, no control characters, no `{ } < >`, 80 characters for labels, 400 for descriptions); an unknown table is a schema error. The registry carries them as `Module.translations`; `GET /api/meta` adds `labels`, `descriptions` and per-field `option_labels`, each only where translated, in the shape the client's `labelFor` and `describeFor` already read. The five built-in modules and the admin module declare theirs in the same format. The 22 bundled packages and the built-in modules are translated into German, French, Polish, Finnish, Swedish and Spanish; those texts are machine-drafted until a native reviewer sets them to `reviewed` in `packages/labels/<lang>/status.json`. A test fails when any bundled text is missing or identical to English without being allow-listed.

**Why.** Module and field names came from manifests in English only, so an installed module showed English inside a German or Finnish interface, and a third-party author had no way to fix that. **Rejected.** A per-language catalogue in the client for every package (cannot cover packages written later); one manifest per language (versions drift); label keys separate from the schema (typos pass silently); translating permission group names (they are identifiers). **Consequences.** Packages grow by roughly the size of their English text per language (the 256 KiB limit still applies to the whole document); free-text error messages, record data and the marketplace listing of a package that is not installed stay as the server sends them; labels are not inflected, so sentences that insert a model name use frames that tolerate the nominative; the machine-drafted state of the six languages is tracked, not hidden. **Evidence.** D34, D45, D46, D47, docs/MODULES.md section 3.7, docs/brand/LOCALIZATION.md sections 1.4 and 8.

#### D53 Two-factor authentication
**Status** BINDING (owner-directed in chat, 2026-10-17). **Reversibility** two-way door. **Owner action** yes: every hosted or production instance needs `OBOP_SECRET_KEY` (docs/DEPLOY.md); the Sliplane provisioner sets a fresh one per instance.

**Decision.** A person can protect their account with a time-based one-time password (RFC 6238: HMAC-SHA-1, 6 digits, 30 s, the one profile every authenticator app supports). Enrolment has two steps: `POST /api/auth/mfa/begin` returns a 160-bit secret (base32 and an `otpauth://` URI) and activates nothing; `POST /api/auth/mfa/confirm` with a valid code activates it and returns 10 recovery codes, once. Secrets are sealed at rest with ChaCha20-Poly1305 under a key derived by HKDF-SHA-256 from the server secret `OBOP_SECRET_KEY` (32 bytes, 64 hex digits or base64), with the user name as associated data; without the key, enrolment is refused (`503 mfa_unavailable`) and the admin policy is not applied, because nobody could satisfy it; `OBOP_DEV_INSECURE_KEY=1` selects a public key for development and logs a warning. Recovery codes are 80 random bits, stored as SHA-256 hashes, single use. Verification accepts one step either side of the current one, compares in constant time, and never accepts a step that is not newer than the last accepted one, so a code works once. Sign-in becomes two steps when it is on: `POST /api/auth/login` answers `{mfa_required, mfa_token}` (5 minutes, stored hashed, not a bearer token, 5 wrong codes then it is void) and `POST /api/auth/login/mfa` with a code or a recovery code answers the session; wrong codes also count toward the per-user lockout of the password. Disabling and regenerating recovery codes need the password and a current code or recovery code. A `platform.admin` can reset another person's second factor (never their own through that route; it revokes their sessions); `obop admin reset-mfa USER --db URL` does the same with database access and is the break-glass path. Agent tokens are not people: they are unaffected at sign-in and get 404 on every two-factor route, as does `--dev-auth`. The setting `security.require_mfa_for_admins` (default true, `OBOP_REQUIRE_MFA_FOR_ADMINS=0` changes the default, an administrator's stored value wins) and the optional `security.require_mfa_for_all` limit a session of someone who is covered and has no second factor: it may only call the two-factor routes, and every other REST call, `/api/meta` and `/mcp` answer `403 mfa_enrolment_required` with a hint, until the confirmation lifts that same session. Every enrolment step, wrong code (at most one record per user per 10 s), recovery-code use, reset, lockout and limited session is appended to the log table `security_event` (user, kind, actor, time; never a code or a secret), exposed read-only as the `security_event` model of the `platform` module (`platform.admin` only; `get`, `list`, `search`, no writes on any surface). Control-plane accounts get the same optional TOTP under `/api/platform/...`, never enforced.

**Why.** Passwords alone are the weakest link of an instance that holds every other secret, and administrators can install modules and approve agents. TOTP works offline, on every phone, with no vendor; sealing the secret makes a database leak not enough. **Rejected.** SMS codes (SIM swap, a vendor and a cost); WebAuthn and passkeys now (the better factor; they came with D65, spec/security-privacy.md AU3 and AU4, but they need origin and relying-party handling that the single-origin instance model has not settled); email codes (the mailbox becomes the weakest factor); a hashed TOTP secret (TOTP needs the secret itself); a per-user random data key wrapped by the server key (more moving parts than one derived key, and rotation needs a migration either way); enforcing for everyone by default (an invited colleague without a phone would be locked out; the switch exists). **Consequences.** Honest limits: TOTP is phishable by a real-time proxy, which passkeys are not; the server holds the key, so whoever controls the process and the key reads every secret, and losing `OBOP_SECRET_KEY` makes enrolled users unable to use their codes (recovery codes cannot be checked either way, but an operator reset works); keys rotate with `obop secrets rotate` (D59); step-up for sensitive actions (AU5), step-up on session age, device trust and "remember this browser" are not built; the lockout counters and the replay memory are in the database, so several server processes share them (D59); the admin policy is an instance setting an administrator can turn off, and since D59 a change to any `security.*` setting is a row in the security log with who, old and new value; turning off one's own two-factor or changing the password ends the person's other sessions; the instance setting `security` object is readable by every signed-in user because the settings are. The recovery codes shown once are the one place a secret leaves the server in clear. **Evidence.** D18, D33, D40, D45, D46, spec/security-privacy.md (AU2, AU5, 4.5), RFC 4226, RFC 6238, RFC 5869, RFC 8439.
#### D54 Connectors and compliant data flows
**Status** BINDING (owner-directed in chat, 2026-10-17). **Reversibility** two-way door. **Owner action** no.

**Decision.** `connectors` is a default built-in app (module `connectors`, crates `obop-connectors` for the framework-neutral core and `connectors` for the registry metadata) through which an administrator connects external systems and a person connects their own accounts. Every model has a data class and a group like any other (D41), so REST, MCP, the CLI and the backoffice are generated: `connector_provider` (the catalogue shipped in the binary), `provider_policy` (what an administrator decided per provider), `connection`, `consent` (the recorded legal basis), `sync_run`, `data_flow_log`, the read model `processing_register`, the singleton `egress_policy` and the computed `privacy_preview`. Administration is `connectors.admin` (and `platform.admin`); people hold `connectors.user` and see only the connections, consents, runs and log rows they own, enforced by guards composed behind the generated ones (`Dispatcher::add_guard`). A connection's `state` is governed (D48): `connect`, `pause`, `resume`, `retry` and `revoke` are approval-required for agents, as is any policy that exposes more than the defaults, `sync` and `consent.withdraw`. Credentials and OAuth tokens are class `secret` (CONVENTIONS section 5): sealed with ChaCha20-Poly1305 under a key derived by HKDF from `OBOP_SECRET_KEY` (a key generated and kept in the database is the evaluation fallback, and the checklist says so), written only, returned by no surface, no log and no error.

*The gate.* Nothing leaves without `Egress::prepare`, which refuses unless flows are enabled for the instance, the connection is `connected`, an active consent record covers the data classes that would leave, and, when personal data would leave (pseudonymised data is still personal data), the agreement with the provider is recorded. It keeps only the fields on the connection's allowlist (an empty allowlist sends nothing) and treats each by its class: `secret` never; `confidential_hr`, `special_category` and `financial` denied unless the owner raises the class AND records an impact-assessment acknowledgement (who, when and text of at least 30 characters, stamped by the server) AND the provider's maximum classes include it; other personal data pseudonymised (HMAC-SHA256 under a per-connection key, so stable per connection and meaningless elsewhere); non-personal fields allowed. Other treatments are `mask` (a reversible token kept sealed in the instance and restorable only in inbound responses of that connection) and `redact`. Record ids never leave: each row carries a keyed pseudonym as `ref`. Rate and volume caps per connection, one `data_flow_log` row per flow with the field names, the treatments and a SHA-256 of the payload (never the payload), retention per connection with `obop connectors purge`. Inbound records go through `Ingress::accept`: the same gate, unknown or not-allowed fields reject the record, values pass the typed validation of D47 and are written by the connection's connector principal, an agent-kind principal limited to the groups its owner holds (narrowed to the groups of the target model), so an action that needs approval stays a proposal (D18, D48). Connectors never read or write their own records or the platform's. Erasing a party (`party.erase`) drops the pseudonym maps, tokens and external-id links that point at it and logs the erasure.

*Transport.* One outbound client: https only (plain http to a literal loopback host only when the operator sets `OBOP_CONNECTORS_ALLOW_LOOPBACK=1`), a host allow-list per provider or connection and an optional operator list, DNS resolved once per request with every address checked against private, link-local, loopback, carrier-grade NAT, documentation, multicast, reserved and cloud-metadata ranges (IPv4, IPv6, mapped and NAT64 forms) and the connection pinned to those addresses, redirects never followed, timeouts and size caps. Webhooks in are verified (Standard Webhooks, GitHub and Stripe schemes) in constant time against the raw body, the timestamp (five minutes) and a replay record that survives restarts, behind a per-connection request limit; webhooks out are signed the same way and retried with backoff in an in-process queue, then dead-lettered. OAuth2 is the authorization code flow with PKCE (S256), a single-use `state`, tokens sealed at rest and refreshed before they expire; the administrator supplies the client id and secret, obop ships none.

*Catalogue.* Four providers work (`webhook_out`, `webhook_in`, `rest_api_pull`, `csv_export`); six are generic adapters configured for a service and tested against a local counterpart, not the service (Slack incoming webhook, Stripe, GitHub webhook, Zapier, Make, n8n); two are definitions only (Google and Microsoft calendar and contacts, which need the administrator's own OAuth client). The catalogue and the UI say which is which, and a sub-processor fact that was not checked says "verify with the provider" instead of being asserted.

**Why.** Connecting systems is where an instance leaks: credentials in logs, personal data in webhooks, an agent widening what a connection sends, a server fetching an internal address. Putting one gate in front of every flow, built on the data classes and masking the platform already has (D40, D41), makes the safe path the only path and makes the compliance record a by-product of using it. **Rejected.** A connector framework with per-connector code paths for policy; masking only on the AI gateway; trusting the client or the UI to apply the policy; storing credentials in settings; following redirects; a payload log. **Consequences.** The controls support GDPR compliance (Articles 5, 6, 7, 25, 28, 30 and 32 are mapped in [CONNECTORS.md](CONNECTORS.md)); they are not legal advice or a certification, and the purposes, legal bases, agreements, assessments and information duties stay the controller's. The agreement flag is an attestation, not a check. Key rotation and a durable retry queue came with D59; erasure covers the party's own maps and tokens and not personal data copied into other models or already held by a recipient, rate counting scans the log, and the SQLite backend is outside the compliance claims (D44). **Evidence.** D10, D18, D27, D33, D40, D41, D47 to D52, spec/integrations.md 4.3 and 4.5, spec/ai.md 4.5, spec/security-privacy.md; the named tests of the threat model in CONNECTORS.md.

#### D55 Module metadata, core version and versioned dependencies
**Status** BINDING (owner-directed in chat, 2026-10-17). **Reversibility** two-way door. **Owner action** no.

**Decision.** *One core version.* The workspace package version (`0.2.0`) is the core version. `obop --version`, `GET /api/meta` (`core_version`), the OpenAPI `info.version`, the MCP server info and card, and the website footer report that one string (`obop_types::CORE_VERSION`). While the core is below 1.0 a minor bump may break (semver 0.y rule); from 1.0 only a major bump may. *Module metadata.* The `[module]` table gains `summary` (at most 140 characters), `license` (an SPDX expression, `LicenseRef-...`, `proprietary` or `UNLICENSED`; the checker is hand-written with a list of the identifiers a module realistically uses), `authors`, `homepage`, `repository`, `documentation`, `support` (https URLs only), `keywords` (at most 10), `categories` (from `finance`, `sales`, `supply-chain`, `people`, `services`, `marketing`, `productivity`, `platform`, `other`; at most 3), `icon`, `maturity` (`stable`, `beta`, `experimental`) and `requires_core` (a semver requirement). Every key is optional when a package is uploaded, so older manifests parse unchanged; a bundled or marketplace package must declare `license` and `requires_core`, and an upload without `requires_core` is assumed to run on every core (`*`) with a warning. *Dependencies.* `depends = ["hr"]` stays valid and means any version; the new table `[module.dependencies]` maps a module id to a requirement (`hr = ">=0.1, <1"`, `base = "^0.2"`, `projects = "*"`). The two forms may not name the same module. A dependency on a built-in module is checked against the core version, because built-ins version with the core. Optional dependencies are not offered: a `ref` to a model of a module that is not installed cannot be honoured by the registry, so a dependency that may be absent would be a lie. *Semver.* A 300-line matcher in `obop-pkg` (no dependency) supports `*`, `1.2.3` (as in Cargo, a caret), `^`, `~`, `>=`, `>`, `<=`, `<`, `=`, partial versions, wildcards, comma-separated ANDs and pre-release ordering, with the npm and Cargo rule that a pre-release satisfies a requirement only when that requirement names a pre-release of the same version. *Resolution.* Installing or upgrading computes a plan before it does anything: the core requirement, every dependency (built-ins against the core, installed packages, marketplace candidates), missing dependencies pulled in transitively in topological order, cycles named (`dependency cycle: a -> b -> a`), an installed dependency upgraded when the marketplace offers a version that fits, and a conflict (an installed module whose requirement the new version would break, for example `projects` 2.0.0 while `timesheets` needs `<2`) as a blocker. Downgrades and re-installs of the same version stay refused. The plan is the read-only admin command `module_plan.preview`; `marketplace_listing.install` and `module.install` run it and apply it as one operation under one approval (an agent proposes the whole plan once), and if a step fails the steps already applied are undone. `without_dependencies: true` is an error: required dependencies cannot be skipped. Uninstall is refused while an installed package needs the module, naming the dependents transitively. `module.list`, `module.get` and `marketplace_listing.list` return the metadata plus `requires_core`, `compatible`, `dependencies` (id, requirement, kind, installed and available version, satisfied), `dependents`, `installable` with `blockers`, `update_available`, `source`, `installed_at` and `installed_by`, for built-in modules too. The marketplace `index.json` listing carries the same metadata so a remote catalogue can show cards without fetching manifests; the first-generation index (five fields) still works. *Licences.* The bundled packages are first-party apps, so they carry `AGPL-3.0-or-later` (D1: core and first-party apps; Apache-2.0 is for SDKs, WIT worlds, the UI SDK and templates, which is why the tutorial module `docs/modules/assets.toml` is `Apache-2.0`). D1 is still PROPOSED (Q1); if the owner picks `-only` or another licence, the one line in each package and in `ModuleMeta::first_party` changes. *Command line.* `obop modules list` shows version, licence, core requirement and source; `modules tree [ID]` the dependency tree; `modules plan FILE|ID` the plan; `modules check [--catalog] FILE...` all the new rules without a database (ranges satisfiable by what exists, licence and core requirement for catalogue use, a core mismatch as a warning for an upload). *The page.* Customize, Modules shows the running core, Installed, Marketplace and Updates, a card per module with licence, maturity, core compatibility, source and a one-line dependency summary, a side panel with Overview, Dependencies (the core requirement and a nested tree with required range, installed version and status), Contents and Versions, a plan dialog before every install and upgrade, an uninstall dialog that names the dependents, an upload area that runs `module_plan.preview` as the file arrives, and an instance-wide dependency overview with a table alternative.

**Why.** The owner found the Modules page unclear about dependencies. The facts that decide whether an install is safe (which core, which other modules and at which versions, under which licence) were not declared, so neither the page nor an agent could say them before the install. Declaring them in the manifest and resolving them in the one installer keeps REST, MCP, the CLI and the page in agreement, and makes the install a plan a person confirms once.

**Rejected.** The `semver` crate (acceptable, but a hand-written matcher of this size removes a dependency from the install gate and lets the messages be ours); optional dependencies (see above); an SPDX list of all 600 identifiers (almost all irrelevant, and `LicenseRef-` covers custom terms); resolving on the client; skipping dependencies with a flag; a SAT-style solver (one version of each module can be installed, the marketplace offers one version of each, so a depth-first walk with a conflict check is complete); versioning built-in modules independently of the core.

**Consequences.** The marketplace offers one version per package, so the resolver never has to choose between versions; a catalogue with several would need a real solver. Dependency requirements are checked at install, upgrade and uninstall, not continuously, and a core upgrade does not re-check installed packages: they still load, and the page marks them incompatible. Summaries are not translated (D52 labels cover names and descriptions only). The build of the website reads the core version from `Cargo.toml`. A package version may carry a pre-release (`1.0.0-rc.1`); the core version may not.

**Evidence.** D1, D32, D41, D45, D47, D52, docs/MODULES.md sections 3, 7 and 9, the tests `dependency_tests`, `modules_tests` and `tests/modules.spec.ts`.

#### D59 Operations and durability
**Status** BINDING (owner-directed in chat, 2026-10-17). **Reversibility** two-way door. **Owner action** no.

**Decision.** *Several processes, one database (B1).* Nothing that decides an answer lives only in one process's memory. `obop-storage` gains, on all three backends and under one contract test: a cross-process lock (`Backend::lock`: a PostgreSQL session advisory lock, a SQLite file lock `<db>.lock-<key>`, a process-local lock for memory), atomic expiring counters (`INSERT ... ON CONFLICT` on PostgreSQL, the equivalent elsewhere; fixed window, the database's clock), expiring text values with put-if-absent, compare-and-set swaps, an atomic multi-write (the one shared `Op` list of D61, whose `Put` also creates or replaces a record, run by `apply_checked` on memory, SQLite and PostgreSQL), a streaming snapshot export and a transactional import. Built on those: login lockout and second-factor attempt counters; the MCP, public-site, checkout and webhook rate limits; order idempotency keys; the dispatcher's governed-write lock (it was one `Mutex`); pending approval plans (sealed, 7 days, approvable from any process, once); REST mask vaults (sealed under the server key and keyed by a hash of the bearer token, 24 hours after the last change; an agent's call holds a lock on its vault, because mask tokens are sequence numbers, a person's call only when it added tokens, which the default policy never does) and MCP sessions (sealed records with a sliding expiry, bound to the opening token, locked for the length of a request). The forum and the status page keep their in-memory copy as a cache: a write takes a database lock, reloads the copy if a shared version number moved, writes through and bumps the version; a read reloads when the number moved (checked at most every 250 ms); one process per interval runs the status checks. Tokens were already records. Installed packages are records too, but each process registers their commands in its own dispatcher: every install, upgrade or removal bumps a shared version number and each process reconciles its registrations when the number has moved (checked at most once a second from the dispatcher's entry points). *Connector queue (B2).* The retry queue and dead letters are rows: a worker claims due jobs under a 120 second lease, so a restart or another process continues deliveries; delivery is at-least-once and the job id, sent as the webhook id, is stable; the payload is sealed; a job that used its retries moves to `connector_dead` with the reason and can be sent again. Pulls and the daily purge are scheduled through the database. *Key ring (B3).* `OBOP_SECRET_KEY` is the current key and `OBOP_SECRET_KEY_PREVIOUS` (comma separated) the earlier ones; a sealed value is `e2.<key id>.<nonce>.<ciphertext>` with the purpose as associated data, so opening finds its key and a missing key is reported by id; new values use the current key; the two first formats (`v1.`, `obs1:`) open by trying every key. `obop secrets rotate` re-seals every inventoried place (two-factor seeds, connection credentials and OAuth tokens, the OAuth client secrets, vault values, stored pseudonym keys, queue payloads, plans, vaults and MCP sessions) in two passes: a read-only pass that opens everything and refuses to start if any value opens with no key (naming the place), then batches of compare-and-set swaps, each batch a transaction, so it runs while serving, a value changed meanwhile is left for the next run, and stopping anywhere leaves a readable database. Pseudonym keys are stored sealed on first use so a rotation never changes a pseudonym a receiver already has. Reports and errors carry places and key ids, never a key, a plaintext or a sealed value. *Backups (B4).* `obop backup` streams one consistent snapshot into gzip JSON Lines plus a checksum manifest (format 1, schema version, core version, per-model counts) without stopping the server; `obop backup verify` re-reads it; `obop restore` verifies first, refuses a non-empty target without `--force`, a format it does not know and a schema newer than the binary, and writes in one transaction; secrets stay sealed as stored; sessions, plans and counters are not backed up. `deploy/restore-drill.sh` restores into a scratch PostgreSQL database, checks counts, accounts and secrets, starts a server on the copy and drops the database; CI runs it. *Schema versions (B5).* `obop_meta/schema` holds the version; `obop-migrate` keeps ordered, idempotent steps (a step returns its writes, applied together with its version record in one transaction, or does batched resumable work); runners hold a database lock and re-read the version inside it; `obop migrate status|plan|run [--dry-run]`; a server refuses a newer schema, runs pending steps only with `--auto-migrate` (default on for SQLite, off for PostgreSQL, set by hosted instances) and otherwise prints the command; an empty database is stamped. Step 1 records the version, step 2 re-seals first-format secrets. *Image and rolling upgrade (B6).* `.github/workflows/image.yml` builds the root Dockerfile (cargo-chef dependency layer, BuildKit cache, provenance and SBOM attestations) for linux/amd64 and publishes `ghcr.io/spacecorps/obop:<commit>` and `:main` or `:deploy`; the control plane prefers `OBOP_IMAGE` over `OBOP_REPO`; `obop platform upgrade-instances --image TAG [--only SLUG] [--dry-run]` moves running instances one at a time through the provisioner trait (Sliplane: `services update --image`, `deploy`, wait live, check the image, `GET /api/openapi.json` must answer 200), stopping at the first failure. *Security gaps (B7).* Changes to `security.*` instance settings are security events (who, old and new value, nothing that looks like a secret); turning off one's own two-factor or changing one's password ends the person's other sessions; `GET /api/auth/sessions`, `POST /api/auth/sessions/revoke-all`, `POST /api/auth/password` (current password, and a code when two-factor is on; the lockout counts wrong passwords), administrators list accounts, disable and enable them (sessions end, tokens stop; never oneself, never the last enabled administrator) and set a temporary password that forces a change (a limited session, like the two-factor enrolment limit); all audited, all in the Security tab with translated strings.

**Why.** The first deployments ran one process per database, with sessions, limits, the forum and the queue in that process's memory: a restart signed agents out and dropped deliveries, a second process would have double-counted every limit and handed out ids twice, nothing could be rotated or restored, a new version had no way to know the shape of an old database, and every customer instance compiled the workspace on a shared server. Those are the first things an operator hits. Putting the shared state in the database the data already lives in needs no new service, and keeping one small contract (lock, counter, expiring value, compare-and-set, transaction) means a fourth backend or a faster store can take it over without touching the callers.

**Rejected.** A separate cache or coordination service (Redis, etcd): another thing to run and back up, for what PostgreSQL does. Sticky routing as the answer to sessions. Making mask tokens derivable (deterministic encryption of the value inside the token): stateless, but it lengthens tokens, leaks value length, and changes the token format agents already use. Row-level pessimistic updates for re-sealing (a lost-update window against the running server) instead of compare-and-set. A native binary backup format or `pg_dump` as the product's backup (not portable between SQLite and PostgreSQL or versions). Down-migrations (a failed or unwanted upgrade is a restore). Emulated arm64 image builds. A one-process `Mutex` per area with a note.

**Consequences.** Every request that checks a limit or a lockout, and every guarded write, makes one more round trip to the database (a lock is a few statements); the forum reloads its whole copy when another process writes, which is cheap for a forum and would not be for a large dataset. Counters are fixed windows (a burst at a window edge may pass twice the limit). A lock wait gives up after 60 seconds with a "busy" answer (503). SQLite supports several processes on one machine, not on a network file system. A rotation that is stopped half way leaves a ring that still needs the previous key; the status command says so. Migrations are forward-only, so the way back from an upgrade is the backup taken before it. The image workflow and the Sliplane upgrade path were tested against stand-ins (Docker build, runner fakes), not against GitHub and Sliplane themselves; whether Sliplane converts a repository-based service to an image is unverified. Hosted instance backups are not scheduled by the product (they need object storage); the operator runs `obop backup` or `pg_dump` from a job. Agent tokens survive a password change and a person's sign-out-everywhere; they are revoked on their own. **Evidence.** D6, D7, D30, D33, D36, D37, D40, D44, D45, D51, D53, D54, docs/DEPLOY.md, the tests `shared_tests` (storage), `multi_process` (community and instance), `queue::tests`, `reseal::tests`, `obop-migrate::tests`, `backup::tests`, `account::tests` and `tests/security.spec.ts`.

#### D60 Blobs and images
**Status** BINDING (owner-directed, 2026-10-17). **Reversibility** two-way door. **Owner action** no.

**Decision.** Two field kinds, `image` and `file` (manifest `kind = "image"`, optional `max_bytes`, default 5 MiB for an image and 25 MiB for a file, at most 64 MiB), hold the id of a stored blob: 64 lowercase hex characters, the SHA-256 of the stored bytes. *Storage.* `obop_storage::blob::Blobs` is the trait the rest of obop uses (put, info, streamed read, attach, detach, detach by record, derived objects for thumbnails, gc, export, import); `Catalog` implements it over the record store (the blob metadata, owners and pending uploads are ordinary records of model `obop_blob`, so a database backup carries them and every change is a compare-and-set batch) and a `BlobBytes` byte store, with three implementations: a directory (`OBOP_BLOB_DIR`, else `<sqlite file>.blobs`; files at `<dir>/<aa>/<id>`, built only from a validated id), the database itself (a chunked table of 512 KiB `bytea` rows on PostgreSQL, streamed back chunk by chunk) and memory for tests. **An S3-compatible store is one more `BlobBytes` implementation** (put, open, delete, keys); nothing else changes. Same content is stored once and counts as several owners. *Lifecycle.* An upload is a pending claim of the uploading principal; saving a record that names the blob attaches the owner (model, record, field); replacing or clearing the value, deleting the record and erasing it detach; a blob nobody holds and nobody has pending is deleted; `obop serve` checks hourly and removes uploads nobody claimed for a day and bytes without metadata. *Validation (`obop-media`, the `image` crate with only the png, jpeg, gif and webp features).* The type comes from the first bytes, never from the name or `Content-Type`; a declared type that disagrees is refused; markup (SVG, HTML, XML) is refused outright because SVG can carry script and sanitising it safely is a project of its own; dimensions are read from the header and limited (8000 by 8000, 36 million pixels, a 320 MiB decoder budget) before pixels are allocated, which defeats decompression bombs; the accepted image is **decoded and encoded again** (JPEG stays JPEG, PNG stays PNG, GIF becomes a PNG of its first frame, WebP becomes JPEG or, with transparency, PNG; the EXIF orientation is applied to the pixels first), which removes EXIF and GPS, XMP, IPTC, ICC profiles, comments and any appended script or archive; animation is not kept. Files are checked against a short list by magic number (PDF, PNG, JPEG, GIF, WebP, ZIP-based office formats, UTF-8 text without control characters), kept byte for byte and always served as downloads. A virus scanner plugs in as `Scanner` before `put`; obop ships none and sends nothing anywhere. *Access.* `POST /api/blobs?field=model.field` (raw body, bearer token, caller needs write access to the target field, 40 uploads per ten minutes per principal) returns the id; the id can be saved into a field only by the principal who uploaded it, or when that field already holds it, or when the principal can already read a record that holds it, and a made-up or foreign id answers like a missing one; `GET /api/blobs/{id}` (optional `?w=` of 320, 640, 960 or 1280 for cached thumbnails, made once and never larger than the original) needs a bearer token and read access to a record that holds the blob (or being its uploader); **agents never get bytes** (404), only ids and metadata through the generated commands, and there is no `blob.read` command. Responses carry the content type, `nosniff`, a sandboxing CSP, a strong hash ETag and a long private cache (the URL is content-addressed). The public site serves `/media/{id}.{png|jpg}` only for blobs held by a **published** record through a field its package declared public, whose required parents (a gallery picture's listing) are published too; everything else, a private holder, a pending upload, an unpublished record, answers a plain 404, with a year-long public cache. The D41 gate refuses a public field that is personal data (a photo of a person: `party.photo`, `hr_employee.photo` are never public) and a visitor submission that names an `image` or `file` field. Erasure: `party.erase` clears the photo and deletes the blob. Backups: `Blobs::export` yields every blob with its bytes and owners one at a time and `import` restores it after checking the hash; the backup command calls these.

**Why.** A shop without product pictures, a website without a cover image and an HR record without a photo read as unfinished; images are also where an upload becomes an attack (script in SVG, polyglots, EXIF locations, bombs), so the safe path has to be the only path. **Rejected.** ImageMagick or any external process; sanitising SVG (a long tail of vectors for no need); trusting `Content-Type` or the file name; storing originals untouched (leaks location and carries payloads); a blob id that is a random value (content addressing gives dedupe and tamper evidence for free); public URLs that list by directory; multipart parsing (a parser to attack; a raw body is enough); S3 now (the byte trait makes it a later, local change). **Consequences.** Uploads are re-encoded, so JPEG quality is not the camera's and ICC profiles and animation are lost; images whose bytes are identical share one blob, so one published holder makes the blob public even if a private record holds it too; a CDN or browser that already cached a public picture keeps it after the record is unpublished until it is purged; HTTP downloads buffer the object (storage reads stream; the cap is the field's `max_bytes`); the upload limiter and the access checks are per process; when row-level permissions arrive, `BlobService::may_read` must apply them; there is no antivirus unless an operator installs a `Scanner`; the `image` crate (MIT or Apache-2.0) and its png, zune-jpeg, gif and image-webp dependencies are the compile-time and size cost, and the dev profile compiles dependencies with optimisation so tests stay fast. **Evidence.** D29, D40, D41, D47, D50, `crates/kernel/obop-media`, `crates/kernel/obop-storage/src/blob.rs`, `crates/kernel/obop-commands/src/blobs.rs`, docs/STOREFRONT.md (threat model), the tests named there.

#### D61 Shop stock, discount codes and taxes
**Status** BINDING (owner-directed, 2026-10-17). **Reversibility** two-way door. **Owner action** no.

**Decision.** *Atomic writes.* `Backend::apply_checked` (and `apply`, which reports failures as text) run a list of steps (insert, bounded counter add with optional upsert, compare-and-set patch, delete) all or nothing and isolated from every other writer: one lock in memory, `BEGIN IMMEDIATE` in SQLite, row locks (`SELECT ... FOR UPDATE`) in PostgreSQL. A package declares which integer fields the server may change this way (`[model.public] server_adjust = ["stock_quantity"]`) and which models the server may read whole (`server_read`, for discount codes and tax rates, which are not public); `PublicApi::submit_order` writes the order, its lines, the stock and the code counters in one batch, so two buyers cannot both take the last unit, a code cannot pass its maximum use, and a refused checkout leaves nothing behind. *Stock.* A listing is tracked when its policy is `block_when_out` (units never go below zero) or `allow_backorder` (units are counted and may go below zero); `always_available` is not tracked. A shortfall names what is left ("Only 2 of Stoneware Teapot left."); an order that is cancelled, expires, fails to be paid or is refunded before delivery puts its units back once (`stock_returned` is set in the same batch). *Discount codes* (`ecommerce_discount_code`): percent in basis points or fixed, minimum order, valid from and to, a maximum number of uses, a limit per customer, optionally one category. A code is looked up case-insensitively and validated on the server at the cart and again at checkout; **every reason it fails (unknown, off, expired, not started, used up, below the minimum, wrong category, malformed) gives the same answer**, and failed attempts are limited to ten per ten minutes per address, after which codes are not looked at. Uses are counted in the order's batch (`used_count` against `max_uses`, and one upsert counter per code and customer keyed by a hash of the email address, so the address is not kept). A percent discount is rounded once for the whole order and split over the eligible lines by the largest remainder method; a fixed discount never exceeds the eligible lines; delivery is never discounted. `POST /shop/discount/check` answers JSON for the same rules; the cart works without it. *Taxes* (`ecommerce_tax_rate`: name, basis points, country, category, included, active): per line, on the amount after the line's share of the discount, with exact `i128` integer arithmetic and **rounding half away from zero per line**; a rate that is `included` (the usual EU case) is the tax part of the price (`gross * r / (10000 + r)`) and changes nothing the buyer pays, one that is not is added on top (`net * r / 10000`); one rate applies to a line, the most specific by category over country over the general one (the earliest entered wins a tie); delivery is taxed with the general rate of the buyer's country; the order keeps a tax line per rate and the tax of every order line. The buyer picks the delivery country (shown only when a rate is scoped by country). *Totals.* Prices, names, currency, stock, discount, tax, delivery (including free over a threshold, compared with the lines at listing prices) and the total come only from the published listing, the stored codes, rates and shipping methods; the browser sends listing ids, quantities, delivery method, country, how to pay and the code text, and nothing else is read.

**Why.** An order that does not reduce stock, a code that is an oracle for guessing, and a total the browser could influence are the three ways a shop loses money; each needs an atomic check, a generic answer or server-only arithmetic. **Rejected.** Reserving stock by a separate table with timers (the counter plus a reservation time on the order is the same without a second moving part); per-line tax rounded after summing (different from what the document shows line by line); a VAT engine now; returning the reason a code failed (an oracle); client-side totals (the old script is replaced by a fragment the server renders). **Consequences.** Out of scope, stated: VAT identification numbers, reverse charge, the EU One-Stop-Shop and destination thresholds, tax by product type beyond a category, legal invoice rules of any country; the owner enters the rates and is responsible for them. Free delivery is judged on the lines before the discount. The rate limits and idempotency keys are per process. A code's counters are on records the owner can edit by hand, which is intended. `Backend::apply_checked` reads whole documents (the typed-column schema manager will make it cheaper). **Evidence.** D47, D48, D50, D44, `crates/kernel/obop-storage/src/atomic.rs`, `crates/kernel/obop-site/src/pricing.rs`, docs/STOREFRONT.md.

#### D62 Payments
**Status** BINDING (owner-directed, 2026-10-17). **Reversibility** two-way door. **Owner action** yes: the owner connects Stripe (key, webhook secret, agreement, legal basis) in the Connectors app and lists `stripe` in the site settings.

**Decision.** The crate `obop-payments` implements `obop_commands::PaymentPort` (what the public shop calls) and `PaymentHooks` (what the webhook door calls) over a `PaymentProvider` trait: create a payment page for an amount, verify a notification, ask for the status, refund, expire. Three providers. `manual`: no page; the order shows the instructions the owner wrote (`site.payment_instructions`), staff mark the order paid with the existing action (a wrapper on the command settles the payment record), and a refund is recorded for staff to make by hand. `stripe`: Stripe Checkout Sessions over the REST API through the connectors' hardened egress client (https to `api.stripe.com` only, every resolved address checked, no redirects, caps); the secret key and the webhook signing secret are the sealed credentials of the instance's own `stripe` connection (no second place for secrets); one line item, "Order <number>", with the **server-computed total in minor units and the currency of the order** and the payment id as idempotency key; no customer name, address or email is sent to Stripe. `fake`: a local demo whose "hosted page" is `/shop/fake-pay/{session}`; it exists only when the operator sets `OBOP_DEMO_PAYMENTS=1` **and** the owner lists `fake` in `site.payment_methods`. *Flow.* Checkout creates the order (`pending`, stock taken, `reserved_until` set: 45 minutes for an online payment, `site.payment_hold_days` for a transfer) and then the `ecommerce_payment` record (provider, the provider's reference, amount and currency copied from the stored order, state `open`) and sends the buyer to the provider's page; if the page cannot be made the order is cancelled and everything is given back before the buyer sees the error. The buyer returns to `/shop/pay/{order token}` (and `?s=cancel`): **the page never believes the redirect**; it asks the provider for the status and shows the server's state. `POST /hooks/pay/stripe` (public, 256 KiB body cap, rate limited before any signature work) verifies the `Stripe-Signature` on the raw body with the five-minute tolerance and constant-time comparison before reading the JSON, remembers the delivery in the database (a replay inside the window is acknowledged and changes nothing), then applies the event to the payment: an amount or currency that differs from the stored one is ignored; every change is a compare-and-set, so two deliveries racing leave one state and one `mark_paid`. Events handled: `checkout.session.completed` (paid), `async_payment_succeeded`, `async_payment_failed`, `expired`. A failed, expired or cancelled payment cancels the order and gives back its units and its code uses, once. Payment arriving for an order that was already cancelled is refunded, not kept. A sweep (run from checkout, at most every 20 seconds) cancels unpaid orders whose reservation ran out, after asking the provider once more. *Refunds* are the order's `refund` and `refund_delivered` actions (manager, approval for agents): a wrapper on the command (`Dispatcher::around`, which runs only when the command really runs, after guards and approval) asks the provider first with a fixed idempotency key, records the refund id and amount on the payment, and only then lets the state change; an order whose refund the provider refuses stays paid; an undelivered refund also puts the units back. Amounts are always whole minor units, the currency is the order's. *Settings* (`site.*`): `payment_methods`, `payment_instructions`, `default_country`, `payment_hold_days`. *PCI.* The shop never sees, stores or logs card data (the buyer pays on Stripe's page): SAQ A scope, the merchant's own questionnaire and duties remain theirs. *Receipts.* There is no mail sender, so no emailed receipt: the confirmation page is the receipt, and `/shop/order/{token}/receipt` is a printable page.

**Why.** An order that cannot be paid is a catalogue, and payments are where a shop is attacked: forged success pages, forged and replayed webhooks, tampered amounts, double refunds, stock held forever. The provider boundary keeps those rules in one place and lets a second provider be added without touching checkout. **Rejected.** Believing the success URL; marking orders paid from the browser's return; a second secret store for the Stripe key; sending itemised lines, names or emails to Stripe; a payment method chosen by the browser without checking it is offered; refunding after the state change (a failed refund would leave a refunded order and kept money); a timer thread (a request-driven sweep and the provider's own expiry are enough); PayPal, Mollie and others now (the trait is the seam). **Consequences.** Honest limits: not tested against Stripe itself, only against a local stand-in that speaks the same shapes (the Connectors catalogue says so); no S3 or other byte store; no email receipts; no VAT or OSS engine (D61); partial refunds, multiple payments per order, payment links, saved cards, SCA fallbacks beyond what Checkout does, disputes and payouts are not built; a refund holds the dispatcher's transaction lock while it calls the provider (up to the 20 second timeout); the Stripe connection needs the compliance record of D54 (a consent with a legal basis) before it can connect, which is intended; the replay record and the rate limits are per database and per process; asynchronous methods rely on their own events. **Evidence.** D18, D33, D44, D48, D50, D54, D60, D61, `crates/kernel/obop-payments`, docs/STOREFRONT.md (threat model), docs/CONNECTORS.md section 8.

#### D63 Mandatory version ranges, module updates, and updating the instance from inside it
**Status** BINDING (owner-directed in chat, 2026-10-18). **Reversibility** two-way door. **Owner action** yes: set `OBOP_BACKUP_DIR` on hosted instances (a volume) and publish releases with `obop platform release publish`.

**Decision.** *Ranges are mandatory.* Every package declares `requires_core` (the core versions it runs on) and, for each dependency, the range of that dependency it supports, in `[module.dependencies]`. A missing or empty range, a range nothing satisfies (`>=2, <1`) and the retired `depends = [...]` shorthand are parse errors that say what to write. A range with no upper bound (`*`, `>=0.2`) is a warning for an upload and an error for the bundled catalogue and the marketplace (`obop modules check --catalog`, `Listing::stub`); a marketplace listing without `requires_core` is left out. Built-in modules declare `^<core series>` for their dependencies. The bundled packages already carried bounded ranges. The ranges are enforced both ways by the one resolver: installing or updating checks them against what is installed, and updating, rolling back or uninstalling checks every installed dependent's declared range; the plan lists each dependent with its range and whether it would break. *Update and rollback.* `module.upgrade ID`, `module.upgrade_all` and `module.rollback ID` (REST, MCP, CLI `obop modules update|update-all|rollback`) are `platform.admin` commands that agents only propose (D18), audited in `security_event` (`module_update`, `module_rollback`, the data steps named), and run under the D59 cross-process lock `modules.apply`. A whole plan is one `apply_checked` batch: the package records and every data step are written together or not at all; registration in the process is undone when anything fails. The package record keeps the previous manifest, so one level of rollback exists. `[module] changelog` carries release notes. *Data.* Additive changes (new model, optional field, option, action) need nothing. Breaking changes (removed or retyped field, removed option or model, new or newly required field while records exist) are refused unless the new version declares `[[migration]]` steps: `rename_field`, `set_default`, `drop_field` (needs `confirm = true`). Each record is changed by a compare-and-set on the value read, so a concurrent edit fails the batch and it is retried; renames are reversed on rollback, a drop makes the update irreversible (the way back is the backup). *The instance.* An instance never holds hosting credentials. A control plane mints a per-instance update token at creation (`obu_` plus 256 random bits; the control plane keeps only its SHA-256 hash and a one-year expiry; the instance receives it as a secret environment variable and seals it under its key, an entry in the `secrets rotate` inventory). The token can read the state of its update, ask to be moved to a *published version* (never an image) and ask to go back to the previous image; it opens no account API, is rate limited per instance, and every use is written to the control plane's audit log. The control plane runs the existing rolling-upgrade path (`Provisioner::upgrade`: redeploy, health check) and, when the new version does not come up, puts the previous image back before reporting `rolled_back`. `GET /api/releases` publishes the releases (`obop platform release publish`); each carries a SHA-256 digest, an integrity check that drops damaged entries, not a signature, which is why the feed never decides what runs. Customize, Updates (and `obop update check|status|start|rollback`, `instance_update.check|status|start|rollback`) shows the running and available core, the release notes, every installed module judged against the new core by its declared `requires_core` and its ranges on built-in modules (incompatible ones block, with a hint when the module has an update that fits both), takes a backup into `OBOP_BACKUP_DIR` first (no backup, no request, unless the administrator confirms their own), asks the control plane, polls the result and offers the rollback. A self-hosted instance gets the exact commands (`docker pull`, `obop backup`, `obop migrate`). The feed (`OBOP_UPDATE_FEED`, default the obop.dev feed, `off` to disable) is only read when an administrator checks.

**Why.** The owner wanted administrators to update modules and the instance from inside it, and every module to say which versions of its dependencies it supports. D55 had the ranges but allowed `*` and an absent core range; an update path that cannot say what it will break is not safe to offer.

**Rejected.** Letting the instance hold Sliplane credentials (one compromised instance would reach every customer); a token that names an image or a URL (it would be a remote-execution handle); signature-only trust in the feed (needs key distribution first, tracked as I-1 in docs/ISSUES.md section H); free-form migration scripts (code, X2/X3); automatic conversion of retyped fields; multi-level rollback; automatic background update checks (an unprompted call home).

**Consequences.** Packages written before this decision need `requires_core` and ranges; the bundled ones have them. Marketplace indexes without `requires_core` list nothing. Migration steps read all records of a model into one batch, fine for the sizes of this product, not for millions. Rollback of the instance restores the old image, not the data: migrations are forward-only (D59), the backup is the way back. The control-plane half was tested against the fake provisioner and a loopback control plane, not against live Sliplane or obop.dev; the release feed on obop.dev has no releases until the owner publishes them. **Evidence.** D18, D45, D55, D59, docs/MODULES.md 7 and 7.1, docs/DEPLOY.md "Updating from inside", the tests `update_tests` (pkg, platform, obop), `migrate::tests`, and `tests/module-updates.spec.ts`, `tests/updates.spec.ts`.

#### D64 OAuth sign-in for MCP clients
**Status** BINDING (owner-directed in chat, 2026-10-19). **Reversibility** two-way door. **Owner action** yes: set `OBOP_PUBLIC_URL` (and `OBOP_TRUST_PROXY` behind a proxy you control) on every hosted instance and forward `/oauth/*` and `/.well-known/*` (docs/DEPLOY.md).

**Decision.** *One authorization server per instance.* An instance is the authorization server of its own `/mcp`, so Claude Desktop, claude.ai and Claude Code connect with a browser sign-in and no pasted token (the MCP authorization specification, OAuth 2.1). `/.well-known/oauth-authorization-server` (RFC 8414) and `/.well-known/oauth-protected-resource` with its `/mcp` variant (RFC 9728, which now names the server) are public; the `401` of `/mcp` carries `resource_metadata` pointing at the `/mcp` variant, whose `resource` is `<public URL>/mcp`. Base address: `OBOP_PUBLIC_URL`, else `Host` and `X-Forwarded-Proto` as before; the client address of the rate limits is the peer, or the last `X-Forwarded-For` entry with `--trust-proxy`. With `--dev-auth` there is no server and the metadata says so. *Registration* (`POST /oauth/register`, RFC 7591): public clients only (`token_endpoint_auth_method: none`), `authorization_code` and `refresh_token`; 1 to 5 redirect URIs, `https` or `http` on `localhost`, `127.0.0.1` or `[::1]`, no wildcard, fragment, user information, backslash or non-ASCII host; 20 registrations per address and hour, 300 in all, 2000 clients; a client without an approved connection is forgotten after 24 hours and an idle one after 180 days; names are cleaned and shown only as plain text beside the address the browser will go to, with the statement that obop cannot verify who runs the application. *Authorization* (`GET /oauth/authorize`): the client and the redirect URI are checked first and an error there is a page, never a redirect; the redirect URI must equal a registered one, except that a loopback `http` URI may use any port (RFC 8252); then `response_type=code`, `code_challenge` with `S256` (plain and missing are refused) and `resource` (must be `<public URL>/mcp`; absent means the same) are checked and refused errors go to the redirect URI with `state` and `iss` (RFC 9207). A flow is a short-lived record (10 minutes) found by a random id and bound to the browser by a second random value in an `HttpOnly`, `SameSite=Lax`, `Path=/oauth` cookie (only its hash is stored); every step must present the flow id, the cookie and the flow's CSRF token, come from this origin (`Origin`, else `Sec-Fetch-Site: same-origin`) and be a form post; eight wrong passwords end the flow. Sign in reuses the instance's login: lockout, the two-factor step (the code goes in the form, the `mfa_token` in a hidden field), and the refusal of accounts that must still enrol two-factor or change a temporary password; the session that proves the sign-in is revoked at once. The consent page (seven languages, plain HTML without script, content security policy `default-src 'none'` with the stylesheet by hash and `form-action` limited to this origin and the origin of the redirect URI, `frame-ancestors 'none'`, `no-store`, `Referrer-Policy: same-origin`, which keeps `Origin` on the form posts and sends no referrer to the application) shows who asks and where the browser returns, lists only groups the person holds (administrative ones start unticked, a `scope` that names groups pre-ticks them), asks for 1, 7, 30 or 90 days, and states that approvals still wait for a person and that actions are recorded as the agent's. A group the person does not hold is refused (agents only narrow, D18). *Tokens* (`POST /oauth/token`): the code lives 60 seconds, is spent by whoever deletes it first, and is bound to client, redirect URI, resource and PKCE challenge (a failed attempt burns it; presenting a spent code revokes the grant it produced); a refresh token is single use, and presenting a used one, or losing the race for one, revokes the whole grant and its live access token; a refresh may narrow the scope and never widen it, and is limited to the groups the person still holds; the grant ends on its date. Access tokens are `auth_token` records of kind agent (SHA-256 hashed, D18) with a one hour life, an `audience` and a link to the grant; the REST surface refuses a token that has an audience and `/mcp` refuses one whose audience is not its own address, so a token cannot be used anywhere it was not issued for. `POST /oauth/revoke` (RFC 7009) revokes a grant by either token, for the client that holds it. CORS is open (`*`, no credentials) on the registration, token and revocation endpoints and the metadata. *Storage (D59)*: clients, grants and refresh tokens are records (`oauth_client`, `oauth_grant`, `oauth_refresh`), codes and flows are expiring values, rotation is one `apply_checked` batch with a compare-and-set, every limit is a database counter; nothing secret is stored in the clear or needs the key ring, because codes, refresh tokens and cookie secrets are kept as SHA-256 hashes. *Management*: `GET /api/auth/oauth/grants` and `POST /api/auth/oauth/grants/{id}/revoke` for the signed-in person (agents get 404), the Connected apps table in Customize, Security, and the events `oauth_authorize`, `oauth_denied`, `oauth_revoked`, `oauth_refresh_reuse` and `oauth_code_reuse` in `security_event`, with the application's cleaned name and never a token or a code.

**Why.** D51 shipped `/mcp` with bearer tokens and said so plainly, which left the connector dialogs of the Claude apps, which only offer an OAuth sign-in, unable to reach a hosted instance. The person who connects an agent is the one who must choose what it may do, so the sign-in page is also the place of that choice, with the same narrowing rule as the agent tokens they could always create by hand.

**Rejected.** A client secret (the clients are apps and browsers that cannot keep one); the implicit and password grants; accepting `plain` PKCE or none; a long-lived access token (the refresh token is the long-lived credential and it rotates); issuing the person's own session token to the app; reusing the backoffice session in the browser (it lives in script memory, not a cookie, and a cookie session would bring its own CSRF surface); wildcard or custom-scheme redirects; Client ID Metadata Documents (the instance would fetch a client-supplied URL; deferred, not refused); a consent screen that grants everything by default; sealing the new records (nothing in them is secret once hashed); a third-party identity provider.

**Consequences.** Honest limits. **Not tested against the real Claude Desktop, claude.ai or Claude Code**, only against our own client in Rust and Playwright tests: how those apps register, which redirect URIs they send, whether they send `resource` and `scope`, and how they handle a refusal are taken from the specifications. Registration is open to anyone who can reach the instance, so the only defences are the limits, the cleaning of names, the visible redirect host and the person's consent; an attacker may still register an application named like a well-known one and rely on a careless click. There is one scope: the groups chosen at consent (no per-command or per-company scopes; no step-up for sensitive groups). The consent page signs in with a password afresh every time (no single sign-on from an open back office; since D65 a passkey can be used there, as the second step or alone). The language of the pages is the `lang` parameter or `Accept-Language`; the six translations are machine-drafted. A grant ends only on its date, by revocation, by reuse, by disabling the account or by losing every group; a password change does not end it (agent tokens never did, D59). An administrator cannot yet list or revoke other people's connected apps (the person can; the security log shows the events). Access tokens are bound to `<public URL>/mcp`, so changing `OBOP_PUBLIC_URL` ends every connected app. Rate limits are fixed windows (a burst at a window edge may pass twice the limit). **Evidence.** D18, D33, D40, D51, D53, D59, the MCP authorization specification (2025-11-25), RFC 6749, 7009, 7591, 7636, 8252, 8414, 8707, 9207, 9700 and 9728, docs/DEPLOY.md, the tests in `obop-oauth`, `crates/obop/src/oauth_tests.rs` and `web/packages/e2e/tests/oauth.spec.ts`.

#### D65 Passkeys (WebAuthn)
**Status** BINDING (owner-directed in chat, 2026-10-19). **Reversibility** two-way door (the credentials are public keys in one table; removing the table leaves every account with its password and authenticator app). **Owner action** only for hosted instances: set `OBOP_PUBLIC_URL` to the address people type (a host name over https), as D64 already asks (docs/DEPLOY.md).

**Decision.** *What a passkey is here.* A person may register passkeys (WebAuthn level 2, discoverable credentials preferred, user verification preferred). A passkey is (a) a second factor: it completes the second sign-in step exactly where an authenticator app code does, counts as a second factor for the `platform.admin` policy and for `require_mfa_for_all` (D53), may be the only second factor, and may sit beside an authenticator app; and (b) optionally a passwordless sign-in: a person who turned on "Let me sign in with a passkey alone" (default off, re-authenticated) signs in without typing a name or a password with a discoverable passkey that verified them (PIN, fingerprint or face) both when it was made and at sign-in; that sign-in is a whole session and satisfies the admin policy (possession plus verification). *Ceremonies.* `obop-auth` implements them with no WebAuthn library: the audited `webauthn-rs` pulls in system OpenSSL, a second cryptography stack and a large tree, so a small reader of what the specification needs was written instead, with signatures checked by `ring` (already in the tree through TLS; `rsa` stays out, RUSTSEC-2023-0071). Accepted: attestation format `none` only (the options ask for it, so a browser returns it), ES256 (-7), EdDSA (-8) and RS256 (-257, 2048 to 4096 bits); a strict CBOR reader (definite lengths, depth 12, no allocation beyond the input) and strict base64url. Registration checks `clientDataJSON` (type `webauthn.create`, the challenge, the exact origin, no cross-origin or `topOrigin`), the authenticator data (RP id hash, user present, the credential data announced by the flags and nothing after it, a credential id of 16 to 1023 bytes equal to `rawId`) and the key (type, curve and size of the algorithm). Authentication checks type `webauthn.get`, origin, RP id hash, user present (and user verified where required), the signature over authenticator data and the SHA-256 of the client data, the user handle when the authenticator sends one (a usernameless sign-in demands it), and the counter. *Origin and relying party.* The HTTP layer derives both and the browser never states them: `OBOP_PUBLIC_URL` when set; else, behind `--trust-proxy`, `X-Forwarded-Host` and `X-Forwarded-Proto`; else `Host` and `X-Forwarded-Proto` (as D64). The RP id is the host without port; an IP address is refused (browsers refuse it too) and so is plain http except on `localhost` and `*.localhost`, with a stable `passkeys_unavailable` answer that says what to set. Every credential stores its RP id and is refused at any other. *Challenges* are 32 random bytes, stored under the hash of the challenge in the key-value store of D59 with the purpose (`register`, `second`, `login`, `proof`), the person or the pending sign-in it was made for, the RP id and the origin, valid two minutes, and used up by the first answer, right or wrong (the delete that succeeds decides when two answers race); so a ceremony may start on one server process and finish on another. *Counter and clones.* A stored counter that is not below the presented one when either is non-zero is a clone suspect: the answer is refused, the counter is not moved and `passkey_clone` is logged; authenticators that always send zero (many synced passkeys) pass, and the backup-eligible and backup-state flags are stored and shown ("Synced"). *Storage.* `auth_passkey`, keyed by the SHA-256 of the credential id: person, name, credential id, algorithm, public key, counter, whether it verified the person, backup flags, discoverable (from `credProps`), transports, AAGUID, RP id, created and last used. Public keys are not secrets, so nothing is sealed and `OBOP_SECRET_KEY` is not needed for passkeys; the user handle is 32 random bytes kept on the account, never the name. At most 10 per person. *Sign-in.* The first step answers `{mfa_required, mfa_token, methods}` with `methods` listing `totp` and/or `passkey`; `POST /api/auth/login/passkey/options` and `/api/auth/login/passkey` take the `mfa_token` for the second step, or nothing for the passwordless one. *Management* (`/api/auth/passkeys`): list, `register/options` and `register/finish`, `{id}/rename`, `{id}/remove`, `passwordless`, and `proof/options` and `proof`. Every change needs the password again and, when a second factor is on, a code, a recovery code or a passkey **proof** (an assertion given just before, valid 60 seconds, used once, stored in the key-value store; it also stands in for a code when changing the password, turning off the authenticator app and making new recovery codes). The first second factor of a person who has none also returns the ten recovery codes, once, as TOTP does; they sign in through the existing recovery route. Removing a passkey signs out the person's other sessions. *Policy and recovery.* A passkey may not be removed when it is the person's last second factor and the policy requires one (`400`, the sentence says what to add first); turning off the authenticator app was already allowed to leave an administrator with a limited session that must enrol again, and stays so. `obop admin reset-mfa USER --db URL` and the administrator's reset (D53) also delete every passkey and the passwordless setting, end the sessions and log it; recovery codes stay while a passkey remains. *Audit.* `security_event` gains `passkey_register`, `passkey_rename`, `passkey_remove`, `passkey_used`, `passkey_login`, `passkey_failed`, `passkey_clone` and `passkey_passwordless`; no credential, key or challenge is ever written. *Limits.* Ceremony options and answers are limited to 60 and 40 per client address and ten minutes; wrong passkey answers in the second step, a proof or a re-authentication count toward the per-person lockout and the per-sign-in cap of five like wrong codes, and are logged at most every ten seconds per person. *Pages.* The back office gets a Passkeys panel in Customize, Security (add, rename, remove, "Let me sign in with a passkey alone"), "Sign in with a passkey" on the sign-in page, "Use a passkey" in the second step (the first thing a passkey-only person sees), and the enrolment gate of a limited session offers it. The OAuth pages of D64 get the same two buttons through one inline script; their policy keeps `default-src 'none'` and adds exactly `script-src 'sha256-<hash of that script>'` and `connect-src 'self'` on the two sign-in pages only (a hash, not a nonce: the script is one fixed text, so the hash is both stricter and cacheable; the consent page has no script), and two same-origin, CSRF-checked, flow-bound endpoints, `/oauth/authorize/passkey/options` and `/oauth/authorize/passkey`.

**Why.** An instance that asks administrators for a second factor should not make a phishable code the only choice; a passkey is bound to the address, cannot be typed into a fake page and is what browsers and phones now offer by default. **Rejected.** `webauthn-rs` (system OpenSSL; see above); resident-key-only enrolment (security keys without storage must work as a second factor); attestation formats beyond `none` (they exist to tell makes of authenticator apart, which obop has no use for and which needs a metadata service and a trust store); requiring user verification to register (a key that cannot verify still works as a second factor, it just cannot replace the password); making passwordless the default or implied by having a passkey; sealing public keys; deriving the RP id from the browser's claim or from any header without `--trust-proxy` or a configured URL; a nonce for the page script (the script is fixed). **Consequences.** Honest limits. **Tested only with a software authenticator (Rust) and Chrome's virtual authenticator (Playwright over the DevTools Protocol), never with a real phone, platform authenticator, security key, Safari, Firefox, a synced passkey manager or cross-device (hybrid) sign-in.** Real authenticators differ in counters, flags, transports, `credProps`, attestation behaviour and what they do when user verification is unavailable; none of that is verified here. RS256 and EdDSA were verified against the software authenticator only; real EdDSA authenticators are rare. Passkeys exist on instances, not on the control plane (`/api/platform`), whose sign-up app keeps authenticator-app two-factor only. One RP id per credential, so changing `OBOP_PUBLIC_URL` to another host makes existing passkeys unusable until people add new ones (passwords and authenticator apps are unaffected); a related-origins list and RP id parents are not supported. No username hint at sign-in, so a non-discoverable key (some hardware keys) works only as a second step. No conditional-UI autofill (`mediation: conditional`). No attestation, so obop cannot tell which makes of authenticator a person uses and cannot restrict them. Agent tokens cannot hold or use passkeys (D53, D18). Wrong answers lock the second step like wrong codes, so someone who knows a person's name can still make them wait a minute (as with passwords). Rate limits are fixed windows. Passkeys do not replace `OBOP_SECRET_KEY` for the authenticator app and for connectors. The language of the new texts besides English is machine-drafted. **Evidence.** D18, D33, D53, D59, D64, WebAuthn Level 2 (W3C Recommendation) sections 6.1, 7.1, 7.2 and 13.4, RFC 8949, RFC 9053 (COSE), RFC 8152 key parameters, RUSTSEC-2023-0071, the tests in `obop-auth` (`passkey_tests`, `webauthn`), `crates/obop/src/passkey_tests.rs` and `web/packages/e2e/tests/passkeys.spec.ts`.

#### D66 TLS to PostgreSQL
**Status** PROPOSED, owner-directed (batch 1, small unblockers, 2026-10-24). **Reversibility** two-way door (a URL parameter; removing it restores the plain connection). **Owner action** hosted and self-hosted operators: put `sslmode=require` (at least) into the database URL of any PostgreSQL that is not on the same private network as the instance, and turn TLS on at the server; `verify-full` with the server's CA when the CA is known.

**Decision.** Every PostgreSQL connection the product opens (the storage backend, its advisory-lock connections and export snapshot, the blob store, the control plane's cell admin connections, the status probe of the cell) goes through one place, `obop_storage::tls::PgConnector`, which reads `sslmode=disable|prefer|require|verify-ca|verify-full` and an optional `sslrootcert=PATH` (or `system`) from the query of a `postgres://` URL. The meanings are libpq's: `disable` and `prefer` as expected (`prefer` uses TLS when the server offers it and does not check the certificate); `require` encrypts and does not check the certificate, **unless** a root certificate is given, in which case it is checked like `verify-ca`; `verify-ca` checks the chain and the validity period and not the host name; `verify-full` also demands that the certificate names the host dialled. Roots come from the PEM file, or from the bundled Mozilla roots (`webpki-roots`, already in the tree) when `sslrootcert=system` or none is given with a `verify-*` mode. **A URL without `sslmode` keeps today's behaviour: a plain connection** (this differs from libpq's `prefer` on purpose, so no existing deployment changes; docs/DEPLOY.md recommends `require` or better for every non-internal host). The TLS parameters are removed from the string before the driver sees it. `allow`, client certificates (`sslcert`, `sslkey`), `sslcrl` and duplicates are refused at start-up with a message that names the problem and never the URL. *Implementation.* rustls 0.23 with the `ring` provider (no system OpenSSL, no `aws-lc`; both were already in the tree through the HTTP client) and `tokio-rustls`, joined to the synchronous `postgres` driver by a small `MakeTlsConnect` in `obop-storage` (about 100 lines; the `tokio-postgres-rustls` crate would add the X.509 and `tls_codec` trees for channel binding, which is not needed). There is no channel binding, so `SCRAM-SHA-256-PLUS` is never selected; SCRAM-SHA-256 runs inside the TLS tunnel. The `ring` provider is TLS 1.2 and 1.3. The unverified modes still check the handshake signature; they only skip the trust decision.

**Why.** A password and every record cross the network on each PostgreSQL connection; on a shared network or across hosts (the usual hosted layout) a plain connection can be read and altered by anyone on the path. The product had no way to say otherwise. **Rejected.** `native-tls`/`openssl` (system library, D14 images without it, a second cryptography stack); `tokio-postgres-rustls` (larger tree for a feature we do not use); defaulting to `prefer` or `require` (breaks every existing plain deployment and every local test database without a server certificate); libpq's keyword DSN form (only `postgres://` URLs are accepted by the connector, so no `ssl*` key can be silently ignored); client certificate authentication (not built; E-row in docs/ISSUES.md).

**Threat model.** *Assets:* the database password, all records, sealed secrets in transit. *In scope:* a passive eavesdropper or an active man in the middle between the server process and PostgreSQL. `disable` and the default protect against neither. `prefer` and `require` stop passive eavesdroppers; an active attacker can still impersonate the server (and `prefer` can be downgraded by answering the SSL request with `N`). `verify-ca` and `verify-full` with a root the operator trusts stop both; `verify-ca` still accepts any certificate the CA issued, for any name, so only `verify-full` binds the connection to the host. A wrong or missing root file, an untrusted chain or a name mismatch is a hard error at connect time, not a fallback. *Out of scope:* a compromised PostgreSQL server or CA; certificate revocation (no CRL or OCSP); client certificates; encryption at rest. *Mistakes the design guards against:* an unreadable or empty `sslrootcert` fails when the URL is read, not at the first query; a typo in `sslmode` is an error rather than a silent downgrade; the password is not in any error text (tested).

**Acceptance tests** (`crates/kernel/obop-storage/src/tls_tests.rs`): `a_url_without_sslmode_means_no_tls_and_is_passed_on_unchanged`; `every_documented_sslmode_is_read_and_removed_from_the_connection_string`; `sslrootcert_is_a_path_or_system_and_needs_a_mode_that_uses_it`; `unknown_duplicate_and_unsupported_ssl_options_are_refused_with_a_clear_message`; `errors_never_contain_the_password`; `a_missing_or_empty_root_certificate_file_is_refused_when_the_url_is_read`; `require_and_verify_modes_refuse_a_server_that_has_no_tls`; `only_postgres_urls_are_accepted_so_no_ssl_key_can_be_ignored`. Against a throwaway `postgres:17` container with TLS on and a self-signed certificate made in the test (skipped with a message when Docker is not available): `a_plain_url_still_connects_and_is_not_encrypted`; `require_and_prefer_encrypt_the_connection_without_checking_the_certificate`; `verify_full_accepts_a_trusted_certificate_that_names_the_host`; `verify_full_refuses_a_host_name_the_certificate_does_not_carry`; `verify_ca_accepts_a_name_mismatch_but_verify_full_does_not`; `verify_modes_refuse_a_certificate_signed_by_nobody_we_trust`; `require_with_a_root_certificate_is_checked_like_verify_ca`; `the_storage_backend_uses_tls_for_its_main_and_lock_connections`.

**Consequences.** **Not tried against any managed PostgreSQL service** (RDS, Cloud SQL, Neon, Supabase, the Sliplane cell), against PgBouncer or another pooler in TLS mode, against a server that offers only TLS 1.2, with a certificate chain longer than one step, with an ECDSA or Ed25519 server key, or with a public CA through the bundled roots; only against the stock `postgres:17` image with an RSA self-signed certificate. A root file may hold several certificates; an intermediate-only chain was not tried. `sslmode=prefer` falls back to a plain connection only when the server answers `N`; a failed handshake is an error. The pool of lock connections and the export connection each pay a handshake. The status probe and the cell admin connection use the same URL rules, so an operator must put the parameters in `OBOP_CELL_ADMIN_URL` too; the URLs the control plane hands to *new* instances (`postgres://role:pw@host/db`) carry no `sslmode` yet (so new hosted instances connect plainly until the provisioner passes it on). **Evidence.** D44, D59, docs/DEPLOY.md "Database connections and TLS", the PostgreSQL documentation for `sslmode`, the tests above.

#### D67 Health and metrics endpoints
**Status** PROPOSED, owner-directed (batch 1, small unblockers, 2026-10-24). **Reversibility** two-way door (three read-only routes; nothing stored). **Owner action** operators who want metrics: set `OBOP_METRICS_TOKEN` and point a scraper at `/metrics`; point load balancer and orchestrator probes at `/healthz` (liveness) and `/readyz` (readiness).

**Decision.** Every instance (`obop serve`, with or without the public site and the backoffice) serves three routes, registered with the REST routes so no static file, backoffice shell or public page can shadow them (and `healthz`, `readyz` and `metrics` are refused as an `--admin-prefix`). `GET /healthz`: 200 `{"status":"ok"}` while the process serves requests; no database, no state, no authentication. `GET /readyz`: 200 `{"status":"ready"}` when the database answers a ping and its schema is one this build can serve (`obop_migrate::Migrator::status`: not newer than the build, no pending steps; a database with no records is ready); otherwise 503 `{"status":"unavailable","reason":R}` where R is one of four fixed strings (`database unreachable`, `database did not answer in time`, `database is newer than this server`, `database needs migration`); the answer is shared for two seconds and a database that does not answer within three seconds is not ready. `GET /metrics`: Prometheus text (`text/plain; version=0.0.4`): `obop_build_info{core_version}`, `obop_process_uptime_seconds`, `obop_http_requests_total{class}` (1xx to 5xx and other; every response, including fallbacks and the public site, counted by a layer over the whole router), `obop_http_request_duration_seconds` (histogram, 11 buckets from 5 ms to 10 s, measured until the response headers are ready), `obop_db_up`, `obop_db_ping_seconds`, `obop_active_sessions` (valid people's sign-in sessions, from the new `Authenticator::active_session_count`) and `obop_job_queue_depth{queue="connectors",state=waiting|leased|dead}` (the connector delivery queue). Sessions and queue depth read many rows, so scrapes share one reading for 15 seconds. There are no per-path, per-user or per-model labels. *Access to `/metrics`.* Closed unless opened: (1) `OBOP_METRICS_TOKEN` set (at least 16 characters, refused at start-up otherwise): bearer token required, compared in constant time through a hash; wrong or missing token is 401; (2) no token and the server bound to a loopback address (`--addr 127.0.0.1:...`): served only to a direct loopback peer that sent none of `X-Forwarded-*`, `Forwarded`, `X-Real-IP` or `Via`, so a reverse proxy on the same host does not publish it; (3) otherwise the route answers 404 as if absent. `Cache-Control: no-store` on all three. The upgrade health check of the control plane (`GET /api/openapi.json`) is **not** changed: it must still work against the image being rolled back to, which may predate `/readyz`.

**Why.** Orchestrators, load balancers and uptime monitors need a cheap liveness answer and a readiness answer that is false while the database is down or the schema is wrong; operators need a few numbers without a log scrape. The docs said "no metrics endpoint yet". **Rejected.** Putting metrics behind a person's session or an agent token (a scraper should not hold a person's credentials, and a leaked scrape token must not open the API); serving `/metrics` openly on public binds; labels by path, user or model (unbounded series, and names are personal data); detailed readiness (versions, host names, driver errors are reconnaissance); counting body-streaming time; an OpenTelemetry exporter (a larger dependency tree, pull is enough for now); changing the Sliplane upgrade check to `/readyz` now.

**Threat model.** *Assets:* the existence and shape of the instance, load figures, the session count, the database address. *Unauthenticated callers* can reach `/healthz` and `/readyz` only: they learn that a server is up and whether it can serve; the reasons are four constants (no versions, hosts, paths, driver text); `/readyz` costs the database one ping and one read per two seconds however hard it is hit, and the three-second limit stops a stuck database from holding workers. `/metrics` reveals request rates and error counts, uptime, the core version, the session count and queue depth, no names, tokens, record counts or paths. *Mistakes guarded against:* a proxy on the loopback address forwarding the internet to a loopback-only page (proxy headers and non-loopback peers are refused; if a proxy strips the headers the operator must set a token, which the docs say); a short or guessable token (length floor); timing leaks of the token (hash then constant-time compare); a person's session or agent token accepted as the scrape token (test); shadowing by the static or public routes (tests with both). *Out of scope:* denial of service by sheer request volume (the generic limits apply as before); metric values being estimates (the session count is a 15 second old figure; durations exclude body streaming).

**Acceptance tests** (`crates/obop/src/health_tests.rs`, `crates/kernel/obop-http/src/ops.rs`): `healthz_answers_200_with_a_fixed_body_and_needs_nothing`; `readyz_is_200_when_the_database_answers_and_the_schema_fits`; `readyz_is_503_with_a_short_reason_when_the_database_is_newer_than_the_server`; `readyz_is_503_when_the_database_still_needs_migration_steps`; `readyz_shares_one_database_check_for_a_couple_of_seconds`; `readiness_names_only_fixed_short_reasons` (including an unreachable database and a driver error that names a host); `health_endpoints_are_open_and_reveal_nothing_but_status_and_a_fixed_reason`; `metrics_does_not_exist_unless_the_operator_opened_it`; `metrics_with_a_token_refuses_missing_and_wrong_tokens`; `metrics_serves_prometheus_text_with_the_minimal_set`; `metrics_count_responses_by_status_class_and_fill_the_histogram_consistently`; `metrics_report_active_sessions_without_naming_anyone`; `metrics_on_loopback_is_for_direct_loopback_callers_only`; `health_and_metrics_are_not_shadowed_by_the_backoffice_or_the_public_site`; `a_metrics_token_is_checked_for_length_and_wins_over_the_bind`; `admin_prefixes_are_one_safe_segment`.

**Consequences.** **Not tried against any real scraper, load balancer, orchestrator probe or Prometheus server** (the text format is hand-written to the exposition format and checked by the tests above, not by `promtool`); not run behind a real reverse proxy. `/readyz` on a PostgreSQL that has actually gone away is covered by the verdict function and not by killing a server. `/readyz` reports one process: with several processes on one database each answers for itself and the counters are per process (sum them in the scraper). The control plane (`obop platform serve`) has no such routes yet. Counters restart at zero with the process. No `Server-Timing`, no per-route histograms, no in-flight gauge. **Evidence.** D44, D59, D63, docs/DEPLOY.md "Health and metrics", the tests above.

#### D68 Allowed origins (CORS) for browser clients
**Status** PROPOSED, owner-directed (batch 1, small unblockers, 2026-10-24). **Reversibility** two-way door (one setting; unset restores same-origin only). **Owner action** operators who host a browser app on another origin: list that origin in `OBOP_ALLOWED_ORIGINS`. Anyone who set the variable before: it is now validated (see below) and the instance refuses to start with an invalid value.

**Decision.** `OBOP_ALLOWED_ORIGINS` is a comma-separated list of exact origins: `https://host[:port]`, or `http://localhost[:port]`, `http://127.0.0.1[:port]`, `http://[::1][:port]` and `http://NAME.localhost` for development. It is validated when `obop serve` starts: a wildcard anywhere (`*`, `https://*.example.com`), `null`, a missing or other scheme, plain `http` for a non-loopback host, a path (other than one trailing slash, which is removed), query, fragment, user name, space, or a port outside 1 to 65535 stops the server with `OBOP_ALLOWED_ORIGINS has an invalid entry "..." : <reason>` before it listens. Entries are lowercased and de-duplicated. *Default off:* with the variable unset or empty, `/api` behaves exactly as before (no CORS header, no `Vary`, an `OPTIONS` preflight is not granted), so only same-origin pages and non-browser clients work. *When set:* a layer over the whole router acts on paths under `/api/` only. A request whose `Origin` equals an entry exactly (no case folding, no port or scheme inference, no suffix match) gets `Access-Control-Allow-Origin: <that origin>` and `Access-Control-Expose-Headers: Link, Retry-After, WWW-Authenticate`; every `/api/` response (allowed or not) carries `Vary: Origin`; any other origin, and any request without `Origin`, gets no CORS header at all and is processed as before (the API is bearer-token only, so reading the answer is what CORS decides). A preflight (`OPTIONS` with `Origin` and `Access-Control-Request-Method`) from a listed origin asking for `GET` or `POST` with request headers within `Authorization, Content-Type, Accept, Accept-Language` is answered 204 with `Allow-Origin`, `Allow-Methods: GET, POST, OPTIONS`, `Allow-Headers`, `Max-Age: 600` and `Vary: Origin, Access-Control-Request-Method, Access-Control-Request-Headers`; a preflight from an unlisted origin, or asking for another method or header, is 403 with no CORS headers. `Access-Control-Allow-Credentials` is never sent: there are no cookies on `/api` (bearer tokens only), and a page cannot make the browser attach the visitor's cookies to the API. `/mcp` keeps its own origin handling (D51: the same list, the instance's public URL and same-origin on loopback; the 403 for a foreign origin is DNS-rebinding protection) and now reads the same validated list. The OAuth endpoints are not touched: the token, registration and revocation endpoints keep the `*` they send for public clients (D64, no credentials, no cookies), and the sign-in and consent pages (`/oauth/authorize*`) answer as before whatever the list says (tested by comparing every header with and without the list).

**Why.** A browser application on its own origin (a custom front end, an internal dashboard, a development server) cannot call the API at present, and the one existing allow-list covered `/mcp` only and accepted any string. A strict, validated list makes the common case safe and the unsafe cases unsayable. **Rejected.** A wildcard (tokens held by a page would be usable from anywhere the page is framed or scripted, and `*` cannot be combined with credentials anyway); reflecting the request's `Origin` (the classic hole); regular expressions or suffix patterns (`evil-app.example.com`, `app.example.com.evil.test`); allowing plain `http` for remote hosts (tokens in the clear); a cookie session with `Allow-Credentials` (would need CSRF defences obop does not have); CORS on the OAuth consent pages (they are navigated to, not fetched); CORS on webhook doors (server to server).

**Threat model.** *Assets:* the bearer tokens in a listed page, the API answers. *Attackers:* a malicious web page the visitor opens (cannot read answers: its origin is not listed and no cookies exist to ride on); a page on a look-alike origin (exact match only); a cache that serves one origin's answer to another (`Vary: Origin` on every `/api/` response when the list is on); an operator typo that opens everything (wildcards and non-loopback http are unsayable and stop the server). *Residual:* a listed origin is trusted with whatever token its page holds, so an XSS in that application is an XSS against the API; the list is global (every `/api/` route, not per route or per token); a request from an unlisted origin is still executed if it carries a valid token (as for any non-browser client; CORS never was an authorization mechanism). *Out of scope:* private-network-access preflights (`Access-Control-Request-Private-Network`) are not answered; `credentials: "include"` requests fail by design.

**Acceptance tests** (`crates/obop/src/cors_tests.rs`, `crates/obop/tests/startup_config.rs`, `crates/kernel/obop-http/src/cors.rs`): `by_default_no_origin_gets_any_cors_header_and_preflights_are_not_answered`; `a_listed_origin_gets_its_own_origin_back_and_never_credentials`; `an_origin_that_is_not_listed_gets_no_cors_headers_but_a_caching_hint`; `the_origin_is_never_reflected_from_the_request`; `a_preflight_from_a_listed_origin_is_answered_with_methods_headers_and_max_age`; `a_preflight_from_an_unlisted_origin_is_refused_without_cors_headers`; `a_preflight_asking_for_an_unsupported_method_or_header_is_refused`; `an_options_request_without_the_preflight_header_is_not_a_preflight`; `the_oauth_and_consent_endpoints_answer_exactly_as_they_did_without_a_list`; `the_mcp_endpoint_keeps_using_the_same_list`; `a_hand_built_list_cannot_allow_more_than_the_rules_do`; `the_public_site_router_applies_cors_to_api_paths_only`; `a_wildcard_in_allowed_origins_stops_the_server_with_a_clear_message`; `other_invalid_allowed_origins_are_refused_at_startup_too`; `a_running_server_answers_cors_health_and_metrics_as_configured` (a real process and socket); `valid_entries_are_normalised`; `wildcards_and_other_invalid_values_are_refused_with_a_message_that_names_the_entry`; `matching_is_exact_on_what_the_browser_sent`.

**Consequences.** **Not tried in a real browser** (Chrome, Firefox, Safari), with a real front-end framework, behind a CDN or a reverse proxy that adds or strips CORS headers (a proxy that also sets CORS headers will produce duplicates; set them in one place), or with credentialed fetches. The behaviour of browsers is taken from the Fetch standard and checked with raw requests. The expose list is short on purpose; add what a client needs. Other platform routes (`/api/platform`, the control plane) have no CORS. **Evidence.** D51, D64, D18, the Fetch standard (CORS protocol), docs/DEPLOY.md "Browser clients and allowed origins", the tests above.
#### D69 People administration: create, edit groups, offboard, import
**Status** PROPOSED (owner-directed in chat, 2026-10-24, as part of "batch 1, small unblockers"; not yet ratified as binding). **Reversibility** two-way door (the new fields on `auth_user` are optional; every change is undone by the opposite change, except that credentials revoked by an offboarding stay revoked by design). **Owner action** no.

**Decision.** *What exists.* Until now an account's groups were fixed when it was created and nothing could change them. Three account tools now exist beside enable, disable and the temporary password (D53, B7), one rule set in `obop-auth` (`admin.rs`, the `AccountsApi` port of `obop-commands`), reached from four places. REST: `GET /api/auth/groups`, `POST /api/auth/users` (create), `POST /api/auth/users/{name}/groups`, `POST /api/auth/users/{name}/offboard`, for a signed-in administrator's session only (an agent token gets the same `404` as for any hidden route). MCP and agents: a `user_account` model in the Customize module with `list`, `get`, `add`, `set_groups`, `offboard`, `disable` and `enable`; every command that changes an account needs approval, so an agent can only propose, and a person approves with the usual `POST /api/approve/{plan}`. CLI: `obop admin users|groups|offboard|disable|enable|import` (the operator's database access is the authority, as for `admin create`; the log names the actor `operator`). Backoffice: Customize > Security > People (new person, groups dialog, offboard dialog, status badges), in the seven languages through the existing catalogue process. *Groups.* The groups a person can hold are the ones the registered models, fields, commands and `see_all` lists name (`Dispatcher::known_groups`), so a module installed later adds its own; a name no module declares is refused, except that a group the person already holds may stay when its module is gone. The stored groups are read on every request (`user_principal`), so an edit applies to every open session and to agent tokens (which only narrow their owner's groups) at the next request, with nothing revoked. A change that makes someone an administrator on an instance that requires two-factor for administrators limits their open sessions to enrolment at once, and the reverse lifts that limit. *Locks.* Nobody can take `platform.admin` from themselves, nobody can take it from the last enabled administrator, and nobody can disable or offboard themselves or the last enabled administrator; the checks run under the same cross-process lock as the two-factor changes (`auth.mfa`). *Creating.* A name of letters, digits and `. _ - @`, groups checked as above, and either a chosen password (at least 12 characters) or a random one returned once; either way the person must choose their own at the first sign-in unless the administrator says otherwise. The generated password is never written to the log. An agent's `add` must carry a password a person chose, because the answer to an agent is shaped for the agent and a generated password could not be shown to anyone. *Offboarding.* One action: the account is disabled and marked offboarded, and every `auth_token` of the owner (sessions and agent tokens, among them the access tokens of connected apps) is revoked, every `oauth_grant` of the owner is ended with its refresh tokens deleted, and the passkey proof and half-finished sign-ins of the person are dropped. Enabling the account later clears the flag and lets the person sign in; nothing revoked comes back (a plain disable keeps the old behaviour: agent tokens work again after enabling). The optional note is cut to 200 characters without control characters. Anonymising the person's display data later is not built. *Audit.* New `security_event` kinds: `user_create`, `user_groups` (who; groups added, removed and now held), `user_offboard` (who; counts and the note), and `user_enable` says what stays revoked. An approved proposal is logged as `alice/agent` (the owner `alice` cannot be locked out by her own agent: the self-checks compare the account, not the label). *Import.* `obop admin import FILE.csv [--dry-run] [--out FILE]`: a UTF-8 CSV with `name` and optionally `groups`, parsed by the strict reader in `obop_commands::csv` (BOM dropped, `,` or `;` chosen from the header, quotes and line breaks in quotes, at most 1,000 rows and 1 MiB, cells at most 64 KiB, a stray quote an error that names the line); every row is checked before anything is written and the accounts are created in one transaction or not at all; each gets a generated temporary password, printed once or written to a file created with mode 0600 that is never overwritten.

**Threat model.** *Stolen or over-reaching agent:* it cannot call the REST routes at all, and every `user_account` change is a proposal; the approval re-reads the proposing administrator's stored account, so a plan made before that administrator was disabled or demoted does nothing (test `agents_can_only_propose_account_changes_and_an_administrator_decides`). *Privilege escalation by a non-administrator, or by an administrator whose session is limited to enrolment:* `404`, tested for REST, for the port and for the tool list. *Lock-out and last administrator:* refused, including through an agent's label (`groups_edit_an_approved_agent_proposal_runs_as_the_agent_but_cannot_touch_its_owner`). *A stale credential surviving an offboarding:* every token kind, the OAuth grant and its refresh tokens, pending second steps and the passkey proof are covered; enabling revives none (`offboard_ends_everything_and_enabling_does_not_bring_it_back`, and the same through the real OAuth flow in `offboarding_ends_connected_apps_for_good_and_enabling_does_not_revive_them`). *Secret leakage:* a temporary password appears once in the response and nowhere else (not in the log, not in an agent's answer; `create_user_with_a_password_or_a_generated_temporary_one`); the import's password file is created exclusively with mode 0600 (`cli_import_checks_first_writes_a_private_password_file_and_never_overwrites`). *Racing edits:* read-modify-write under the cross-process lock. *CSV:* the reader never evaluates a cell, so spreadsheet formula injection concerns exports (none here) and not this import. *Residual:* no step-up re-authentication for these actions (they sit with the other administrator actions; issue E7f); an administrator can give any registered group to anyone, including `platform.admin`, which is what an administrator is; names are matched by exact text, with no per-group delegation.

**Acceptance tests (named).** `admin_tests::groups_edit_*` (live sessions see the change, audit of before and after, validation against registered groups, last administrator and self lock-out, who may, the two-factor policy on live sessions, the agent label), `create_user_with_a_password_or_a_generated_temporary_one`, `offboard_*` (everything ends, refusals, the operator), `import_checks_every_row_first_and_creates_all_or_nothing` in `obop-auth`; `accounts_tests::rest_create_edit_groups_and_offboard_a_user`, `agents_can_only_propose_*`, `agents_tool_lists_show_*`, `cli_import_checks_first_*` and the OAuth offboarding test in `obop`; `csv::tests` for the reader; Playwright `people.spec.ts` for the panel.

**Why.** An instance whose people cannot be moved between roles, or removed cleanly, cannot be run by anyone but its operator, and an agent that proposes "give ada the sales role" is the point of the platform. **Rejected.** Editing groups by editing tokens (tokens already follow the stored groups); a separate "role" object (groups are the contract of CONVENTIONS); deleting an account to offboard it (the log and the owner of records need the name); revoking agent tokens on every plain disable (that is the existing, documented behaviour and some people want a temporary pause); letting an agent set a generated password; erasing display data now (needs the erasure design of D54 first). **Consequences.** Honest limits. **Not tried** with a PostgreSQL deployment under concurrent edits from several server processes (the lock is the same one as for two-factor, which is tested on PostgreSQL), with the real Claude apps as the connected application, or in browsers other than Chrome. The labels of the new `user_account` model are translated like the rest of the Customize module; the six translations of the interface strings and of those labels are machine-drafted (issue D7). Existing agent tokens keep their scopes when a person loses a group; they simply stop being allowed that group. An offboarded person's records keep their user id in `own` fields (they are not rewritten).

#### D70 Bulk create and CSV import
**Status** PROPOSED (owner-directed in chat, 2026-10-24, as part of "batch 1, small unblockers"; not yet ratified as binding). **Reversibility** two-way door (one more generated command and one small table, `bulk_idempotency`; nothing in a model changes, and an import is undone by deleting the records it made, whose ids the answer lists). **Owner action** no.

**Decision.** *One command for every model.* Every model gets `<model>.bulk_create` beside `create` (`GENERATED_COMMANDS` has seven names now; a package action may not use it), on REST (`POST /api/{model}/bulk_create`), MCP (`<model>__bulk_create`, with an input schema built from the model's fields) and the CLI (`obop import MODEL FILE.csv [--mode partial] [--dry-run] [--key K]`), and in OpenAPI and `/api/meta` (`can_bulk_create`). The permission is the write group of the model; the command needs approval for an agent exactly when `create` does (today never, because the registry cannot mark `create`; the rule is `bulk.needs_approval = create.needs_approval`, so a future approval flag on `create` carries over). *Input.* `rows` (a list of objects, at most `MAX_BULK_ROWS` = 1,000) or `csv` (the text of a file; header names are field names, references are record ids), `mode` (`all_or_nothing`, the default, or `partial`), `dry_run` and `idempotency_key`; any other input name is refused so a typo cannot silently turn a dry run into a real one. *Each row gets the checks of `create`*, by the same code: unknown fields, a supplied `id`, computed and numbered fields, governed fields starting at their first option (the very guard of `create` is run per row), kinds, required fields, references that the caller may see, sequences (numbered in the unit, so a refused row uses no number), `own` defaulting to the caller, the row-level rule that a creator may not make a record they could not then see (D58), and unique values (D57), checked against the stored records and against the rows already accepted in the same call. Image and file fields are refused in every row and column (a blob is uploaded and claimed by its uploader, record by record). *Modes.* All or nothing: one bad row writes nothing and the call answers `400` naming the first five problems; `partial` writes the good rows (a row that failed half way is taken back out of the unit, `Unit::mark` and `rewind`) and reports the rest; `dry_run` does every check, numbering included, discards the unit and always answers with the full report (`ok`, `total`, `valid`, `failed`, `errors` as `{row, line?, error}`, at most 100 listed). *Atomicity.* All rows, the counters they consumed and the idempotency record go to the storage in one `apply_checked` batch, and the call holds the command layer's write lock (the cross-process lock of D59) from its first check to the end, as `create` of a model with sequences or unique fields does. *Idempotency.* With a key, a retried call (same person, model, key, mode and rows) returns the first answer with `replayed: true` instead of creating the rows again; the answer is a `bulk_idempotency` record written in the same transaction as the rows (so it exists exactly when they do), valid 24 hours, purged lazily; the same key for different rows is refused; a dry run neither reads nor spends the key; a failed call leaves it free; the key belongs to the person. *CSV.* `obop_commands::csv` (shared with D69): UTF-8 only, a byte order mark dropped, the delimiter chosen between `,` and `;` from the header line, RFC 4180 quoting with doubled quotes and line breaks inside quotes, a stray or unterminated quote, a short or long row, an empty or repeated header name, a NUL character all errors that name the line; at most 1 MiB, 1,000 rows, 100 columns and 64 KiB per cell. Cells are converted by the field's kind: whole numbers only (a decimal point in a number or money cell is an error: there is no decimal kind and money is in minor units), `true/false/yes/no/1/0`, dates and options and references as text, an empty cell leaves the field out. *Formula injection* concerns writing untrusted text into a file that is opened in a spreadsheet; this import never evaluates anything and keeps a cell such as `=1+1` exactly as text, and any CSV exporter must neutralise cells that start with `=`, `+`, `-`, `@`, tab or carriage return (the note stands here because the reader is here). *Rate limit.* `OBOP_BULK_PER_MINUTE` calls per person per minute (default 12, `0` for none), counted in the shared store, dry runs included, so one person cannot hold the write lock for most of every minute. *Audit and masking unchanged.* The answer carries ids and error texts only; reads of what was made are masked as ever; the observers of the command layer see `<model>.bulk_create` with its `ids`, and the connectors runtime turns that into one `<model>.create` event per record, so subscribed flows behave as for single creates. *Backoffice.* An Import button in the list toolbar (only where `can_bulk_create`), a dialog that reads the file, dry-runs it, lists the problems by row and line, chooses the mode, imports once (a fresh key per chosen file), in the seven languages.

**Threat model.** *A person or agent with the right to create* can make 12,000 records a minute at most, and nothing more than create allows: permission, scope, approval, field kinds, references they can see, the creator-visibility rule, unique values and governed fields are the same checks (tests `bulk_create_applies_the_checks_of_create_to_every_row`, `bulk_create_follows_the_row_rules_and_the_permission_of_create`, and the REST and agent tests in `bulk_tests`). *Someone without the right* gets the same `404` as for an unknown command, and the tool is not listed. *Resource exhaustion:* input is capped before any row is read (1 MiB, 1,000 rows, 100 columns, 64 KiB cells, 100 listed errors), per-row work is bounded (a few lookups), the unit has a record cap, and the rate limit bounds how often the write lock can be held. *Replay and confusion:* the key is scoped to the person and model and bound to a fingerprint of the request, so another person's key or other rows with the same key do nothing. *Partial effects:* nothing is written before the single batch, and a failure of that batch leaves nothing (the sequence numbers included). *Hostile files:* binary or non-UTF-8 input, NUL characters, quote tricks, ragged rows and oversized cells are refused with a line number; a formula cell is stored as text. *Information leak:* error messages quote the offending value as `create` does (a unique-violation names the value); the answer never contains record fields. *Residual:* the call holds the write lock while it runs, so a slow database makes a large call hold it long (on a PostgreSQL round trip of 7 ms, measured on a laptop with the database in a container, a 1,000-row call took about half a minute; on a local database it takes about a second); nothing yet splits the lock into batches. The stored answers of a day of keyed calls live in one table until purged. Row-level attribution of a unique violation that appears only at commit (another writer was faster) is the database's message, for the whole call.

**Acceptance tests (named).** `engine_tests::bulk_create_*` (all or nothing, one bad row and the dry-run report, partial, the checks of create, numbering without gaps, the row rules and permissions, idempotency including expiry, malformed calls, the rate limit, a thousand rows) on memory, SQLite and PostgreSQL; `store::tests::bulk_csv_*` (cells by kind, row and line in errors, header and file problems), `csv::tests` and `unit::tests::rewind_takes_back_what_was_done_since_a_mark` in `obop-commands`; `bulk_tests::rest_bulk_create_checks_creates_and_replays`, `agents_bulk_create_with_the_scope_of_create_and_stay_masked`, `mcp_and_openapi_describe_bulk_create_*`, `cli_import_goes_through_bulk_create_with_every_mode` in `obop`; Playwright `import.spec.ts` for the dialog.

**Why.** Entering a hundred records one by one is how an instance stops being tried; an agent that must call `create` a thousand times is slow, rate-limited by its transport and leaves a half-done import when it fails, and a person moving from another tool has a spreadsheet. **Rejected.** A separate import module or endpoint with its own validation (two sets of rules drift apart: the point is that the rows pass through the same code); remapping ids or pointing at a record of the same file (needs a two-pass design with temporary keys; ids are written as ids); decimal and date-time kinds (not in the platform yet); importing images and files (needs the blob claim rules per row and a transport for the bytes); a background job for large files (the cap keeps a call short enough to answer, and a queue brings status, cancellation and retention); skipping the lock for validation (sequences and unique values need it); a configurable cap above 1,000 (the lock, the 4,000-record unit and the answer size all scale with it); approval for every agent bulk call (the owner asked for create's rule); storing the idempotency answer outside the batch (a crash between the two would replay a call that never happened or repeat one that did). **Consequences.** Honest limits. **Not tried** against a PostgreSQL database under concurrent writers from several server processes, against 1,000-row calls on a network database, or with a file produced by a real spreadsheet program (tested: quotes, semicolons, a byte order mark, CRLF; not Excel's other encodings, which are refused as not UTF-8). There is no decimal or date-time kind, no remapping of ids, no cross-row references and no image or file column. A model whose rows depend on each other (an order and its lines) is imported in two calls, parents first, with the parent ids copied into the second file. The error messages are the server's English text, shown as they come. The translations of the dialog strings are machine-drafted (issue D7). The validation and the commit are two phases of one call, so a very slow database makes the lock last; splitting a call into batches is open (issue I8).

#### D74 Connection pool for PostgreSQL
**Status** PROPOSED (owner-directed in chat, 2026-10-25, step 1 "storage foundations"; requirement OBR-DAT-006, connection pool and non-blocking reads; not yet ratified as binding). **Reversibility** two-way door (the `Backend` contract does not change; every setting is an environment variable with a default; nothing is stored; `OBOP_DB_POOL_SIZE=1` with every time limit set to `0` comes close to the old single connection). **Owner action** operators: check `max_connections` against the sizing rule in docs/DEPLOY.md ("Connection pool and poolers"); behind PgBouncer in transaction mode set `OBOP_DB_POOLER=transaction` and `OBOP_LOCK_DATABASE_URL`; point a scraper at the new `obop_db_pool_*` series; clients of the API should honour `Retry-After` on 503.

**Decision.** *Three small pools instead of one connection behind a lock.* `obop-storage` gets a blocking pool written in the crate (`pool.rs`, generic over a manager that opens and pings connections, so it is tested without a database; `pgpool.rs` is the PostgreSQL side) and no new dependency. The PostgreSQL backend (`pg.rs`) keeps a **main pool** (`OBOP_DB_POOL_SIZE`, default 8, at most 64) for reads and writes, a **lock pool** (`OBOP_DB_LOCK_POOL_SIZE`, default and maximum 8) for session advisory locks that does not count against the main pool, and the blob store (`blob.rs`, `DbBytes`) a **blob pool** (`OBOP_DB_BLOB_POOL_SIZE`, default 4); every connection of every pool is opened through `PgConnector`, so TLS (D66) applies to all of them, and carries `application_name` `obop-main`, `obop-lock` or `obop-blob` (unless the URL names one), a connect timeout, TCP keep-alive and a TCP user timeout. The `Mutex<Client>` is gone. *Acquire.* A call takes a connection for the length of one database call. If none is free it waits at most `OBOP_DB_ACQUIRE_TIMEOUT_MS` (default 2000), counting the time to open a new connection, which happens on a helper thread so a slow connect never keeps a caller past the timeout; and only if fewer than `OBOP_DB_MAX_WAITERS` (default 256) callers already wait, otherwise it is refused at once. The newest idle connection is taken first so the others age out; idle connections close after `OBOP_DB_IDLE_TIMEOUT_SECS` (300), every connection after `OBOP_DB_MAX_LIFETIME_SECS` (1800) (a sweeper thread, plus a check on checkout and on return); a connection idle for `OBOP_DB_HEALTH_CHECK_IDLE_MS` (1000) or more is pinged when handed out (a fresh one never is; `0` pings every checkout), and one that fails the ping takes the other idle connections with it, because they most likely share its fate. A connection whose call failed in a way that leaves its state unknown (socket broken, server shutting down, a failed rollback, an idle-in-transaction kill) or whose holder panicked is discarded, and the idle ones are closed with it. After a failed connect the pool tries again no sooner than 200 ms and one probe at a time, and callers meanwhile get `storage_unavailable` at once instead of waiting out the timeout. A **read** (`get`, `list`, `find`, `count`, `total`, counter and value reads, blob chunks) that finds an old connection dead is repeated once on a fresh one; a **write** is never repeated (it may have been applied) and fails once. *Time limits by command class,* all configurable and `0` meaning "leave the server's own `statement_timeout`": point read or write 5 s, list or search 10 s, aggregate (a scan, `total`) 15 s, batch and import 60 s (a multi-statement transaction, a restore, an export, `ensure_unique`, `purge_expired`). A single statement sets the limit with a session-level `SET statement_timeout` that is issued only when it differs from what the connection already has (tracked per connection, `RESET` for "server default"), so a run of point reads costs no extra round trip; a transaction starts with `BEGIN; SET LOCAL statement_timeout = ...` in one round trip and never touches the session value. *Long reads.* `scan`, `export` and `import` hold one pooled connection and nothing else. `scan` and `export` run in one `REPEATABLE READ READ ONLY` transaction (one snapshot from the first row to the last, no writer blocked); a scan fetches 500 rows at a time through a portal, so memory is bounded and the time limit applies to each fetch and not to however long the consumer takes; a consumer that stalls longer than `OBOP_DB_IDLE_IN_TRANSACTION_MS` (120 s) between fetches loses its snapshot (`SET LOCAL idle_in_transaction_session_timeout`). At most `OBOP_DB_LONG_READS` (default half the pool) of them run at once (a permit taken before the connection), so a few heavy reads cannot take every connection from interactive calls. *Exhaustion.* The pool's refusal is the error text `storage_busy: all database connections are in use, try again` (or `... too many requests are waiting ...`); the other storage faults are `storage_unavailable:` and `storage_timeout:` (`obop_storage::fault`). **The typed way to HTTP:** the storage contract stays `Result<T, String>`, so (1) the error text starts with the fixed code word, which `Fault::of_message` recognises in one place, and (2) the pool *notes* the fault on the calling thread. `obop-http`'s `blocking()` clears the note before a handler's blocking part and reads it after; a layer (`ops::storage_faults`) then replaces the answer of any request that hit a fault by **503 with `Retry-After` (1 s for busy, 5 s for the others) and `{"error":"storage_busy","code":"storage_busy","hint":...}`** (`storage_unavailable`, `storage_timeout` likewise), except on `/healthz`, `/readyz` and `/metrics`, which decide for themselves. *Locks.* A lock is a session advisory lock on a lock-pool connection; the locks one thread holds at the same time share one connection (a thread-local registry of weak references, per backend), so a request that holds an agent's vault lock, then the write lock, then a session lock needs one connection, never waits for a second while holding the first, and eight threads cannot deadlock a pool of eight (or of two) by each holding one and wanting another. A thread that wants its first lock while eight other threads hold theirs waits the acquire timeout and gets `storage_busy`. A lock call that fails poisons its session, which is closed (the server then releases what it still held) when the last lock on it is dropped. `OBOP_LOCK_DATABASE_URL` gives the lock pool a direct address (own `sslmode` rules); at start-up the backend connects both ways and refuses to start unless both report the same `current_database()` and `pg_postmaster_start_time()` (the pooler may alias the name; locks in the wrong database would exclude nobody). *Poolers.* `OBOP_DB_POOLER=transaction` is for PgBouncer (or a pooler like it) in transaction mode: every single statement then runs in a transaction of its own with `SET LOCAL` (about twice the round trips), because the server connection behind a client connection changes between transactions; prepared statements are made and used inside that transaction, so it works with `max_prepared_statements` on or off. Session-mode PgBouncer and direct connections need nothing. *Metrics* (`/metrics`, read from the pools, no connection needed): `obop_db_pool_max_connections`, `_in_use`, `_idle`, `_waiting`, `_acquire_seconds` (histogram, 0.5 ms to 2.5 s, refusals included), `_acquire_timeouts_total`, `_acquire_rejected_total`, `_connect_failures_total`, `_connections_opened_total`, `_connections_closed_total`, all labelled `pool="main|lock|blob"`, and `obop_db_statement_timeouts_total` and `obop_storage_faults_total{fault}`. A ping that fails only because the pool is full counts as "up" for `obop_db_up` and as ready for `/readyz` (the database is there; it is busy). SQLite and memory are untouched: SQLite keeps its one connection (a second read-only connection in WAL mode would let readers run beside a writer for a file database and is not trivial for `scan`, which would need a read transaction held across the visitor; left out).

**Why.** One `postgres::Client` behind a `Mutex` meant that a list, an aggregate or a restore blocked every other request in the process for as long as it ran, that a stuck database call blocked all of them with no way out, that nothing bounded how long a request waited, and that a restarted database left a dead connection behind a mutex; the lock connections were an unbounded set (8 kept), and every `obop backup` opened a connection of its own. The hosted layout puts many instances on one PostgreSQL, so connections are the scarce resource and have to be counted; a pooler in front is the usual answer and had to be made to work with session advisory locks and `SET`. **Requirement mapping and where it differs from the requirement text:** the requirement says "default 8 per process"; the main pool is 8 and the process can also hold up to 8 lock and 4 blob connections (documented in the sizing rule). It asks that a long read "shall not hold a connection used by other requests": a long read holds one connection exclusively for its duration (that capacity is not available to others), capped by the lane. It asks for the trait to stay blocking (no async rewrite), which is what was done.

**Rejected.** *`r2d2` + `r2d2_postgres`, `deadpool-sync`, `bb8`:* each adds three to five crates (and, for r2d2, helper threads per pool) for a pool whose interesting parts are ours anyway: a bounded wait queue, a long-read lane, fault notes, per-pool metrics, connections opened through `PgConnector`, and a manager that tracks session state; r2d2 queues callers up to its timeout with no bound on their number and exposes no waiter count. About 700 lines of pool (comments included), tested without a database, was a smaller risk than adapting one. *An async pool and an async `Backend`:* moves the requirement to size L and rewrites every caller. *A session-level `SET` behind a transaction-mode pooler:* it lands on a session another client then uses. *`SET LOCAL` in a transaction for every statement in direct mode:* four round trips for a point read where two do. *A process-wide semaphore around long reads:* it would have kept the old behaviour for the second one. *Unbounded waiting, or waiting 60 s like a lock:* that is the queue the requirement forbids. *A typed error enum in the `Backend` contract:* the signature `Result<T, String>` is used by about forty files and by every concurrent branch, and callers turn errors into other things on the way up (`.ok()`, `unwrap_or(0)`, `let _ =`, "not signed in"), so a type would be lost exactly where it matters; *an error-string prefix alone* has the same weakness (a session lookup that failed on a full pool would be answered 401 and a client would drop its token). The thread note survives swallowing because a handler runs on one thread from start to end; the code word keeps the text readable on the command line and in logs. *Making `/readyz` fail while the pool is full:* a load balancer would take the busiest instance out and push its traffic onto the others. *One connection per nested lock:* deadlocks a small lock pool. *A connection per request or per user:* the database would hold as many sessions as there are users.

**Threat model.** *Assets:* the availability of database connections (PostgreSQL's `max_connections` is shared with other instances), the integrity of what a connection carries from one caller to the next, the time limits, and the secrecy of the database address. *Pool exhaustion as a denial-of-service lever:* anyone who can make the server hold connections (a signed-in person or agent running aggregates, exports or large `bulk_create` batches, a flood of requests on a public route such as sign-in or the shop) can use up the pool. Bounded by: the acquire timeout and the waiter bound (a flood costs at most 256 parked threads and answers 503 in 2 s, not memory or time that grows with the load); the long-read lane (heavy reads cannot take more than half the pool); the time limits (no call holds a connection longer than its class allows; a stalled scan consumer loses its snapshot after two minutes); the separate lock pool (a flood of ordinary requests cannot stop a lock from being taken and the other way round); and the answer being cheap and honest (`Retry-After`). *Not bounded:* per-person fairness (one person with many parallel requests can still occupy the pool; the per-IP, per-token and per-account rate limits that exist are counters in the same database, and they fail open when the database is busy, which is why a request that hit the full pool is answered 503 as a whole and not allowed through), and the HTTP layer's own concurrency (requests beyond the blocking-thread limit of the runtime queue in the runtime before they reach the pool). Run a reverse proxy with connection and request limits in front of a public instance. *Statement-timeout bypass:* the limits are set by the pool and by nothing else; there is no SQL surface (values are bound, identifiers come from the registry and `ident()`), so no request can run `SET statement_timeout`; a transaction cannot raise its own limit, because `SET LOCAL` is issued by the pool before the caller's statements; the lock pool's sessions run only lock statements. Gaps: a limit of `0` (operator's choice) is the server's value; time in the consumer of a scan is bounded by the idle-in-transaction limit and not by a statement limit; time spent waiting for a row lock inside a batch counts against the batch limit (60 s), which is also how long a batch may hold a connection; the global write lock and same-key waits (`LOCK_WAIT`, 60 s) are a separate queue that this decision does not bound. *Connection leakage across requests:* a connection goes back only after its call finished; an open transaction is rolled back or the connection is closed; a panic discards the connection; statements are closed by the driver; the only per-connection state is the tracked time limit, and the lock sessions return to their pool only when no lock is held on them (tested: `nested_locks_of_one_thread_share_a_connection...` ends with every key free for a fresh handle). A process serves one database (D6), so no tenant shares a pool with another; the pool never changes role or database on a connection. Later work that needs per-request session state (a role per caller, row-level-security settings) must use `SET LOCAL` inside the call's transaction or a pool per role, never a session-level `SET`. *`SET` state leaking between pooled sessions:* only `statement_timeout` is ever set; direct mode tracks it per connection and `RESET`s it for "server default" (test `time_limits_follow_the_command_class_and_never_leak_between_callers`: seven calls of mixed classes on one connection each see exactly their own limit, a transaction's `SET LOCAL` ends with it); transaction mode sets nothing on a session at all. A client that is told one limit by the server and another by `SHOW` cannot arise from the pool. *Dead or stale connections:* checked on checkout when idle, dropped with their neighbours on failure, never put back after an error that leaves their state unknown; a write is not repeated. *Disclosure:* the 503 bodies are fixed words and a hint; the driver's text (which names no host or user, tested for the lock address) goes to the error string only; `/metrics` carries counts and the three pool names, no record, user or path; the lock URL is validated with the same rules as the database URL and its text is never echoed. *Out of scope:* a compromised database or pooler; a network that drops packets silently (keep-alive and a user timeout are set where the platform supports them); admission control above the pool.

#### D56 Action effects and assertions
**Status** BINDING (owner-directed in chat, 2026-10-17). **Reversibility** two-way door. **Owner action** no.

**Decision.** An action (a transition, D48) may declare `assert` conditions and `[[model.action.effect]]` entries. Conditions are boolean expressions (docs/MODULES.md 3.8) over the record and its child records, checked before anything is written; a failure refuses the action with the declared message. Effects run in order after the new state is set, in the same unit of work: the command layer builds every write in an overlay (so later effects see earlier ones), applies them with one `Backend::apply` transaction on SQLite and PostgreSQL (`insert_many` generalised to inserts, merges and deletes), and the sequence counters taken on the way are part of it. Kinds: `create` (fields from `$self.f`, `$self.id`, `$line.f`, `$created.name`, `$now`, `$today`, `$caller` or constants; `for_each` repeats it per child row), `update` (a ref'd record or the children of this record), `adjust` (add or subtract an amount from a number field of the record a ref names or the one a `match` finds, optionally creating it, optionally with a floor), and `set_state` (run an action of another model, whose own group, from-state, required fields, assertions, sequences and effects all apply; an effect never sets a governed field any other way). Effects run with the caller's permissions: the caller needs the write group of every model an effect writes and the group of every action it starts, every record involved must be visible to the caller (D58), and typed validation (D47) applies to what is written. The guard computes this before anything runs, so an agent without the groups is refused at once; if any action reachable through `set_state` needs approval, the whole operation is one proposal and the approver must hold all those groups. Limits: 12 effects per action, 500 records created, changed or looked at per operation, `set_state` chains at most 4 deep with no cycle; expressions are at most 400 characters and 80 parts. The install refuses an effect whose target model or field does not exist or is not in the package's dependencies, whose value does not fit the target field's kind, that omits a required field, that loops over a model that is not a child of this one, that refers to `$created` before it exists, or that closes a cycle of `set_state` effects. Built-in modules declare the same metadata in Rust (`Effect::create` and friends): confirming a sale order creates the draft invoice and its lines, `invoice.post` is asserted to have a total, `inventory_move.validate` adjusts the stock items at both ends, accounting refuses to post an unbalanced entry.

**Why.** Actions that can only flip a field left every workflow to be completed by hand, and the platform's promise (one data model, generated surfaces, agents that propose and humans that approve) fails if the interesting part of a workflow is outside it. **Rejected.** Code in packages (D11 reserves it for Wasm); a general expression or scripting language (unbounded, unreviewable); effects that run as the system (an escalation that would let any action holder write anywhere); eventual consistency through a queue (a half-applied posting is the failure this exists to prevent); triggers on plain create and update (hidden control flow). **Consequences.** The unit lives in one process: the dispatcher holds one lock around every write of a model that has a rule or is an effect target, so two servers on one PostgreSQL database can still race between the reads and the transaction (one process per database stays the rule, D30, D48). The transaction makes the writes atomic, not the reads consistent across servers. Effects cannot call out; notifications and payments wait for the Wasm tier. Data written outside the commands (seeds, imports) does not run effects. **Evidence.** D11, D18, D41, D47, D48, MODULES.md 3.4 and 3.8, tests `engine_tests` and `model_tests`.

#### D57 Computed fields, uniqueness and sequences
**Status** BINDING (owner-directed in chat, 2026-10-17). **Reversibility** two-way door. **Owner action** no.

**Decision.** *Computed fields.* `computed = "<expression>"` on a `text`, `number`, `money` or `bool` field: integers, text and booleans only, `+ - * /` (division rounds half away from zero, null counts as 0, `""` or false), comparisons, `&&`, `||`, `!`, `if`, `concat`, `is_set`, and the aggregates `sum`, `min`, `max`, `count` over child records (`sum(lines.amount)`, optionally `where <condition on the child>`). A computed field is not stored: it is evaluated when a record is read, from the current children, and put into the record before filtering and sorting, so it can be filtered and sorted on and is in `get`, `list`, `search` and the response of every write. It cannot be written (sending its current value back is accepted, anything else is refused), is never required, and may read other computed fields as long as there is no cycle. *Why on read:* a stored total drifts whenever any write path forgets it (an effect, an import, a child changed by another action); a total computed from the children cannot. The cost is a look at the children per read: an indexed lookup for one record, one scan of the child table grouped by parent for a list. A computed value is as protected as its inputs: the install requires the same permission group, a class that covers the inputs' (the same class if they are sensitive) and personal-data status. *Uniqueness.* `unique = true` (optionally `unique_with = ["company"]`): checked against the records as the unit would leave them, under the dispatcher lock, so there is no check-then-write race inside a server, and backed by a partial unique index on SQLite and PostgreSQL (an expression index over the JSON, empty values excluded) that also catches a second server; a violation is `model.field must be unique: "x" is already used by another record`. *Sequences.* `kind = "sequence"` with a `format` such as `INV-{year}-{seq:05}`, `assign_on` (an action; default: at create), `gapless` and `reset` (`never`, `year`, `month`). The number comes from a counter record (`sequence_counter`, per model, field and period) read and written inside the same unit as the record, so a failed posting consumes no number and parallel postings cannot share one. `gapless` additionally forbids deleting a record that holds a number. A sequence is read-only and is unique by construction (and indexed). `obop sequences backfill [MODEL [FIELD]]` numbers existing records in creation order, in one transaction per field; records created before the field existed stay unnumbered until then, and the year of a backfilled number is the current one.

**Why.** Totals, balances, numbers and duplicate checks were conventions that people kept by hand (MODULES.md section 10 listed them as limitations); invoice numbers in particular were a placeholder. **Rejected.** Stored computed values with recompute hooks (drift, and every write path needs the hook); a general formula language with floats and functions (rounding bugs, unbounded cost); database sequences (not rolled back, so not gapless, and not available on SQLite); numbering at create for invoices (draft cancellations would leave holes). **Consequences.** Aggregates ignore row-level access (D58) and sum all children of a record the caller can see; give children `via` the parent so the two agree. Computed values cost reads and are not indexed. Sorting by a computed field reads all rows. Date arithmetic does not exist: SLA elapsed times stay out. A unique index cannot be created over existing duplicates; the instance then logs a warning and keeps the write-time check only. **Evidence.** D30, D47, D56, MODULES.md 3.3 and 3.8, tests `engine_tests`, `model_tests` and the storage contract.

#### D58 Row-level access
**Status** BINDING (owner-directed in chat, 2026-10-17). **Reversibility** two-way door. **Owner action** no.

**Decision.** `[model.access]` adds record rules to the group checks of a model: `own` (a text or ref field holding the user id of the person the record belongs to), `via` (a ref field: visible when the parent record is, up to four hops), `public_field` (a bool, which may be computed: visible to everyone who may read the model when true), `shared_with` (a text field of user ids separated by commas) and `see_all_group` (a group, or a list of groups, that sees every record). A record is visible when any rule grants it; `platform.admin` sees everything; a model with no rules is unrestricted. Enforced in `get`, `list`, `search` (the rule is applied before the filter, the sort, the page and the count, so `total` counts only visible rows), `update`, `delete`, every action including those started by effects, the referrers named when a delete is refused, and ref validation (a ref to a record the caller cannot see fails with the message for a record that does not exist). A forbidden record answers exactly like a missing one in every command (`no <model> <id>`). An agent acts for its owner: `own` and `shared_with` match the owner's id, and the groups are the owner's intersected with the token's scopes, so it never sees more than its owner and sees `see_all` records only if the scope includes the group. On create, `own` defaults to the creator and a person who cannot see the result is refused (`set employee to yourself`); an update cannot move a record out of the caller's own sight. The public site (D50) is a separate layer with its own whitelist and is unchanged. Applied to hr leave requests, expenses, timesheets, documents (by confidentiality, through a computed `open_to_all`), dashboards (`shared`, closing A6; tiles follow their dashboard through `via`), while connectors keep their own owner scoping.

**Why.** Group checks cannot say "your own", so every leave request, expense and confidential document was readable by everyone who could read the model, and the dashboard sharing flag was a label. **Rejected.** Post-filtering in the surfaces (counts and totals leak, and each surface would need it); per-field rules (D40 and field groups already cover columns); rules in expressions (an evaluator on the hot path of every read; the five declarative rules cover the cases that occur). **Consequences.** Rows are filtered in the command layer after the model is read from the store, as filtering already is (D49), so the cost is linear in the table. Aggregates and computed totals ignore the rules (D57). The id of a user is the login name; a record owned by a name that is not a login is invisible to everyone but the managers. Existing records get no owner: a model that gains `own` hides its old records from non-managers until their field is filled in. Data written outside the commands is not checked. A unique constraint can still reveal that some record holds a value (a duplicate is refused), because uniqueness is global. **Evidence.** D10, D18, D40, D48, D49, D56, D57, MODULES.md 3.9, the oracle test in `engine_tests` and `model_tests`.
