## 0. Summary

A customer who runs an obop instance for its own people can show them its own name, not "obop". One record, `instance_brand`, holds the name, a slug, the logo, a sign-in title per language, a sign-in message per language and (from S2) one switch. Every server-side place that shows the product name to an end user reads that record through one reader. The phone app is the one exception (section 1). An instance that sets nothing renders its pages byte for byte as today and the default product name stays obop; section 13 says exactly which outputs that covers, because the authenticated command lists grow.

- One record, three typed commands (`get`, `configure`, `clear`) on the CLI, REST and MCP and a tab in Customize, changed only by a person who holds `platform.admin`, through one wrapper. `configure` merges the fields it is given over the stored row, with an explicit way to clear each field (sections 3 and 4).
- Stored as a record, not as environment variables, because it is a command, it has a logo, several server processes must agree and a change must be audited (section 4).
- It defers to what exists: the instance theme owns the accent, the `site.*` keys stay the explicit override of the public site, `OBOP_MFA_ISSUER` stays an explicit override of the authenticator label, and `get` shows which source won for every value (section 5).
- Server-rendered pages take the record through a reader with a two-second process cache. The back office, which must show the name before anyone has signed in, gets a small public subset injected into its page, the way `OBOP_DEFAULT_LANGUAGE` is today. Both widen what is public, which is why section 15 names the records they change (sections 4 and 6).
- Five sentence families of the OAuth pages name obop, and German, Finnish and Swedish attach the name to compounds and case endings. With a brand set they switch to neutral wording that names no product, in all seven languages (section 7).
- The OAuth and signing pages keep their content security policy. The logo there is inline SVG built by the server from a strict subset, never an image or a style (section 8).
- What the record cannot touch is fixed and listed: the security statements of the consent page, the wire names, the licence and NOTICE text, any attribution (sections 10 and 11).
- Delivery is four slices, S1 to S4, sized in section 12. S1 alone is not a customer-ready cut. Tests, including a scan that fails when a literal `obop` is added to a page that should use the record, are in section 13.

## 1. The direction, and what is not asked

There is one instance branding record that every surface reads; MOHV only sets values. The values for MOHV are the name `MOHV` and, for now, a plain "M" as the logo, to be replaced later by the real logo as one file. The phone app is called MOHV on the phone, with application id `se.mohv.app` and test id `se.mohv.app.test`; "Mileage" stays the module name inside the host.

Its name under the icon, both permission prompts and the sign-in strings are fixed when the app is built, and the sign-in screen is shown before any server is known (section 12, S4). That is a proposal that depends on draft PR 63 and on a brand block that the host spec does not have yet. The exception is a Q71 item.

## 2. The record

One model, `instance_brand`, in the built-in module `platform` (the Customize app) beside `setting` (`K/obop-pkg/src/installer.rs:2418`) and `sso_provider` (`K/obop-pkg/src/sso.rs`). One row, id `instance`. No row means no brand.

**One predicate.** A brand is *set* when the row exists and validates. That single test decides the neutral wording (section 7), the icon link and the policy addition (section 8), titles, messages, the generated tile and the shell rewrite (section 4). There is no second test. A row that names `obop` is not special: it renders the name obop with the generated tile unless it carries an artwork, and nothing it holds is dropped without a word. `clear` restores the stock look.

Every field has data class `none` (the code's `DataClass::None`, "explicitly not personal data", the class `setting.value` has; CONVENTIONS 5 lists no row for it). Every field is readable without signing in, by design, so none may hold personal data; the field descriptions and the form say so. `<lang>` is each of `en`, `de`, `fr`, `pl`, `fi`, `sv`, `es` (`K/obop-oauth/src/page.rs:16`); a test ties the model's language fields to that list, so an eighth language is a deliberate model change.

| Field | Kind and limit | Meaning |
|---|---|---|
| `name` | text, 1 to 40 characters | The product name. Required: a row without one is not stored. Character policy below |
| `slug` | text, up to 30 | Lowercase `a-z`, `0-9`, `-`. Empty means derived from `name` (below). The stem of the recovery-codes file and the MCP `serverInfo.name` |
| `title_<lang>` (7) | text, up to 60 | The sign-in title in that language: the line beside the logo on the sign-in screens and the tab title before sign-in. Empty means the English title, then `name`. Same character policy as `name` |
| `message_<lang>` (7) | text, up to 240 | One plain-text message under the heading of the sign-in screens in that language. Empty means the English message, then none. Character policy below; shown escaped, no links |
| `logo_svg` | longtext, up to 16 KiB in | The logo and the tab icon, one artwork. Input is an SVG file; what is stored is the canonical text the parser of section 8 re-wrote, never the input. Empty means the generated tile |
| `hide_product_docs` | bool (added in S2) | Hide the Brand book and the Guide in Customize, the account menu and the command palette (section 6). Nothing reads it before S2, so the field and the flag arrive with S2 |

Characters count as Unicode code points, as D90 does. There is no stored logo hash. The *version* of the logo, `v`, is the first 16 hex digits of the SHA-256 of the exact bytes the logo route serves (the stored artwork, or the generated tile drawn from the name and the resolved accent). `Reader::current` computes it, so the `ETag` and the `?v=` of the icon URL always follow what is served, also when a theme change alone alters the tile. The icon URL is `/api/brand/logo.svg?v=<v>` in every case.

No colour field: the accent stays the instance theme's (section 5). No `logo` for dark mode: one artwork, so a logo that must work on both light and dark backgrounds uses explicit colours (section 14).

**Character policy** (one allow-list for `name`, `title_<lang>` and `message_<lang>`; the same code on the command, on the read and in the shell). Text is normalised to NFC before the checks and stored in NFC; a stored value that is not NFC fails the read check. A character is allowed only if its Unicode general category is one of:

- a letter (`Lu`, `Ll`, `Lt`, `Lo`; not `Lm`, whose members include look-alike modifiers) that has a real script, so the mathematical alphanumerics (script Common) are out;
- a mark (`Mn`, `Mc`) directly after a letter or digit;
- a decimal digit (`Nd`);
- the ASCII space U+0020 only, never leading, trailing or doubled (every other `Z` category is out, so no no-break space or ideographic space);
- punctuation: for `name` and `title_<lang>` the ASCII `- . , & ' + _ ( ) !` and nothing else; for `message_<lang>` any punctuation category (`P*`) and currency symbols (`Sc`).

Whatever the category, a character with the Unicode property Default_Ignorable_Code_Point is refused. That covers the zero-width characters, the soft hyphen, the variation selectors, the tag characters U+E0000 to U+E007F and the Hangul filler; the bidirectional controls and the other format characters (`Cf`), controls (`Cc`), private use (`Co`), unassigned (`Cn`) and surrogates are refused by category. `<` and `>` are not allowed in any field. `name` and `title_<lang>` start with a letter or digit and may not hold `@`, `/`, `:` or a quote, so no URL or address can pass as a name. For `name` and `title_<lang>` every letter belongs to one script, with the allowance of the Highly Restrictive level of Unicode UTS #39 (a single script, or Latin together with Han, Hiragana and Katakana, or with Han and Bopomofo, or with Han and Hangul), so a name that mixes Latin and Cyrillic letters is refused; digits and the listed punctuation are script-neutral. The tables the check needs (normalisation, general category, script, default-ignorable) come from the ICU4X crates `icu_normalizer` and `icu_properties`, which are already in `Cargo.lock` (`Cargo.lock:859`, `Cargo.lock:882`) next to the `icu_collator` and `icu_locale` that `obop-commands` depends on (`K/obop-commands/Cargo.toml:24-25`); their licence (Unicode-3.0) is checked against the dependency rule when they are added to `obop-brand`, and is not verified here.

**The slug.** Derived from `name` when `slug` is empty: decompose (NFKD), drop marks, lowercase, keep `a-z` and `0-9`, turn every other run into `-`, trim the ends. If nothing is left (a name with no Latin letters, such as one in Cyrillic or Han), the slug is `brand-` plus the first 8 hex digits of the SHA-256 of the NFC name. That keeps it from falling back to `obop` and from being one shared value, such as `instance`, for every non-Latin instance in `serverInfo.name` and in the recovery file; two instances with the same non-Latin name still share it, and an operator who wants a readable slug sets `slug`.

**The generated tile.** With a name and no `logo_svg`, the server draws a tile: the first letter or digit of the name on a rounded square, with the contrast rule the public site already applies (`K/obop-site/src/seo.rs:56-72`; the `fill` and `on_fill` come from `theme::resolve`). The glyph is that one scalar value; it is uppercased only when the simple, one-to-one uppercase mapping gives a single scalar, so `ß` stays `ß` and does not become `SS` (the public site's own tile uses `to_uppercase()` on the first alphanumeric, `seo.rs:58-64`, which can expand). The fill is the *resolved accent*: the theme's stored accent when it is a valid `#rrggbb`, else a neutral slate, `#495670` (the Slate preset, `UI/src/theme.ts:22`). The tile is never the obop violet `#6d3fd0` (`UI/src/theme.ts:16`, `UI/src/tokens.css:76`), whatever the theme says or does not say. That is the "M" placeholder for MOHV, and no file is needed for it. Swapping to the real logo later is one flag with one file, and it changes nothing else of the row: `obop admin brand configure --logo-file logo.svg` (section 3).

## 3. Commands, who may change it, audit

Per CLAUDE.md "agentic first", every capability is a typed command on all surfaces. The shape follows `sso_provider` (`K/obop-pkg/src/sso.rs`), a one-row configuration model with `get`, `configure` and `clear`:

| Command | CLI (the built `admin` area) | REST and MCP | Effect |
|---|---|---|---|
| `instance_brand.get` | `obop admin brand status` | `/api/instance_brand/get`, tool `instance_brand__get` | Returns the effective brand with the source of every value (below). Read group `*` (any signed-in principal), because the values are public anyway |
| `instance_brand.configure` | `obop admin brand configure [--name N] [--slug S] [--title LANG=TEXT]... [--message LANG=TEXT]... [--logo-file F or --clear-logo] [--hide-product-docs on or off] [--from FILE] [--dry-run]` | `/api/instance_brand/configure`, `instance_brand__configure` | Merges the fields it is given over the stored row, validates, writes and audits in one batch. A refused value names the field and the rule, and nothing is stored |
| `instance_brand.clear` | `obop admin brand clear` | `/api/instance_brand/clear`, `instance_brand__clear` | Deletes the row; every surface is as today. With no row it answers `{"cleared": false}` and writes no event |
| (CLI shortcut) | `obop admin brand check FILE.svg` | the same as `configure` with `dry_run` and only `logo_svg` | Runs the SVG reader of section 8 on a file with no database, like `obop modules check FILE`, and prints the canonical text's size and `v` or every refusal with its reason. It is the same dry run, so there is no capability that only the CLI has |

**`configure` has one rule on all three surfaces.** The CLI, REST and MCP call the same function, `brand::apply`, which merges by supplied field:

- A field that is not supplied keeps its stored value. The first call needs `name`. So the one-flag logo swap `configure --logo-file logo.svg` replaces the artwork and leaves the name, titles and messages alone, and `configure --title sv=Logga in` changes one title.
- Each field has an explicit clear value. A text field (`slug`, `title_<lang>`, `message_<lang>`) is cleared by an empty string (the CLI `--title sv=` with nothing after the sign); the artwork by `logo_svg: ""` (the CLI `--clear-logo`); the switch is set by an explicit true or false (the CLI `on` or `off`). `name` cannot be cleared, only replaced; `clear` removes the row.
- `dry_run: true` (the CLI `--dry-run`) does all the checks, writes nothing, logs nothing, and returns what would be stored: the canonical artwork's size and `v`, each field that would change with its old and new value, and every refusal with its reason. D80 asks a dry run of a mutating command. The `plan_id` of D80 is the approval path of an agent, and no agent may run this command, so it has none.
- It is idempotent by construction: the same values twice change nothing and write no event, which is what the idempotency key of D80 is for, so none is added.
- The read, the merge and the write happen under the dispatcher's transaction lock (`serialize` of `register_guard`, `K/obop-commands/src/lib.rs:765`), so two administrators do not lose each other's change.
- `--from FILE` is a CLI convenience: a TOML file of the same keys is read and sent as the fields of one call (a proposal that serves the exception of section 1).

**What `get` returns.** The effective brand, so that an operator can see why a surface still says obop. Each public value comes with its `source`, one of `record`, `env`, `site` (a `site.*` key), `theme` or `default`:

| Value | Possible sources |
|---|---|
| `name`, `slug`, `logo` (artwork or tile) | `record`, `default` |
| `title_<lang>`, `message_<lang>` (the value after the fallback chain of section 2) | `record`, `default` |
| `authenticator_issuer` (the label and `issuer=` of a new authenticator entry) | `env` (`OBOP_MFA_ISSUER`), `record`, `default` |
| `accent` (the sign-in screens and the tile) | `theme`, `default` |
| `site.title`, `site.logo_url`, `site.accent`, favicon (the public site) | `site`, `record`, `theme`, `default` |

It also lists `fallbacks`: each field of a stored row that failed the read check and so fell back to the default, with the reason (for example after a release tightened a rule). With no row it returns the defaults with source `default` and `set: false`; the Identity tab and the signed-in app call it, so it must be cheap and never an error. At a terminal `status` reports the environment of the terminal's own process, which may not be the server's; REST and MCP report the server's.

**Who.** Group `platform.admin` (`K/obop-commands/src/lib.rs:52`) and a person. There is **one mechanism**: a `Dispatcher::around` wrapper on `instance_brand.configure` and `instance_brand.clear` that refuses unless `Principal::is_person()` (`K/obop-commands/src/lib.rs:101`: a user principal with no scopes), the way `sign_link.create` does (`K/obop-commands/src/sign/link.rs:52`). That is the only check that also stops a mobile app's token, because that token keeps the owner's plain id with `scopes` set (`K/obop-auth/src/lib.rs:432-447`) and so an id test such as `person_only` of `sso_provider`, which looks for a `/agent` suffix (`K/obop-pkg/src/sso.rs:102-107`), would let it through. The wrapper runs when the command really runs, after the guards and after any approval, and an approved plan runs as the principal that proposed it (`K/obop-commands/src/lib.rs:1094-1098`), so an agent's approved proposal is refused too; the commands declare no approval, so an agent gets a refusal, not a proposal. `sso_provider` is cited only for the D41 rule that a command is on every surface or on none (`K/obop-registry/src/lib.rs:949`), so `configure` and `clear` are listed in the MCP tools of a principal that holds `platform.admin` and refuse when they run. `get` has no wrapper: reading is open to any principal, an agent token included. The reason for the guard is that a name and a logo decide what a person believes they are signing in to.

**Only these commands exist.** A command exists on the REST, MCP and CLI surfaces only where a handler is bound (`Dispatcher::register` fills the command table, `K/obop-commands/src/lib.rs:679-760`), so the model is hand-registered like `sso_provider`: `get`, `configure` and `clear` and nothing else. The generated `create`, `update`, `delete`, `bulk_create` (and with it `obop import`), `list` and `search` do not exist for it; `register_crud` is not called for it (`K/obop-commands/src/store.rs:299-345`). Were a later change to bind them, each would have to be refused through the same `around` wrapper, as `sign_link` refuses `bulk_create` (`K/obop-commands/src/sign/link.rs:42-47`). A test asserts the commands are absent or refused (section 13). Because the model has no `list`, `/api/meta` and the authenticated OpenAPI document do not list it (a model appears there only with a visible `list`, `K/obop-commands/src/lib.rs:543`), and MCP gives its tools the generic input schema; the typed shapes are those of this section.

**At a terminal** `obop admin brand` acts on the database as the operator, as `obop site set` does (`crates/obop/src/main.rs:1343-1363`) and as `obop admin sso configure` does through `operator_sso_configure` (`crates/obop/src/accounts_cmd.rs:218-220`): a person with the host, not a token. It calls the same `brand::apply`, with the actor `operator`. The back office tab (section 6) calls the three commands and nothing else, so there is no UI-only path, and the parity gate of D80 applies to all three commands.

**Audit.** `brand::apply` writes the row and the events in **one atomic batch** (`Backend::apply_checked`: `Op::Put` of the row, or `Op::Delete` for `clear`, and one `audit::event_op` per changed field, `K/obop-commands/src/audit.rs:74`, `K/obop-storage/src/lib.rs:38`). The entry then exists exactly when the change does. This is not the settings precedent, which writes the data first and the event afterwards and only prints a failure to stderr (`K/obop-pkg/src/installer.rs:1437-1451`, `K/obop-commands/src/audit.rs:47-58`). Each event has kind `brand_configured` or `brand_cleared`, the actor, the field name and the **old and the new value** of that field. All fields are class `none` and at most 240 characters, so the values are written as they are; the artwork is recorded as the old and new `v`, since 16 KiB does not belong in a log line. After a `clear` or an overwrite the log therefore still shows exactly what users saw. Both kinds are added to the list in the description of `security_event.kind` (`K/obop-pkg/src/installer.rs:2442-2445`), which `K/obop-http/src/audit_kind_tests.rs` holds to the code.

## 4. Where it is stored, and how each surface reads it

**Record, not environment.** The existing branding-like settings are environment variables read once at start (`OBOP_MFA_ISSUER`, `K/obop-auth/src/mfa.rs:99-101`; `OBOP_DEFAULT_LANGUAGE`, `K/obop-http/src/shell.rs:1-9`). That does not fit here: (1) an environment variable is not a command, and every surface must have one; (2) a logo of 16 KiB does not belong in an environment variable; (3) several server processes on one PostgreSQL database must agree without a restart, which a record read through a short cache gives and an environment variable cannot; (4) a change must be audited and the environment has no author. Precedent for a record read at request time exists: `Auth::security_setting` reads `obop_setting/instance` each time (`K/obop-auth/src/mfa.rs:147-151`) and `site_settings` does the same for the public side (`K/obop-commands/src/public.rs:745-757`). No new environment variable is added in S1, and `OBOP_MFA_ISSUER` and `OBOP_DEFAULT_LANGUAGE` keep working (section 5).

**Not inside `obop_setting/instance`.** That row is one JSON text that `setting.update` replaces whole for any principal that holds `platform.admin`, with no person-only check (`K/obop-pkg/src/installer.rs:2614-2626`), and its one field is class `none` with no per-field rule. The brand needs per-field validation and a person-only guard, so it is its own model. The theme stays where it is.

**One reader.** `Brand` and its rules live in a new leaf crate `obop-brand` (the validation and character policy, the slug, the SVG reader, the tile, the neutral-wording switch; no I/O, as `obop-values` is a leaf crate). The reader, `obop_commands::brand::Reader`, is made once per backend at start and handed to the shell, the OAuth and signer handlers, `Auth`, the connector return page and the MCP server; there is no global. It has two reads.

- `current()` returns a `Brand` for display. It runs the same validation as the command on every field (defence in depth: a row written by a restore, an import or an older binary is checked again on read). A field that fails falls back to the default for that field, never rendered raw, and the reason is kept for `get`. A failed store read returns the default brand and writes one log line.
- `strict()` returns the brand or an error, and is used where the text is written into the person's own device and cannot be corrected afterwards: the TOTP `begin` (when `OBOP_MFA_ISSUER` is not set; the environment value wins and needs no read) and the passkey registration options (`rp.name`, `K/obop-auth/src/passkey.rs:619`, emitted with `residentKey: preferred`, `passkey.rs:626`). It fails closed: when the store read fails, or the stored `name` fails validation, the enrolment answers 503 (`MfaError::Unavailable`, mapped at `K/obop-http/src/mfa.rs:154-157`) and never writes a silently defaulted label. No row at all is not a failure; the default is the answer. A sign-in passkey ceremony emits no name (`passkey.rs:445-471`) and does not need `strict()`.

`Brand::default()` is name `obop`, no artwork, no titles, no messages, neutral wording off, and so is any instance with no row; every consumer asks `Brand` for the name and so takes one code path with or without a row. The shell, the OAuth handlers, the signer door, the connector return page, `mfa`, the passkey context builders and the MCP server call the reader and no other code reads the row (a scan, section 13). A golden corpus of names that must stay accepted is part of the tests, so a release that tightens the character policy fails CI instead of reverting a customer's name to obop (section 13).

**The cache.** The reader keeps the parsed `Brand` (the row, the resolved accent read from `obop_setting/instance`, the logo bytes and `v`) in the process for at most two seconds. Two seconds is the bound that D67 sets for the one unauthenticated route that reads the database (`/readyz` "costs the database one ping and one read per two seconds however hard it is hit", `docs/DECISIONS.md:763`). The shell is the fallback for every unmatched path (`K/obop-http/src/lib.rs:502-516`), so scanner traffic for `/wp-login.php` or `/.env` would otherwise cost a read each. A `configure` or `clear` through this process drops its own cache at once; a theme change (`setting.update`) and a change made through another process show within two seconds. A shared version number as in D59 (`docs/DECISIONS.md:657`, the pattern `K/obop-community/src/store.rs` uses) would make that immediate, but it would not cover a theme change made by `setting.update`, which does not touch the brand row and changes the accent that the tile and the meta tag carry; so the time bound is used, and it covers both. A request that is not for an HTML document or the logo route never asks the reader, so it costs no read. Tests build the reader with a zero bound.

**Pages before sign-in.** The back office shows the sign-in, second-factor, enrolment and forced-password screens before the settings can be read, and no pre-sign-in route carries a setting today: "no other setting is public" (`K/obop-http/src/shell.rs:3-8`; `/api/meta` and `/api/commands` are routes at `K/obop-http/src/lib.rs:331-332` that answer 401 without a token, which is from the render check). The same mechanism carries the brand, and it widens what is public (section 15.1 lists the exact fields and the records). Today the shell rewrites the page only when `OBOP_DEFAULT_LANGUAGE` is set: with no language it returns the file service's answer untouched (`shell.rs:326-328`), and `Shell` holds no store handle (`struct Shell { files, language, limit }`, `shell.rs:269-274`). So S2 gives `Shell` the reader and makes it rewrite with or without the language variable. The two places that build a `Shell` use the same reader: `spa_with_json_api_404` (`K/obop-http/src/lib.rs:505`) and the public-site router that nests it under `--admin-prefix` (`K/obop-http/src/public.rs:86`). The reader is asked only when the answer is an HTML document (the shell's `is_html` check), so scripts, style sheets and pictures cost no read.

- With no brand set and no language the answer is byte for byte what it is today, validators kept (tested).
- With a brand set the answer is a `200`, `no-cache`, without `ETag` and `Last-Modified`, and the request's validators are ignored, exactly as for the language tag (`shell.rs:14-22`).
- The rewrite (1) replaces the first `<title>…</title>` with the escaped `name`; (2) replaces any `<link rel="icon" …>` tag, whatever its `href` and attribute order, with `<link rel="icon" href="/api/brand/logo.svg?v=<v>" type="image/svg+xml">` (the source tag at `BO/index.html:7` has `href="/favicon.svg"`, but the Vite build prefixes the base, set by `OBOP_ADMIN_BASE` in `BO/vite.config.ts:8-10`, and the render check saw `/admin/favicon.svg` in the image shape, so a match on the source text would miss it); (3) adds `<meta name="obop-brand" content="…">` whose value is one JSON object, attribute-escaped by the existing `shell::attribute`: `name`, `slug`, `titles` (the non-empty ones), `messages`, `v`, and `accent` (only when the theme stores a valid `#rrggbb`) and nothing else. The page reads it before its first render, as it reads `obop-default-language`. `hide_product_docs` is not in it; the signed-in app gets it from `instance_brand.get`.
- A shell that cannot take the rewrite on a row that exists (no `<head>`, no `<title>`, no icon link) is served as it is, and one line is written to stderr once per process, so a title that silently stays obop is not a mystery.

**The logo route.** `GET /api/brand/logo.svg` (public, like `/api/openapi.json`, `K/obop-http/src/lib.rs:333`) serves the stored canonical text or the tile and nothing else; it takes no path or id, so it is not a file server. Headers: `Content-Type: image/svg+xml`, `X-Content-Type-Options: nosniff`, `Content-Security-Policy: default-src 'none'; style-src 'none'; sandbox`, `Cache-Control: no-cache`, `ETag` = `v`. No brand set: 404 (today there is no such route).

## 8. The OAuth and signing pages: policy, logo, SVG, escaping

**Policy stays.** Both pages send `default-src 'none'; style-src 'sha256-<hash of CSS>'; …` and no `img-src` (`page.rs:151-165`, `K/obop-http/src/sign_page.rs:54-58`); the hash is computed from the fixed `CSS` constant, and the passkey script is allowed by its own hash. Rules this proposal keeps: no new script, no `style=` attribute, no new rule in `CSS` (a changed `CSS` changes the hash and every page's bytes), no `<img>`. So the logo on these two pages is inline `<svg>` with presentation attributes (`width`, `height`, `viewBox`, `fill`, `stroke`, `d`), which the policy does not govern. The one addition is the icon link: when it is emitted the two policies gain `img-src 'self'`, because browsers differ in whether a tab icon is held to `img-src` and which do is not verified here. With no brand set neither the link nor the directive exists.

**Serving the logo to an unauthenticated page.** There is no file serving. The artwork is one stored value, served by one fixed route (section 4) or inlined by the server into the page it renders. The server never serves an uploaded file as it came, never follows a URL in the artwork, and never takes a path or id.

**SVG rules.** Input is parsed by a strict, hand-written reader in `obop-brand`; the stored text is a re-serialisation from the parsed values, so a parser bug can refuse or mis-read a logo but cannot store hostile markup. The subset is wide enough for a logo exported from a design tool after it has been cleaned, because the owner's "swap the real logo later with one file" depends on it, and `check` and `dry_run` (section 3) say exactly what to remove.

- Accepted: an optional `<?xml version … ?>` line; one root `<svg>` with a `viewBox` of four finite numbers (width and height are ignored, not stored); at most 128 elements in all, of these kinds: `<g>` (grouping only, nested at most 4 deep), `<path d>`, `<rect x y width height rx>`, `<circle cx cy r>`, `<ellipse cx cy rx ry>`, `<line x1 y1 x2 y2>`, `<polygon points>`.
- Attributes per element: `fill` and `stroke` as `#rgb`, `#rrggbb`, `none` or `currentColor`; `fill-rule`; `stroke-width` as a finite non-negative number; `transform` limited to a list of at most four `matrix(a b c d e f)`, `translate(x y)` or `scale(x y)` with finite numbers, which the reader folds into one `matrix(…)` on output (a rotation or skew is written as a `matrix`). A number is a plain decimal of at most 12 characters.
- The `d` of a path and the `points` of a polygon only hold the path commands, numbers and separators, at most 8 KiB each.
- Refused with a named reason: `<script>`, `<style>`, `<foreignObject>`, `<image>`, `<use>`, `<text>`, `<a>`, `<defs>`, `<polyline>`, gradients, patterns, clip paths, filters, masks, animation, a DOCTYPE, an entity or `&`, CDATA, a comment, a processing instruction other than the first line, any attribute not in the list above (`style`, `class`, `id`, `opacity`, `stroke-dasharray`, `on*`, `href`, `xlink:*`, `xmlns:*`), any other `xmlns` than the SVG namespace, any URL or `url(`, input over 16 KiB, a second root. A design tool's comment, `id`s and `<defs>` are the usual reasons a file is refused; the reason names the element, so the fix is to delete it.
- `currentColor` takes the text colour on the server-rendered pages and is black in an `<img>` (the back office); a logo for both light and dark uses explicit colours.

**Escaping.** `name`, titles and messages are written to HTML text with the existing `esc` (`page.rs:81-92`; the signer page imports it, `K/obop-http/src/sign_page.rs:17`), to attributes with `shell::attribute`, to JSON with `serde_json`, to the tab title with `esc`. The file name uses only the slug. The generated tile puts one validated scalar value into `<text>`, escaped. The reader re-validates every field (section 4), so a row written around the command cannot reach a page raw.

## 9. Caching

- Server-rendered pages already send `no-store` (`K/obop-http/src/oauth.rs:81`, `sign.rs:428`, `connectors.rs:128`); a change shows on the next render of that page. The brand they read comes from the reader's cache (section 4): a change shows at once in the process that made it and within two seconds in another process on the same database.
- The shell is `no-cache`; the meta tag, title and icon link are made per request from the cached brand.
- The logo route is `no-cache` with an `ETag` equal to `v`, and its URL carries `?v=<v>`, so a new logo, or a new accent under a generated tile, is a new URL and a revalidating client does not keep the old bytes. Browsers hold tab icons for a long time regardless; a changed logo may show in an old tab icon until the browser drops it (section 14).
- Cost: at most one read of the row and one of the theme setting per process per two seconds, however many page, shell or logo requests arrive; none for a request that is not an HTML document or the logo route.

## 10. Anti-phishing: what a brand setting cannot change

The consent page tells the person that the application registered itself and that the instance cannot verify who runs or made it, and shows where the result goes (`{host}`, or the phone scheme). That is the protection against a hostile client. The record may change how the page names itself, not what it says about the client. Fixed, whatever the row says:

1. The "Who is asking" box, its heading and its sentences are never read from the record. The neutral twins keep the claim ("This instance cannot verify who made it"); no field can shorten, hide or reword it. A test fails if a consent page with a brand lacks the sentence, in any language (section 13).
2. The client's name is shown as it registered, escaped, in `<strong>`, and the brand name is never put in the sentence that names the client or on a button. A client that registers a name equal to the brand looks no more trusted than before; it could register "obop" today. The host or scheme line and the "cannot verify" sentence are the defence and stay.
3. The Microsoft and passkey buttons, the names of third parties (Microsoft, Google) and the connector provider names are never replaced by the brand.
4. Only a person who holds `platform.admin` can write the record (one wrapper, section 3); every changed public field is in the security log with its old and new value, written in the same atomic batch as the change.
5. The character policy of section 2 applies on the command and again on every read: no control, format, bidirectional, zero-width or other default-ignorable character, no markup, no URL or address form in a name or title, no mixed-script name. Messages are plain text with no link markup. The logo cannot contain script, text or a reference to another resource.
6. What a message may say is the operator's business. It is shown on the instance's own pages and cannot take a visitor anywhere; the form tells the administrator that the text is readable by anyone.
7. Enrolment fails closed (section 4): the authenticator label and the passkey name are never written from a default that a read error substituted.

## 14. Migration, rollout, hosting and honest limits

**Migration.** None for an instance that sets nothing. A new model adds rows only; records are JSON documents, so there is no DDL and no data step. Backups and restores carry the row as they carry any record; a restore of a backup made before the feature leaves the row absent. A binary without the feature has no code that reads the row. `CORE_VERSION` is not changed. `docs/DEPLOY.md` gets a section when S1 lands, with the rollout order below (configure the brand before the first enrolment included), and the line for `OBOP_MFA_ISSUER` there (`docs/DEPLOY.md:73`) states the precedence.

**Rollout for MOHV.** Order matters. (1) Before the first enrolment of anyone, run `obop admin brand configure --name MOHV` (from S1; with `--hide-product-docs on` once S2 has landed), because the two-factor enrolment that D53 requires of administrators by default writes the authenticator label then, and a passkey writes its relying-party name when it is made, and neither can be corrected afterwards. (2) Choose the accent in Customize, Theme (the existing instance theme, not the record). Until a stored accent exists the generated "M" tile is the neutral slate and the sign-in screens and the back office keep the stock violet; the logo is therefore not free of obop colours until the tile rule of section 2 or a stored accent applies, and the violet UI stays until the accent is set. (3) Swapping to the real logo later is `obop admin brand configure --logo-file logo.svg`, which changes nothing else; `obop admin brand check logo.svg` says first what to remove.

The record is not the only thing MOHV sets. Still outside it: the host name, which is derived from the slug for a provisioned instance (the service name `obop-<slug>`, `K/obop-platform/src/sliplane.rs:251`) or set by `OBOP_PUBLIC_URL`, and the passkey `rp.id` that follows it; the phone app's build identity (S4); the release-feed decision of BO-26 (`OBOP_UPDATE_FEED=off` stops the call to `https://obop.dev/api/releases`, `K/obop-update/src/updater.rs:58-62` and `K/obop-update/src/release.rs:16`, but the Updates tab then shows a standing warning, `K/obop-update/src/updater.rs:315-318`, so whether to switch it off is a decision); the names chosen outside obop (OT-26: the Entra app registration, the Google OAuth client, the connector name typed in Claude); and MOHV's own manifests, Storybook sentence and image metadata (NW-01, NW-02, NW-04). Until S1 lands, `OBOP_MFA_ISSUER=MOHV` and the `site.*` keys (`obop site set`) already do part of this with no code (the audit's S0).

**Hosting and the sandbox.** The record is per instance: one database and one service per instance (`K/obop-platform/src/sliplane.rs:1-2`), and the provisioning request `InstanceSpec` has no brand field (`K/obop-platform/src/provision.rs:6-17`), so one instance cannot read or change another's brand and nothing here reaches across instances. On the hosted offerings of D83 the owner of an instance is an operator of pages on someone else's domain. The free sandbox gives each visitor a short-lived business with an administrator on a SpaceCorps address, so a visitor could put an arbitrary name, a 240-character message and a logo on the unauthenticated OAuth and signer pages of that address. D83 allows no SpaceCorps-only code path and makes abuse and rate controls, a kill switch and auto-reset duties of the sandbox; this document relies on those duties and adds no code path. Q71 asks whether the build should also have a general operator lock (an environment switch that makes `configure` and `clear` refuse, which the sandbox image or a hosted plan sets like any other setting). Default: not built in S1, decided before the sandbox opens.

**Honest limits.**

- Nothing was built or run for this document. Page texts quoted from a render come from a separate check of `main`; the "with a brand" column is design.
- That an inline SVG with presentation attributes passes a policy with `style-src` by hash follows from the policy text; it was not tried in a browser, and neither was `img-src` for a tab icon.
- Nothing was observed on a phone, and no operating-system passkey dialog was observed, so it is not known whether any platform shows `rp.name`, only the host, or both. `rp.name` is emitted only while adding a passkey. A passkey that was made before the brand is set, and that the device stored as a resident key, keeps showing the old name in the person's credential manager; only a new registration shows the new one. The statement that a client is not obliged to show the name is from the WebAuthn text as remembered, not re-fetched.
- The six translations of every neutral twin are machine-drafted and unreviewed, like the catalogue they sit in.
- Tab icons are cached by browsers for a long time; a new logo may take a while to show. Authenticator entries already enrolled keep their old label.
- `hide_product_docs` hides entry points and redirects routes; the Brand book and the Guide stay in the JavaScript bundle (`BO/src/Guide.tsx:3` imports `docs/MODULES.md` as raw text). Taking them out of the bundle needs a build flag and is not sized here.
- One artwork serves as logo and tab icon; a wide wordmark makes a poor tab icon. In dark mode a logo with `currentColor` shows black in the back office.
- Which MCP clients show `serverInfo.title` and which `serverInfo.name` was not observed; that is why both follow the record.
- The tool name `obop__meta` and the token prefix still say obop; an end user who reads a tool list or a token sees them.
- `OBOP_DEFAULT_LANGUAGE` does not reach the OAuth pages, so a Swedish instance still shows an English OAuth page unless the client sends `lang` or `Accept-Language`. Unchanged here.
- The record is public by design. The Identity form says so.
- A process caches the brand for up to two seconds, so another process on the same database may show the old name for that long after a change.
- The Unicode tables of the character policy are those of the ICU4X version in `Cargo.lock`; a character added in a later Unicode version is refused until the crate is updated. The properties named in section 2 (Default_Ignorable_Code_Point, the UTS #39 restriction level) are described from the Unicode standard as remembered, not re-fetched.
- The generated tile uses the neutral slate when the theme stores no accent, but the back office and its sign-in screens keep the stock violet until an accent is stored (section 5); whether violet counts as branding is Q71 item 6.
