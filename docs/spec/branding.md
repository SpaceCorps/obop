## 0. Summary

A customer who runs an obop instance for its own people can show them its own name, not "obop". One record, `instance_brand`, holds the name, a slug, the logo, a sign-in title per language, a sign-in message per language and (from S2) one switch. Every server-side place that shows the product name to an end user reads that record through one reader. The phone app is the one exception (section 1). An instance that sets nothing renders its pages as today, with one exception that arrives in S2: two sentences are reworded for every instance (section 12 says which slices are byte for byte identical, section 13 which outputs).

- One record, three typed commands (`get`, `configure`, `clear`) on the CLI, REST and MCP and a tab in Customize, changed only by a person who holds `platform.admin`, through one wrapper. `configure` merges the fields it is given over the stored row, with an explicit way to clear each field (sections 3 and 4).
- Stored as a record, not as environment variables, because it is a command, it has a logo, several server processes must agree and a change must be audited (section 4).
- It defers to what exists: the instance theme owns the accent, the `site.*` keys stay the explicit override of the public site, `OBOP_MFA_ISSUER` stays an explicit override of the authenticator label, and `get` shows which source won for every value (section 5).
- Server-rendered pages take the record through a reader with a two-second process cache. The back office, which must show the name before anyone has signed in, gets a small public subset injected into its page, the way `OBOP_DEFAULT_LANGUAGE` is today. Both widen what is public, which is why section 15 names the records they change and lists every public read door (sections 4 and 6).
- Five sentence families of the OAuth pages name obop, and German, Finnish and Swedish attach the name to compounds and case endings. With a brand set they switch to neutral wording that names no product, in all seven languages (section 7).
- The OAuth and signing pages keep their content security policy. The logo there is inline SVG built by the server from a strict subset, never an image or a style (section 8).
- What the record cannot touch is fixed and listed: the security statements of the consent page, the wire names, the licence and NOTICE text, any attribution (sections 10 and 11).
- Delivery is four slices, S1 to S4, sized in section 12 from one ledger (sections 6 and 6.1). S1 alone is not a customer-ready cut. Tests, including a scan that fails when a literal `obop` is added to a page that should use the record, are in section 13.

## 2. The record

One model, `instance_brand`, in the built-in module `platform` (the Customize app) beside `setting` (`K/obop-pkg/src/installer.rs:2418`) and `sso_provider` (`K/obop-pkg/src/sso.rs`). One row, id `instance`. No row means no brand.

**One predicate.** A brand is *set* when the row exists. That is the only whole-brand test. It decides the neutral wording (section 7), the icon link and the policy addition (section 8), the generated tile and the shell rewrite (section 4). Each field is then read on its own: a field that fails the read check of section 4 falls back to its default for that field, and the rest of the brand stays. A row that names `obop` is not special: it renders the name obop with the generated tile unless it carries an artwork, and nothing it holds is dropped without a word. `clear` restores the stock look.

Every field has data class `none` (the code's `DataClass::None`, "explicitly not personal data", the class `setting.value` has; CONVENTIONS 5 lists no row for it). Every field except `hide_product_docs` is public by design: pages before sign-in show it (section 4), so none may hold personal data; the field descriptions and the form say so. `hide_product_docs` is read through `get`, which only a signed-in principal can call. `<lang>` is each of `en`, `de`, `fr`, `pl`, `fi`, `sv`, `es` (`K/obop-oauth/src/page.rs:16`); a test ties the model's language fields to that list, so an eighth language is a deliberate model change.

| Field | Kind and limit | Meaning |
|---|---|---|
| `name` | text, 1 to 40 characters | The product name. Required: a row without one is not stored. Character policy below |
| `slug` | text, up to 30 | `a-z`, `0-9` and `-`, starting with a letter, no trailing `-`. Empty means derived from `name` (below). The stem of the recovery-codes file and the MCP `serverInfo.name` |
| `title_<lang>` (7) | text, up to 60 | The line beside the logo on the OAuth and signer pages, in that language. Empty means the English title, then `name`. Same character policy as `name`. The back office does not show it: its sign-in and tab show `name` (section 6) |
| `message_<lang>` (7) | text, up to 240 | One plain-text message under the heading of the sign-in screens in that language. Empty means the English message, then none. Character policy below; shown escaped, no links |
| `logo_svg` | longtext, 16 KiB in and 16 KiB canonical | The logo and the tab icon, one artwork. Input is an SVG file; what is stored is the canonical text the parser of section 8 re-wrote, never the input. Empty means the generated tile |
| `hide_product_docs` | bool (added in S2) | Hide the Brand book and the Guide in Customize, the account menu and the command palette (section 6). Nothing reads it before S2, so the field and the flag arrive with S2 |

Characters count as Unicode code points, as D90 does. There is no stored logo hash. The *version* of the logo, `v`, is the first 16 hex digits of the SHA-256 of the exact bytes the logo route serves (the stored artwork, or the generated tile drawn from the name and the resolved accent). `Reader::current` computes it, so the `ETag` and the `?v=` of the icon URL always follow what is served, also when a theme change alone alters the tile. The icon URL is `/api/brand/logo.svg?v=<v>` in every case.

No colour field: the accent stays the instance theme's (section 5). No `logo` for dark mode: one artwork, so a logo that must work on both light and dark backgrounds uses explicit colours (section 14).

**Character policy** (one allow-list for `name`, `title_<lang>` and `message_<lang>`, applied by `configure`; the reader applies only the safety subset of section 4). Text is normalised to NFC before the checks and stored in NFC. A character is allowed only if its Unicode general category is one of:

- a letter (`Lu`, `Ll`, `Lt`, `Lm`, `Lo`) whose Script_Extensions holds a real script, not only Common or Inherited. The mathematical alphanumerics (script Common, no extensions) are out; the Japanese prolonged sound mark U+30FC (category `Lm`, extensions Hiragana and Katakana, as remembered and not re-fetched) is in, so a name such as `株式会社ムーヴ` passes;
- a mark (`Mn`, `Mc`) directly after a letter or digit, for the scripts that need them;
- a decimal digit (`Nd`);
- the ASCII space U+0020 only, never leading, trailing or doubled (every other `Z` category is out, so no no-break space or ideographic space);
- punctuation: for `name` and `title_<lang>` the ASCII `- . , & ' + _ ( ) !` and nothing else (the apostrophe is the only quote mark); for `message_<lang>` any punctuation category (`P*`) and currency symbols (`Sc`).

Whatever the category, a character with the Unicode property Default_Ignorable_Code_Point is refused. That covers the zero-width characters, the soft hyphen, the variation selectors, the tag characters U+E0000 to U+E007F and the Hangul filler; the bidirectional controls and the other format characters (`Cf`), controls (`Cc`), private use (`Co`), unassigned (`Cn`) and surrogates are refused by category. `<` and `>` are not allowed in any field. `name` and `title_<lang>` start with a letter or digit.

*Forms that are refused in all three fields.* The characters `:` `/` `\` and `@` (a message would otherwise take them as punctuation); a letter or digit directly followed by `.` and a letter, a dotted form such as `shop.example` (`Inc.` followed by a space is fine); and a run of 7 or more digits of category `Nd`. This is a lint of the obvious forms of a link, an address and a phone number. It is not a guarantee: a message can still say where to go in words, and the pages do not turn text into links.

*One script.* For `name` and `title_<lang>` every letter belongs to one script, with the allowance of the Highly Restrictive level of Unicode UTS #39 (a single script, or Latin together with Han, Hiragana and Katakana, or with Han and Bopomofo, or with Han and Hangul; Common and Inherited are neutral), so a name that mixes Latin and Cyrillic letters is refused; digits and the listed punctuation are script-neutral. The rule is not applied to messages. It does not catch a whole-script look-alike (an all-Cyrillic name that reads as a Latin one), and there is no protected-name list for third parties such as the Microsoft and Google names that the pages show; both are limits (section 14).

The tables the check needs (normalisation, general category, script extensions, default-ignorable) come from the ICU4X crates `icu_normalizer` and `icu_properties`, which are already in `Cargo.lock` (`Cargo.lock:859`, `Cargo.lock:882`) next to the `icu_collator` and `icu_locale` that `obop-commands` depends on (`K/obop-commands/Cargo.toml:24-25`); their licence (Unicode-3.0) is checked against the dependency rule when they are added to `obop-brand`, and is not verified here.

**The slug.** Derived from `name` when `slug` is empty: decompose (NFKD), drop marks, lowercase, keep each run of `a-z` and `0-9` and join the runs with `-`; if the result starts with a digit, put `i-` in front; cut it to 30 characters and trim a trailing `-`. If nothing is left (a name with no Latin letters or digits, such as one in Cyrillic or Han) the slug is `instance`, so it never falls back to `obop`; two such instances share it in `serverInfo.name` and in the recovery file, and an operator who wants a readable slug sets `slug`.

**The generated tile.** With a name and no `logo_svg`, the server draws a tile: the first letter or digit of the name on a rounded square, with the contrast rule the public site already applies (`K/obop-site/src/seo.rs:56-72`; the `fill` and `on_fill` come from `theme::resolve`). The glyph is that one scalar value; it is uppercased only when the simple, one-to-one uppercase mapping gives a single scalar, so `ß` stays `ß` and does not become `SS` (the public site's own tile uses `to_uppercase()` on the first alphanumeric, `seo.rs:58-64`, which can expand). The fill is the *resolved accent*: the theme's stored accent when it is a valid `#rrggbb` other than obop's default violet `#6d3fd0` (`UI/src/theme.ts:16`, `UI/src/tokens.css:76`), else a neutral slate, `#495670` (the Slate preset, `UI/src/theme.ts:22`). That holds when the theme stores no accent and also when it stores exactly `#6d3fd0`, because the Theme tab's "Set as the default for everyone" saves the whole resolved theme, default accent included (`BO/src/Customize.tsx:249,334`, `UI/src/theme.ts:25-26`): the sign-in screens then show the theme's violet and the tile stays slate. A violet chosen on purpose is treated the same. The rollout therefore sets an explicit accent (section 14). The tile is a template of the server with one escaped glyph; it is not read by the SVG reader of section 8 (which refuses `<text>` in stored artwork) and has its own test. It is the "M" placeholder for MOHV, and no file is needed for it. Swapping to the real logo later is one flag with one file, and it changes nothing else of the row: `obop admin brand configure --logo-file logo.svg` (section 3).

## 3. Commands, who may change it, audit

Per CLAUDE.md "agentic first", every capability is a typed command on all surfaces. The shape follows `sso_provider` (`K/obop-pkg/src/sso.rs`), a one-row configuration model with `get`, `configure` and `clear`:

| Command | CLI (the built `admin` area) | REST and MCP | Effect |
|---|---|---|---|
| `instance_brand.get` | `obop admin brand status` | `/api/instance_brand/get`, tool `instance_brand__get` | Returns the stored fields, `set`, `v`, the effective values with the source of each, and `fallbacks` (the declared answer fields, below). Read group `*` (any signed-in principal), because the values are public anyway |
| `instance_brand.configure` | `obop admin brand configure [--name N] [--slug S] [--title LANG=TEXT]... [--message LANG=TEXT]... [--logo-file F or --clear-logo] [--from FILE] [--dry-run]` | `/api/instance_brand/configure`, `instance_brand__configure` | Merges the fields it is given over the stored row, validates, writes and audits in one batch. A refused value names the field and the rule, and nothing is stored. S2 adds `--hide-product-docs on or off` |
| `instance_brand.clear` | `obop admin brand clear [--dry-run]` | `/api/instance_brand/clear`, `instance_brand__clear` | Deletes the row; every surface is as today. With no row it answers `{"cleared": false}` and writes no event |
| (CLI shortcut) | `obop admin brand check FILE.svg` | the same as `configure` with `dry_run` and only `logo_svg` | Runs the SVG reader of section 8 on a file with no database, like `obop modules check FILE`, and prints the canonical text's size and `v` or every refusal with its reason. It is the same dry run, so there is no capability that only the CLI has |

**`configure` has one rule on all three surfaces.** The CLI, REST and MCP call the same function, `brand::apply`, which merges by supplied field:

- A field that is not supplied keeps its stored value. The first call needs `name`. So the one-flag logo swap `configure --logo-file logo.svg` replaces the artwork and leaves the name, titles and messages alone, and `configure --title sv=Logga in` changes one title.
- Each field has an explicit clear value. A text field (`slug`, `title_<lang>`, `message_<lang>`) is cleared by an empty string (the CLI `--title sv=` with nothing after the sign); the artwork by `logo_svg: ""` (the CLI `--clear-logo`); the switch is set by an explicit true or false (the CLI `on` or `off`). `name` cannot be cleared, only replaced; `clear` removes the row.
- `dry_run: true` (the CLI `--dry-run`) does all the checks, writes nothing, logs nothing, and answers what would happen: for `configure` the `changes` and the `refusals` (below), for `clear` whether a row would be removed. D80 asks a dry run with a digest-bound `plan_id` of a mutating command; this design has the dry run and no `plan_id`, because that is the approval path of an agent and no agent may run these commands (15.1, Q71).
- It is idempotent by construction: the same values twice change nothing and write no event. That is what the idempotency key of D80 is for, so none is added (15.1, Q71).
- `brand::apply` takes the cross-process lock `Backend::lock("brand.write")` itself (`K/obop-storage/src/lib.rs:385-389`; a lock of its own, as `auth.mfa` is, `K/obop-auth/src/lib.rs:312-315`) and does the read, the merge and the write under it. It does not rely on the dispatcher's transaction lock (`dispatcher.txn`, `K/obop-commands/src/shared.rs:17,164-174`) because the CLI path has no dispatcher, and `Backend::lock` is not re-entrant, so a second key avoids taking one key twice. Whoever calls it, the dispatcher or the CLI, two changes at once cannot lose each other.
- `--from FILE` is a CLI convenience: a TOML file of the same keys is read and sent as the fields of one call (a proposal that serves the exception of section 1). A key that is not a field of the record is refused.

**The answers are declared fields.** A key of an answer that is not a declared field of the model is withheld on every surface (`K/obop-commands/src/lib.rs:1287-1300`), so the keys of the three answers are declared on the model, as `sso_provider` declares its output-only fields `secret_set`, `break_glass` and `break_glass_enough` and its input `client_secret` (`K/obop-pkg/src/sso.rs:42-54`), and as `sign_link` declares `link`, which only the answer to `create` carries (`packages/sign.toml:258-262`). Their class is `none`, their group `*` (`ANY_GROUP`, `K/obop-commands/src/lib.rs:55`). The registry has no object or list kind (`K/obop-registry/src/lib.rs:45-81`), so a structured part is a text field that holds JSON; its shape is stated here, not in a schema.

| Declared field | Kind | Where | Content |
|---|---|---|---|
| `dry_run` | bool | input of `configure` and `clear`, echoed in the answer | Nothing was written |
| `set` | bool | `get` | A row exists |
| `v` | text | `get`, `configure` | The version of the logo |
| `effective` | text, JSON object | `get` | For each public value of the table below: `{"value": ..., "source": ...}` |
| `fallbacks` | text, JSON list | `get` | Each stored field that failed the read check: `{"field": ..., "reason": ...}` |
| `changes` | text, JSON list | `configure` | `{"field": ..., "old": ..., "new": ...}` for each changed field; the artwork as old and new `v` |
| `refusals` | text, JSON list | `configure` with `dry_run` | `{"field": ..., "rule": ...}`. Without `dry_run` a refusal is the error and carries the same list |
| `cleared` | bool | `clear` | A row was removed (with `dry_run`: would be) |

`get` also returns the stored fields as stored, except `logo_svg`; the artwork is served by the logo route. MCP and the REST body schema give a hand-registered command the generic object schema (`K/obop-mcp/src/schema.rs:368-373`), so the input keys are named in the description of each command in the catalogue (`/api/commands`, the MCP tool text), as `sso_provider.configure` does (`K/obop-pkg/src/sso.rs:22-27`). What exists for the parity of D80 is therefore: the same command names, the same input keys and the same output field names and kinds on the three surfaces, held by a test (section 13). A typed input schema does not exist for any hand-registered command and is not added here.

**What `get` shows.** The effective brand, so that an operator can see why a surface still says obop. Each public value comes with its `source`, one of `record`, `env`, `site` (a `site.*` key), `theme` or `default`:

| Value | Possible sources |
|---|---|
| `name`, `slug`, `logo` (artwork or tile) | `record`, `default` |
| `title_<lang>`, `message_<lang>` (the value after the fallback chain of section 2) | `record`, `default` |
| `authenticator_issuer` (the label and `issuer=` of a new authenticator entry) | `env` (`OBOP_MFA_ISSUER`), `record`, `default` |
| `accent` (the sign-in screens and the tile) | `theme`, `default` |
| `site.title`, `site.logo_url`, `site.accent`, favicon (the public site) | `site`, `record`, `theme`, `default` |

`fallbacks` lists the fields of a stored row that failed the read check and so fell back to the default, with the reason. With no row it returns the defaults with source `default` and `set: false`; the Identity tab and the signed-in app call it, so it must be cheap and never an error. At a terminal `status` reports the environment of the terminal's own process, which may not be the server's; REST and MCP report the server's.

**Who.** Group `platform.admin` (`K/obop-commands/src/lib.rs:52`) and a person. There is **one mechanism**: a `Dispatcher::around` wrapper on `instance_brand.configure` and `instance_brand.clear` that refuses unless `Principal::is_person()` (`K/obop-commands/src/lib.rs:101`: a user principal with no scopes), the way `sign_link.create` does (`K/obop-commands/src/sign/link.rs:52`). That is the only check that also stops a mobile app's token, because that token keeps the owner's plain id with `scopes` set (`K/obop-auth/src/lib.rs:432-447`) and so an id test such as `person_only` of `sso_provider`, which looks for a `/agent` suffix (`K/obop-pkg/src/sso.rs:102-107`), would let it through. The wrapper runs when the command really runs, after the guards and after any approval, and an approved plan runs as the principal that proposed it (`K/obop-commands/src/lib.rs:1094-1098`), so an agent's approved proposal is refused too; the commands declare no approval, so an agent gets a refusal, not a proposal. `sso_provider` is cited only for the D41 rule that a command is on every surface or on none (`K/obop-registry/src/lib.rs:949`), so `configure` and `clear` are listed in the MCP tools of a principal that holds `platform.admin` and refuse when they run. `get` has no wrapper: reading is open to any principal, an agent token included. The reason for the guard is that a name and a logo decide what a person believes they are signing in to.

**Only these commands exist.** A command exists on the REST, MCP and CLI surfaces only where a handler is bound (`Dispatcher::register` fills the command table, `K/obop-commands/src/lib.rs:679-760`), so the model is hand-registered like `sso_provider`: `get`, `configure` and `clear` and nothing else. The generated `create`, `update`, `delete`, `bulk_create` (and with it `obop import`), `list` and `search` do not exist for it; `register_crud` is not called for it (`K/obop-commands/src/store.rs:299-345`). Were a later change to bind them, each would have to be refused through the same `around` wrapper, as `sign_link` refuses `bulk_create` (`K/obop-commands/src/sign/link.rs:42-47`). A test asserts the commands are absent or refused (section 13). Because the model has no `list`, `/api/meta` and the authenticated OpenAPI document do not list it (a model appears there only with a visible `list`, `K/obop-commands/src/lib.rs:543`).

**At a terminal** `obop admin brand` acts on the database as the operator, as `obop site set` does (`crates/obop/src/main.rs:1343-1363`) and as `obop admin sso configure` does through `operator_sso_configure` (`crates/obop/src/accounts_cmd.rs:218-220`): a person with the host, not a token. It calls the same `brand::apply`, with the actor `operator`, and so takes the same lock. The back office tab (section 6) calls the three commands and nothing else, so there is no UI-only path.

**Audit.** `brand::apply` writes the row and the events in **one atomic batch** (`Backend::apply_checked`: `Op::Put` of the row, or `Op::Delete` for `clear`, and one `audit::event_op` per changed field, `K/obop-commands/src/audit.rs:74`, `K/obop-storage/src/lib.rs:38`). The entry then exists exactly when the change does. This is not the settings precedent, which writes the data first and the event afterwards and only prints a failure to stderr (`K/obop-pkg/src/installer.rs:1437-1451`, `K/obop-commands/src/audit.rs:47-58`). Each event has kind `brand_configured` or `brand_cleared`, the actor, the field name and the **old and the new value** of that field. All fields are class `none` and at most 240 characters, so the values are written as they are; the artwork is recorded as the old and new `v`, since 16 KiB does not belong in a log line. After a `clear` or an overwrite the log therefore still shows exactly what users saw. Both kinds are added to the list in the description of `security_event.kind` (`K/obop-pkg/src/installer.rs:2442-2445`), which `K/obop-http/src/audit_kind_tests.rs` holds to the code.

## 4. Where it is stored, and how each surface reads it

**Record, not environment.** The existing branding-like settings are environment variables read once at start (`OBOP_MFA_ISSUER`, `K/obop-auth/src/mfa.rs:99-101`; `OBOP_DEFAULT_LANGUAGE`, `K/obop-http/src/shell.rs:1-9`). That does not fit here: (1) an environment variable is not a command, and every surface must have one; (2) a logo of 16 KiB does not belong in an environment variable; (3) several server processes on one PostgreSQL database must agree without a restart, which a record read through a short cache gives and an environment variable cannot; (4) a change must be audited and the environment has no author. Precedent for a record read at request time exists: `Auth::security_setting` reads `obop_setting/instance` each time (`K/obop-auth/src/mfa.rs:147-151`) and `site_settings` does the same for the public side (`K/obop-commands/src/public.rs:745-757`). No new environment variable is added in S1, and `OBOP_MFA_ISSUER` and `OBOP_DEFAULT_LANGUAGE` keep working (section 5).

**Not inside `obop_setting/instance`.** That row is one JSON text that `setting.update` replaces whole for any principal that holds `platform.admin`, with no person-only check (`K/obop-pkg/src/installer.rs:2614-2626`), and its one field is class `none` with no per-field rule. The brand needs per-field validation and a person-only guard, so it is its own model. The theme stays where it is. That leaves a stated limit: `setting.update` can still change the theme accent (which joins the public subset and sets the tile fill) and the `site.*` keys for any principal that holds `platform.admin`, an agent token included, and this record does not change that (section 14).

**One reader.** `Brand` and its rules live in a new leaf crate `obop-brand` (the validation and character policy, the slug, the SVG reader, the tile, the neutral-wording switch; no I/O, as `obop-values` is a leaf crate). The reader, `obop_commands::brand::Reader`, is made once per backend at start and handed to every consumer; there is no global. The consumers, all of them: the shell (S2), the OAuth handlers, the signer door, the connector return page, `Auth` (the authenticator issuer), the two passkey context builders, the public site and shop (inside `PublicApi::site_settings`, `K/obop-commands/src/public.rs:745-757`) and, from S3, the MCP server (`initialize`, the server card, the discovery documents), the OpenAPI builder and the Slack message prefix. The Reader and `brand::apply` are the only code that reads the model (a scan, section 13). The reader has two reads.

- `current()` returns a `Brand` for display and never fails. Each field is checked against a *safety subset* of the policy, not the whole of it: its length limit, and none of a control, format, private-use, unassigned or surrogate code point, a default-ignorable one, a space other than U+0020, or `<` and `>` (the output is escaped anyway). The rest of the policy (scripts, the refused forms of section 2) is applied when `configure` writes the value, so a policy tightened in a later release never reverts a stored name. A field that fails even the safety subset (a row written by a restore, an import or an older binary) falls back to its default for that field only (`name` to `obop`, a title or message to empty) and is never rendered raw; one line is written to stderr, once per process and field, and `get` lists it under `fallbacks`. When the store read fails, `current()` returns the default brand for display and writes one line on the first failure after a success.
- `strict()` is used only where the text is written into the person's own device and cannot be corrected afterwards: the TOTP enrolment `begin` (when `OBOP_MFA_ISSUER` is not set; the environment value wins and needs no read) and the passkey *registration* options (`rp.name`, `K/obop-auth/src/passkey.rs:619`, emitted with `residentKey: preferred`, `passkey.rs:626`). Sign-in, the passkey authentication options (the sign-in ceremony emits no name, `passkey.rs:445-471`) and every other passkey route do not use it. It answers from the cache when the cache holds a successful read; otherwise it reads, and it fails when the store read fails or the stored `name` fails the safety subset. No row at all is not a failure; the default is the answer. A failure is a 503 on both enrolments and nothing is written.

The failure is `MfaError::Unavailable` with a fixed message that starts "the instance branding could not be read". `mfa_error` gives every non-transient `Unavailable` the hint "Ask the operator to set OBOP_SECRET_KEY" (`K/obop-http/src/mfa.rs:153-162`), the wrong cause here, so S1 adds an arm before it that matches that prefix, the way the transient arm above it matches on the message (`mfa.rs:154`), and answers 503 with the code `brand_unavailable` and a hint that names the branding (`obop admin brand status`). The REST passkey builder `ctx()` (`K/obop-http/src/passkeys.rs:52-68`) serves every passkey route, sign-in included, and keeps filling `rp_name` from `current()`; only the `register_options` handler (`passkeys.rs:122-130`) calls `strict()` and replaces it. A bad stored name therefore cannot lock a passkey-only administrator out of sign-in, and the administrator can still open the Identity tab to repair it.

`Brand::default()` is name `obop`, no artwork, no titles, no messages, neutral wording off, and so is any instance with no row; every consumer asks `Brand` for the name and so takes one code path with or without a row. A golden corpus of names that `configure` must keep accepting is part of the tests (section 13), so a release that tightens the character policy fails CI instead of refusing a customer's own name on its next save.

**The cache.** The reader keeps the parsed `Brand` (the row, the resolved accent read from `obop_setting/instance`, the logo bytes and `v`) in the process for at most two seconds, and **only after a successful read**. A failed read is never cached: the next caller reads again, and `strict()` never meets a default that a failure produced. A refill whose theme read failed serves the slate accent and is not cached; the theme never blocks an enrolment. The refill is not single-flight: concurrent callers at expiry may each read once, and while the store is down every caller retries (the same request fails elsewhere then). Two seconds is the bound that D67 sets for the one unauthenticated route that reads the database (`/readyz` "costs the database one ping and one read per two seconds however hard it is hit", `docs/DECISIONS.md:763`). The shell is the fallback for every unmatched path (`K/obop-http/src/lib.rs:502-516`), so scanner traffic for `/wp-login.php` or `/.env` would otherwise cost a read each. A `configure` or `clear` through this process drops its own cache at once; a theme change (`setting.update`) and a change made through another process show within two seconds. D59 (BINDING, `docs/DECISIONS.md:657`) says nothing that decides an answer lives only in one process's memory, and lets an in-memory cache follow a shared version number; this cache is a conscious deviation (15.1): a bounded copy of a database value, which the database corrects within the bound and a restart refills. A shared version number would not cover a theme change made by `setting.update`, which does not touch the brand row but changes the accent that the tile and the meta tag carry, so the time bound is used, and it covers both. The cost is at most one read of the row and one of the theme setting per process per two seconds, for any caller (section 9). Tests build the reader with a zero bound.

**Pages before sign-in.** The back office shows the sign-in, second-factor, enrolment and forced-password screens before the settings can be read, and no pre-sign-in route carries a setting today: "no other setting is public" (`K/obop-http/src/shell.rs:3-8`; `/api/meta` and `/api/commands` are routes at `K/obop-http/src/lib.rs:331-332` that answer 401 without a token, which is from the render check). The same mechanism carries the brand, and it widens what is public (section 15.1 lists the fields and the records). Today the shell rewrites the page only when `OBOP_DEFAULT_LANGUAGE` is set: with no language it returns the file service's answer untouched (`shell.rs:326-328`), and `Shell` holds no store handle (`struct Shell { files, language, limit }`, `shell.rs:269-274`). So S2 gives `Shell` the reader and makes it rewrite with or without the language variable. The two places that build a `Shell` use the same reader: `spa_with_json_api_404` (`K/obop-http/src/lib.rs:505`) and the public-site router that nests it under `--admin-prefix` (`K/obop-http/src/public.rs:86`). The reader is asked only when the answer is an HTML document (the shell's `is_html` check), so scripts, style sheets and pictures do not ask it.

- With no brand set and no language the answer is byte for byte what it is today, validators kept (tested).
- With a brand set the answer is a `200`, `no-cache`, without `ETag` and `Last-Modified`, and the request's validators are ignored, exactly as for the language tag (`shell.rs:14-22`).
- The rewrite (1) replaces the first `<title>…</title>` with the escaped `name`; (2) replaces any `<link rel="icon" …>` tag, whatever its `href` and attribute order, with `<link rel="icon" href="/api/brand/logo.svg?v=<v>" type="image/svg+xml">` (the source tag at `BO/index.html:7` has `href="/favicon.svg"`, but the Vite build prefixes the base, set by `OBOP_ADMIN_BASE` in `BO/vite.config.ts:8-10`, and the render check saw `/admin/favicon.svg` in the image shape, so a match on the source text would miss it); (3) adds `<meta name="obop-brand" content="…">` whose value is one JSON object, attribute-escaped by the existing `shell::attribute`: `name`, `slug`, `messages` (the non-empty ones), `v`, and `accent` (only when the theme stores a valid `#rrggbb`; an invalid stored value is left out) and nothing else. There are no titles in it: the back office shows `name`. The page reads it before its first render, as it reads `obop-default-language`. `hide_product_docs` is not in it; the signed-in app gets it from `instance_brand.get`.
- A shell that cannot take the rewrite on a row that exists (no `<head>`, no `<title>`, no icon link) is served as it is, and one line is written to stderr once per process, so a title that silently stays obop is not a mystery.

**The logo route.** `GET /api/brand/logo.svg` (public, like `/api/openapi.json`, `K/obop-http/src/lib.rs:333`) serves the stored canonical text or the tile and nothing else; it takes no path or id, so it is not a file server, and a query string is ignored except that it is part of the cache key of the browser. Headers: `Content-Type: image/svg+xml`, `X-Content-Type-Options: nosniff`, `Content-Security-Policy: default-src 'none'; style-src 'none'; sandbox`, `Cache-Control: no-cache`, `ETag` = `v` (an `If-None-Match` that matches answers 304). No brand set: 404 (today there is no such route).

A bare placeholder is wrong in those languages and fits the other four only by luck. ## 8. The OAuth and signing pages: policy, logo, SVG, escaping

**Policy stays.** Both pages send `default-src 'none'; style-src 'sha256-<hash of CSS>'; …` and no `img-src` (`page.rs:151-165`, `K/obop-http/src/sign_page.rs:54-58`); the hash is computed from the fixed `CSS` constant, and the passkey script is allowed by its own hash. Rules this proposal keeps: no new script, no `style=` attribute, no new rule in `CSS` (a changed `CSS` changes the hash and every page's bytes), no `<img>`. So the logo on these two pages is inline `<svg>` with presentation attributes (`width`, `height`, `viewBox`, `fill`, `stroke`, `d`), which the policy does not govern. The one addition is the icon link: when it is emitted the two policies gain `img-src 'self'`, because browsers differ in whether a tab icon is held to `img-src` and which do is not verified here. With no brand set neither the link nor the directive exists.

**Serving the logo to an unauthenticated page.** There is no file serving. The artwork is one stored value, served by one fixed route (section 4) or inlined by the server into the page it renders. The server never serves an uploaded file as it came, never follows a URL in the artwork, and never takes a path or id.

**SVG rules.** Input is parsed by a strict, hand-written reader in `obop-brand`; the stored text is a re-serialisation from the parsed values, so a parser bug can refuse or mis-read a logo but cannot store hostile markup. The subset is wide enough for a logo exported from a design tool after it has been cleaned, because the owner's "swap the real logo later with one file" depends on it, and `check` and `dry_run` (section 3) say exactly what to remove.

- Accepted: an optional `<?xml version … ?>` line (not stored); one root `<svg>` with a `viewBox` of four finite numbers (width and height are ignored, not stored); at most 128 elements in all, of these kinds: `<g>` (grouping only, nested at most 4 deep), `<path d>`, `<rect x y width height rx>`, `<circle cx cy r>`, `<ellipse cx cy rx ry>`, `<line x1 y1 x2 y2>`, `<polygon points>`.
- Attributes per element: `fill` and `stroke` as `#rgb`, `#rrggbb`, `none` or `currentColor`; `fill-rule`; `stroke-width` as a finite non-negative number; `transform` as a list of at most four `matrix(a b c d e f)`, `translate(x y)` or `scale(x y)` with finite numbers. A `transform` is kept as validated text and re-printed from the parsed numbers; it is not folded. Rotate, skew and any other function are refused (a design tool can write a rotation as a `matrix`).
- Numbers. On input a number is a plain decimal (optional sign, digits, optional fraction; no exponent) of at most 12 characters. On output every number, in attributes, `d` and `points` alike, is printed from the parsed value rounded to at most 4 decimals with trailing zeros and a trailing point dropped, and never as the raw `f64`; a number that is still longer than 12 characters after rounding refuses the file. The stored text therefore always passes the read check, which has the same rule.
- The `d` of a path and the `points` of a polygon are tokenised and re-emitted: command letters of `MmLlHhVvCcSsQqTtAaZz` and numbers (the two flags of an arc are read as flags), separated by one space, at most 8 KiB each. Anything else in them is refused.
- Limits: input over 16 KiB or canonical text over 16 KiB is refused. The canonical text is a single line made only of the bytes `A-Z a-z 0-9` and space `, . : / # ( ) = < > " -`; the property test of section 13 asserts that set.
- Refused with a named reason: `<script>`, `<style>`, `<foreignObject>`, `<image>`, `<use>`, `<text>`, `<a>`, `<defs>`, `<polyline>`, gradients, patterns, clip paths, filters, masks, animation, a DOCTYPE, an entity or `&`, CDATA, a comment, a processing instruction other than the first line, any attribute not in the list above (`style`, `class`, `id`, `opacity`, `stroke-dasharray`, `on*`, `href`, `xlink:*`, `xmlns:*`), any other `xmlns` than the SVG namespace, any URL or `url(`, a second root. A design tool's comment, `id`s and `<defs>` are the usual reasons a file is refused; the reason names the element, so the fix is to delete it.
- `currentColor` takes the text colour on the server-rendered pages and is black in an `<img>` (the back office); a logo for both light and dark uses explicit colours.

**Escaping.** `name`, titles and messages are written to HTML text with the existing `esc` (`page.rs:81-92`; the signer page imports it, `K/obop-http/src/sign_page.rs:17`), to attributes with `shell::attribute`, to JSON with `serde_json`, to the tab title with `esc`. The file name uses only the slug. The generated tile is not stored artwork: the server writes it from a template and puts one validated scalar value into its `<text>`, escaped (section 2). The reader re-checks every field (section 4), so a row written around the command cannot reach a page raw.

## 9. Caching

- Server-rendered pages already send `no-store` (`K/obop-http/src/oauth.rs:81`, `sign.rs:428`, `connectors.rs:128`); a change shows on the next render of that page. The brand they read comes from the reader's cache (section 4): a change shows at once in the process that made it and within two seconds in another process on the same database.
- The shell is `no-cache`; the meta tag, title and icon link are made per request from the cached brand.
- The logo route is `no-cache` with an `ETag` equal to `v`, and its URL carries `?v=<v>`, so a new logo, or a new accent under a generated tile, is a new URL and a revalidating client does not keep the old bytes. Browsers hold tab icons for a long time regardless; a changed logo may show in an old tab icon until the browser drops it (section 14).
- Cost: at most one read of the row and one of the theme setting per process per two seconds, for any caller and however many page, shell, logo, discovery or OpenAPI requests arrive. A request for a script, style sheet or picture does not ask the reader.

## 10. Anti-phishing: what a brand setting cannot change

The consent page tells the person that the application registered itself and that the instance cannot verify who runs or made it, and shows where the result goes (`{host}`, or the phone scheme). That is the protection against a hostile client. The record may change how the page names itself, not what it says about the client. Fixed, whatever the row says:

1. The "Who is asking" box, its heading and its sentences are never read from the record. The neutral twins keep the claim ("This instance cannot verify who made it"); no field can shorten, hide or reword it. A test fails if a consent page with a brand lacks the sentence, in any language (section 13).
2. The client's name is shown as it registered, escaped, in `<strong>`, and the brand name is never put in the sentence that names the client or on a button. A client that registers a name equal to the brand looks no more trusted than before; it could register "obop" today. The host or scheme line and the "cannot verify" sentence are the defence and stay.
3. The Microsoft and passkey buttons, the names of third parties (Microsoft, Google) and the connector provider names are never replaced by the brand.
4. Only a person who holds `platform.admin` can write the record (one wrapper, section 3); every changed public field is in the security log with its old and new value, written in the same atomic batch as the change.
5. The character policy of section 2 applies when `configure` writes: no control, format, bidirectional, zero-width or other default-ignorable character, no markup, none of the characters or forms that make a link or an address, no mixed-script name. On every read the safety subset applies (section 4). Messages are plain text with no link markup. An uploaded logo cannot contain script, text or a reference to another resource; the generated tile is the server's own template with one escaped glyph.
6. What a message may say is the operator's business. The policy keeps out the plain forms of a link, an address and a phone number (section 2); that is a lint of obvious forms, not a guarantee that a message cannot send a visitor somewhere. The text is shown escaped on the instance's own pages, with no link markup; the form tells the administrator that the text is readable by anyone.
7. Enrolment fails closed (section 4): the authenticator label and the passkey name are never written from a default that a read error substituted.

**The scans (the tests that fail when a literal `obop` is added to a page that should use the record).** *Rust, in S1.* A test `brand_scan_tests.rs` beside `addr_scan_tests.rs` and `audit_kind_tests.rs` in `K/obop-http/src`, on the reader of `src_scan.rs` (comments blanked, test-only code removed, literals kept apart from code). It reads the non-test code of a closed list that holds only files S1 changes (`obop-oauth/src/page.rs`, `obop-http/src/sign_page.rs`, `connectors.rs`, `passkeys.rs`, `oauth.rs`, `obop-auth/src/mfa.rs`) and fails on any string literal that contains `obop`, case-insensitively, that is not a row of `ALLOWED`. A row names the file, the function, the literal and the count, and a class: `default` (the one place that spells the default name, `obop_brand::DEFAULT_NAME`), `wire`, `env`, `identifier`, `admin` or `today` (one of the 35 catalogue cells that stay for an instance with no brand). A row that matches less than it says fails too. Adding `"obop"` to `page.rs` fails with the file and line; adding a sixth catalogue key that names obop fails until it has a neutral twin. A second assertion reads the neutral twins and requires that none contains `obop`. A row in `ALLOWED` is the decision that a text may name obop on every instance and is reviewed against this document. A second scan for the one reader: no code other than `brand::Reader` and `brand::apply` reads the model `instance_brand`. *Rust, extended in S3.* The list gains the files S3 changes (`mcp.rs`, `openapi.rs`, `obop-mcp/src/lib.rs`, `obop-oauth/src/lib.rs`, `obop-connectors/src/runtime.rs`, `obop-blob-gdrive/src/browse.rs`), so no pending literal ever sits on the list. S3 also adds a word scan of `obop-commands`, `obop-registry`, `obop-masking` and the mileage module that matches the word `obop` followed by a space, a point or the end of a literal; today it finds only the two URL literals of the registry, which are rows of `ALLOWED`.

*TypeScript, in S2.* `brandLiterals.test.ts` with a reader in the style of `BO/src/i18nGuard.ts` (test support, not part of the app): over the non-test `.ts` and `.tsx` of `BO/src` and `UI/src` (the `brand/` directory and `Guide.tsx` excluded, since they document obop) and the values of `BO/locales/*/messages.json`, a string literal, JSX text or catalogue value that contains `obop` must be an `ALLOWED` row (storage keys, the console prefix, admin-only keys, the default name). `Logo` may be imported only by `InstanceLogo` and the `brand/` directory.

What the scans do not see: text built at run time, text in a dependency, a Rust or TypeScript file not on the list, a name inside a longer literal that is on the list for another reason, and text in a binary asset. They make a new literal a deliberate act; they do not stop a determined workaround.

## 14. Migration, rollout, hosting and honest limits

**Migration.** None for an instance that sets nothing. A new model adds rows only; records are JSON documents, so there is no DDL and no data step. Backups and restores carry the row as they carry any record; a restore of a backup made before the feature leaves the row absent. A binary without the feature has no code that reads the row. `CORE_VERSION` is not changed (S2 bumps the `sign` package, not the core). `docs/DEPLOY.md` gets a section when S1 lands, with the rollout order below (configure the brand before the first enrolment included), and the line for `OBOP_MFA_ISSUER` there (`docs/DEPLOY.md:73`) states the precedence.

**Rollout for MOHV.** Order matters. (1) Before the first enrolment of anyone, run `obop admin brand configure --name MOHV` (from S1; with `--hide-product-docs on` once S2 has landed), because the two-factor enrolment that D53 requires of administrators by default writes the authenticator label then, and a passkey writes its relying-party name when it is made, and neither can be corrected afterwards. (2) Choose the accent in Customize, Theme (the existing instance theme, not the record), and choose one other than the default violet. Until then the generated "M" tile is already the neutral slate, while the sign-in screens and the back office keep the stock violet; pressing "Set as the default for everyone" without picking a colour stores the default violet, so the screens stay violet and the tile stays slate (section 2). (3) Swapping to the real logo later is `obop admin brand configure --logo-file logo.svg`, which changes nothing else; `obop admin brand check logo.svg` says first what to remove.

The record is not the only thing MOHV sets. Still outside it: the host name, which is derived from the slug for a provisioned instance (the service name `obop-<slug>`, `K/obop-platform/src/sliplane.rs:251`) or set by `OBOP_PUBLIC_URL`, and the passkey `rp.id` that follows it; the phone app's build identity (S4); the release feed, whose default is `https://obop.dev/api/releases` and which the operator can switch off with `OBOP_UPDATE_FEED=off` (`K/obop-update/src/updater.rs:58-62`, `K/obop-update/src/release.rs:16`, `docs/DEPLOY.md:43`) at the price of a standing warning on the Updates tab (`updater.rs:315-318`), which is the operator's own choice and no question here; the names chosen outside obop (the Entra app registration, the Google OAuth client, the connector name typed in Claude); and MOHV's own manifests, Storybook sentence and image metadata. Until S1 lands, `OBOP_MFA_ISSUER=MOHV` and the `site.*` keys (`obop site set`) already do part of this with no code (the audit's S0).

**Hosting and the sandbox.** The record is per instance: one database and one service per instance (`K/obop-platform/src/sliplane.rs:1-2`), and the provisioning request `InstanceSpec` has no brand field (`K/obop-platform/src/provision.rs:6-17`), so one instance cannot read or change another's brand and nothing here reaches across instances. On the hosted offerings of D83 the owner of an instance is an operator of pages on someone else's domain. The free sandbox gives each visitor a short-lived business with an administrator on a SpaceCorps address, so a visitor could put an arbitrary name, a 240-character message and a logo on the unauthenticated OAuth and signer pages of that address. D83 does not cover that: its nine duties (`docs/DECISIONS.md:1178`: terms, privacy notice, abuse and rate controls with a kill switch, egress and mail blocking, auto-reset, sanctions screening, cost, on-call burden, counsel review) are about the sandbox as a service, none about the content an administrator of a sandbox puts on a page, and D83 allows no SpaceCorps-only code path (`DECISIONS.md:1180`). Q71 therefore asks for a general operator lock: an environment switch (a name in the `OBOP_<AREA>_<NAME>` scheme of CONVENTIONS 2.1, chosen when it is built) that makes `configure` and `clear` refuse, which the sandbox image or a hosted plan sets like any other setting. Default: build it, not in S1, decided before the sandbox opens. Related and not solved by it: an operator cannot declare that a brand is required, so a restore from a backup made before the feature, or a `clear`, leaves enrolments carrying the label `obop` until the brand is set again.

**Honest limits.**

- Nothing was built or run for this document. Page texts quoted from a render come from a separate check of origin/main 09861505; the "with a brand" column is design.
- That an inline SVG with presentation attributes passes a policy with `style-src` by hash follows from the policy text; it was not tried in a browser, and neither was `img-src` for a tab icon.
- Nothing was observed on a phone, and no operating-system passkey dialog was observed, so it is not known whether any platform shows `rp.name`, only the host, or both. `rp.name` is emitted only while adding a passkey. A passkey that was made before the brand is set, and that the device stored as a resident key, keeps showing the old name in the person's credential manager; only a new registration shows the new one. The statement that a client is not obliged to show the name is from the WebAuthn text as remembered, not re-fetched.
- The six translations of every neutral twin are machine-drafted and unreviewed, like the catalogue they sit in.
- Tab icons are cached by browsers for a long time; a new logo may take a while to show. Authenticator entries already enrolled keep their old label.
- `hide_product_docs` hides entry points and redirects routes; the Brand book and the Guide stay in the JavaScript bundle (`BO/src/Guide.tsx:3` imports `docs/MODULES.md` as raw text). Taking them out of the bundle needs a build flag and is not sized here.
- One artwork serves as logo and tab icon; a wide wordmark makes a poor tab icon. In dark mode a logo with `currentColor` shows black in the back office.
- Which MCP clients show `serverInfo.title` and which `serverInfo.name` was not observed; that is why both follow the record.
- The tool name `obop__meta` and the token prefix still say obop; an end user who reads a tool list or a token sees them.
- `OBOP_DEFAULT_LANGUAGE` does not reach the OAuth pages, so a Swedish instance still shows an English OAuth page unless the client sends `lang` or `Accept-Language`. Unchanged here.
- The record is public by design. The Identity form says so.
- A process caches the brand for up to two seconds, so another process on the same database may show the old name for that long after a change. The refill is not single-flight, and while the store is down every request retries its read.
- The Unicode tables of the character policy are those of the ICU4X version in `Cargo.lock`; a character added in a later Unicode version is refused until the crate is updated. The properties named in section 2 (Default_Ignorable_Code_Point, Script_Extensions, the UTS #39 restriction level) are described from the Unicode standard as remembered, not re-fetched.
- The character policy cannot see a whole-script look-alike or a name that is somebody else's, and it is a lint of link, address and phone forms, not a guarantee (section 2).
- The back office and its sign-in screens keep the stock violet until an accent is stored (section 5), while the tile is already slate (section 2); whether violet counts as branding is Q71 item 6.
- `setting.update` has no person-only check and can still change the theme accent and the `site.*` keys for any principal that holds `platform.admin`, an agent token included. The person-only guard protects the record, not the values it defers to.
- A clear, or a restore from a backup made before the feature, shows the default name again, and an operator cannot declare a brand required (see Hosting).

## 15. Records and owner questions

### 15.1 Records this design amends

Written as the register asks: changing a BINDING record needs a new ADR that marks the old sentence superseded (`docs/DECISIONS.md:13`, the status table). D94 would carry these supersessions when it is entered; until then the sentences below stand and this design is not built.

- **D52 amendment of 2026-10-27** (`docs/DECISIONS.md:609`): "the instance default language is public … nothing else of the settings is public", and under *Not delivered*, "a language read from `settings.language` for the screens before sign-in (that would make a setting public)". This design makes more public before sign-in: in the meta tag, `name`, `slug`, the non-empty `messages`, the logo version `v`, and the theme `accent` when the theme stores one (the accent is a value from `obop_setting/instance`, so this is a setting in the sense of that sentence); behind the logo route, the artwork or tile. It is justified field by field: each is class `none`, not personal data and not restricted to a group, and the brand is by purpose the thing a person is shown before signing in. `shell.rs:3-8` is edited with S2.
- **D50** (BINDING; "`obop_commands::PublicApi` is the only door", `docs/DECISIONS.md:587-594`) and its amendment of 2026-11-03 (D92, the signer's page, which added one door and recorded it). After S3 an unauthenticated caller can read brand-derived values at these doors, and the list is complete. *Two new read doors:* `GET /api/brand/logo.svg` (S1) and the shell's rewrite of the back office page (S2); neither takes a bearer token, goes through `Dispatcher::call`, sets a cookie or changes state. *Existing doors that now read the record:* the OAuth pages (D64) and the signer's page (D92) and the connector return page, which show the name, logo, title and message (S1); the public site and shop, which take their title, logo and favicon fallbacks inside `PublicApi::site_settings`, the sentence at `K/obop-commands/src/public.rs:744` ("the only settings the public side reads") then being edited (S1); the discovery documents and the MCP server card, which carry the name (S3, routes `K/obop-http/src/lib.rs:362-380`); and the anonymous OpenAPI document's `info.title` (S3, `lib.rs:333`). The fields behind them are the ones above: every field except `hide_product_docs` is public, and the meta tag carries only `name`, `slug`, `messages`, `v` and `accent`. The field-by-field class-`none` rule is the justification, as D41's public-field gate states it for a package. `PublicApi` serves `[model.public]` models of packages, and a hand-registered platform model has no such declaration; routing the brand through it would need one, which is the alternative Q71 offers. Not verified beyond the routes and files cited here and the scans of section 13: that no other route renders the product name.
- **D59** (BINDING; "nothing that decides an answer lives only in one process's memory", `docs/DECISIONS.md:657`) allows an in-memory copy that follows a shared version number. The reader's cache is a conscious deviation: a copy of a database value kept for at most two seconds, the bound D67 sets for `/readyz` (`DECISIONS.md:763`), refilled from the database and corrected by it; nothing that decides an answer lives only there. Q71 asks.
- **D80** (RATIFIED; the definition of done, `docs/DECISIONS.md:1155`). Deviations, all asked in Q71: (1) no digest-bound `plan_id`, because the commands have no approval path and no agent may run them; (2) no idempotency key, because `configure` is a merge and the same values twice change nothing; (3) the dry run exists on `configure` and `clear`; (4) the typed answers are declared output fields, the structured parts being JSON in a text field, and the input has the generic schema of every hand-registered command (section 3); (5) no CLI, REST and MCP parity test exists on `main` today, so the one in section 13 is the first. Reference documentation from the registry (D38) is what the declared fields and the command descriptions give.
- **D64** (BINDING; the consent page names the client "with the statement that obop cannot verify who runs the application", `docs/DECISIONS.md:724`). With a brand set the sentence reads "This instance cannot verify who runs it" and names no product in the five families of section 7. The claim is kept word for word in meaning in every language; only the subject changes.
- **D41** (PROPOSED; a command is on every surface or on none): no change. `configure` and `clear` stay listed in MCP tools for a principal that holds `platform.admin` and refuse at run time, like `sso_provider`.
- **D65** (passkeys) states no relying-party name, so nothing in it changes; the name comes from the record instead of a literal.
- **D83** (hosting and the sandbox): no change to the record, but it does not cover the content an administrator of a sandbox puts on a page (section 14); Q71 asks for an operator lock.
- **Settings** (`setting.update`, `K/obop-pkg/src/installer.rs:2614-2626`): unchanged. It has no person-only check, so an agent token with `platform.admin` can still change the theme accent, which is public and sets the tile fill, and the `site.*` keys. A stated limit (section 14).
