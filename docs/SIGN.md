# Signing a Document through a link (sign, D92)

- **Status:** PROPOSED (D92), built in a draft pull request (PR 51, branch `feat/sign-signer`). The blob row gate it relies on is PR 50 (merged); the preview in the Documents record view is PR 52 (merged). **Nothing here is ratified, deployed or run on a live instance.** It was tested by the repository's tests (synthetic bytes, the real router) and by one manual spike in Chromium 152 (see "Manual checks"). It has not been tried in the other browsers of the matrix at the end of this page, on a phone, or behind the production proxy.
- **Scope:** how a person in staff has a Document (a PDF kept in the Documents app) signed by one other person who has no account, through a link. For the package format see [MODULES.md](MODULES.md); for signing through an outside service see [SIGN-DOCUSEAL.md](SIGN-DOCUSEAL.md); for the decision record see D92 in [DECISIONS.md](DECISIONS.md).

## What it is

A **simple electronic signature**: the signer opens a long random link, reads the PDF, types their full name, ticks "I have read and agree" and presses Sign. obop records the typed name, the time, the address and the browser the request came from, and the SHA-256 of the exact file, in one step. There is no account, no email, no cookie and no script on the signer's page.

**The link is the only authentication.** Whoever holds the link can sign with it, and the typed name is whatever they typed. The record shows that someone who held the link typed this name, ticked the box, at this time, from this address as reported by the proxy chain and with this browser. **It does not show who that person was.** It is not an advanced or a qualified signature (D39) and it carries no trusted timestamp (the time is the server clock). Whether a simple electronic signature is enough for a given contract depends on the law that governs it; ask counsel before relying on it.

## The flow

1. **Install.** `sign` 0.2.1 needs `documents` (Q65 below). See "Upgrade runbook" for an instance that has `sign` already.
2. **Make the request.** A person with `sign.user` creates a `sign_request` with a title, the requested signer's name (`signer_name`) and the Document (`document_id`). No template and no email address are needed for a request about a Document; `expires_on` is optional.
3. **Send it.** The action `send_document` (group `sign.user`; an agent can only propose it, a person approves, D18) takes the SHA-256 of the Document's file, which is its blob id. The file must be a PDF of at most 25 MiB. obop **holds an exact copy** for the request (`document_file`, a content-addressed blob), so replacing or deleting the Document's file later cannot change what was sent. The request moves to `sent`. **If the Document's file is replaced after the request was sent, signing stops** (the signer's page answers 409 "the document changed", and no new link can be made): the held copy keeps what was sent but is no longer offered, and a new request is needed. The Document cannot be deleted instead: the delete is refused for everyone, an administrator included, while any request refers to it ("still referenced by sign_request"), so the Document of an old NDA stays until its requests, and the links of those, are removed (the links, and a signed request, only by an administrator). The action `send` of the DocuSeal path is unchanged; the document flow has its own action so that a DocuSeal connection subscribed to `sign_request.send` does not fire (it would send the signer's name to DocuSeal).
4. **Create the link.** A person with `sign.manager` creates a signing link for the request (`sign_link.create`, or the button "Create signing link" on the request in the back office). Minting a link is **the same right as recording a signature**, because whoever holds the link can sign: it needs `sign.manager`, not `sign.user` (and the person who makes the link needs `documents.user` and to be allowed to see the Document, as the sender does: a person without a role in Documents is refused with "was not found, or you may not see it"). The link is shown **once** and is never stored; only a hash of it is. Hand it over yourself (obop sends no email). The link looks like `https://<your instance>/sign/<request id>/<64 hex characters>`. **To open the English page whatever the signer's browser asks for, add `?lang=en` to the link** (`.../<64 hex characters>?lang=en`; the page's hidden `lang` field carries it into the signing post). The page's language is the address's `lang`, then the browser's `Accept-Language`, then the instance default (`OBOP_DEFAULT_LANGUAGE`), then English: a signer whose browser asks for German gets the German page, and neither the instance default nor anything else on the server makes the page English without `?lang=en`. The post answers with a redirect to the same link plus `?lang=<the language of the post>`, so the "Signed" page that follows is in the language the signer signed in (an English page stays English under a German browser). A visit to the link **without** `?lang=` afterwards, from a bookmark or a mail, shows the page in the browser's language as above.
5. **The signer signs.** The page shows the request title, the requested name, the Document title, the first 16 characters of the file's SHA-256, the held PDF (the browser's own viewer, plus a link that opens it in full size) and the form. On a phone the full-size link is the way to read the whole document. One atomic step then marks the link used, marks the request `signed` with the evidence, and appends a `sign_signed` event to the security log. A second submit, with the same or another name, changes nothing. **Nothing else happens:** no event reaches connector subscriptions or automations, and nobody is notified or emailed (the first is true by construction and not pinned by a test: the door writes through the storage backend and not through the command dispatcher, so no observer sees the write; routing it through the dispatcher would change that and no test would fail); staff open the request to see that it was signed. The PDF is not modified and there is no signed copy: the held copy and the Document's file are the original, and the evidence is the request record and the log entry.
6. **Read the evidence.** `sign_request.get` shows `signed_at`, `signed_name`, `signer_ip`, `signer_user_agent`, `signature_reference`, `document_hash` and `consent_version` to a person with `sign.manager` (REST, CLI and the back office; a plain `sign.user` sees none of them). An agent token, also over MCP, is shown the personal fields masked (D40): the requested and the typed name, the address, the browser, `signer_email` and `signature_reference` (which holds the typed name); it reads the time, the consent version and the hash as they are, and never the held copy. **That hides the values from what the model reads. It is not a secrecy boundary against an agent that can write** (O37): the platform gives a mask token back as the real value when the agent sends it as a whole value, so an agent that holds a group to read a masked field and a group to write anywhere (`sign.manager` and `sign.user` do) can write a token into a plain field, a template's name or a request's title, and the real value is stored there in clear for everyone who can read that field. Give an agent that must not learn these values neither group. An agent should send only the fields it changes: a door field that holds an explicit null is shown to an agent as the text `[masked]` (O39), and sending that text back is refused, which is the safe outcome. An agent that holds the groups cannot test guesses at the personal fields either: the guard refuses a door-owned key to a caller who cannot read the field in clear, whatever the value (see "The signer's page is not a command"). **The security log is not masked:** `security_event.detail` repeats the address, the peer and the forwarded lines of the `sign_signed` and `sign_refused` entries in clear to a person, or an agent token whose scopes include `platform.admin`, who reads the log (O36). **How to tell a signature made at the door from one marked by hand:** the one reliable mark is a `sign_signed` entry in the security log whose `digest` is the SHA-256 of the evidence (the recipe is under "What is recorded"; no command or tool computes it). A door signature also has `signed_at`, `signed_name`, `signer_ip` and `consent_version`, but those fields do not prove the door: a request marked `signed` by hand (only possible for a request that is not about a Document) has no `sign_signed` entry and usually none of them, yet on 0.2.0 staff typed `signer_ip`, `signer_user_agent`, `signature_reference` and `document_hash` and an upgraded instance keeps them, and a platform administrator who is a person can type any evidence field now. The Document's related-records panel lists every request that refers to it, so two signers of one NDA are two requests.

**Several links per request are allowed.** Creating a new link does not cancel an older one: revoke an old link yourself if it may have been seen by someone it should not have been. A link is valid for 14 days by default, never longer than the end of the request's `expires_on` day, and works once.

## What staff do, and what is not logged

- **Send:** `send_document` on the draft request. **Link:** `sign_link.create`, once per hand-over. **Revoke** (needs `sign.manager` or a platform administrator; a plain `sign.user` is told "not found"): the "Revoke" button of a link, or `obop call sign_link update id=<link id> revoked_at=<the time now, for example 2026-11-04T12:00:00Z>` (with `OBOP_TOKEN`, see "Commands on the command line" below). For a person who is not a platform administrator the server replaces the time with its own and refuses a second revoke and the revoke of a link that was used. **A platform administrator who is a person is not held to that:** the value is stored as typed (so type the real time), a link can be revoked twice, a used link can be marked revoked, and `revoked_at` can be emptied, which brings a link back. The door treats any `revoked_at` that is not empty as revoked. **The back office's Revoke button sends the browser's own clock**, so for an administrator the stored time is the time on that computer, not the server's (for everyone else the server replaces it). **Emptying `revoked_at` needs the REST call with `null`** (`POST /api/sign_link/update` with `{"id": "<link id>", "revoked_at": null}`); the command line's `revoked_at=` with nothing after the sign is refused as a value that is not a time (the 'Commands on the command line' note below says how to sign in for a REST call).
- **Decline and expire cannot be undone.** No declared action leaves `declined` or `expired`, no update moves the state out of them, and a platform administrator is not an exception; a link is only made for a `sent` request: after either, the remedy is a new request, not another link. Any `sign.user` can press them (O19).
- **The security log has three kinds of entry** for this feature: `sign_link_issued`, `sign_signed` and `sign_refused`. Revoking a link, `send_document`, `decline`, `expire` and a signature marked by hand write none; the record's own history (D75) is not tracked yet.
- **What the signer reads:** the title, the `message` field, the requested name, the Document's title and the first 16 characters of its hash. The signer cannot decline on the page. A mail scanner that opens the link only views it (a view is counted against the 120 per ten minutes, so a scanner behind the signer's address uses up part of the signer's count; a view changes no request, link or evidence, and writes a `sign_refused` entry when the integrity check fails).
- **In the back office** the status bar, the kanban and the record panel offer no manual "sign" for a request about a Document: the page treats a request as one when `document_id` is set, or `document_hash` is set and `template_id` is empty. The server decides in the end, by the assertion above, which also looks at the held copy (a field the page cannot read); where the two rules differ, the server's wins. The page's rule is never stricter than the server's for a request that the server would sign (a test pins that a 0.2.0 request with a template and a typed hash is still signed by hand); it is looser only where the copy alone says the request is about a Document, which the page cannot read (an administrator cleared the Document and someone added a template), and then the server refuses a button that was offered. The generic New and Import are not offered for `sign_link`: a link is made from its request with "Create signing link". Leaving the page asks one question that names the unsaved changes and the uncopied link together. Escape acts only on the topmost dialog (the leave question over the link dialog, the command palette over that). Revoking a link asks first, with the choices "Keep it" and "Revoke".
- **Run the manual checks on the production URL:** the https origin check (O29) and the address check can only be covered there.

## What is recorded

| Where | What | Notes |
|---|---|---|
| `sign_request.document_hash` | SHA-256 of the file, lowercase hex | set at send; equals the blob id |
| `sign_request.document_file` | the held copy of the PDF | the request gives access to the copy only through the group `sign.system`, which nobody holds (an administrator satisfies every group); **while the Document still holds the same file, everyone who may read the Document can read these bytes through the Document** |
| `sign_request.signed_at` | the time of signing, UTC, server clock | |
| `sign_request.signed_name` | what the signer typed, cleaned: characters that reorder or hide text are refused, other invisible characters are removed and every run of white space becomes one space; the cleaned text is what is stored, digested and put in `signature_reference` | personal data; `signer_name` stays the name that was requested (O28) |
| `sign_request.signer_ip` | the address as reported by the proxy chain, or `unknown` | the last entry of the last `X-Forwarded-For` line behind a trusted proxy, else the peer; read as an IP address (an `ip:port` entry is read as its address); see "Settings and preflight" |
| `sign_request.signer_user_agent` | the browser, as the request named it: a byte that is not text is kept as the replacement character (U+FFFD), characters that reorder or hide text and line breaks are removed, and the text is cut to 300 characters | |
| `sign_request.signature_reference` | `typed:<name>`, the name the signer typed (not the requested one) | personal data, masked for agents like the name |
| `sign_request.sent_on`, `sign_request.signed_on` | the day, written by `send_document` and by the door | not evidence and not guarded: a person with `sign.user` can set them (O34); the evidence is `signed_at` and the log entry |
| `sign_request.consent_version` | the id of the consent wording, the language of the post (its form's, else the address's, else the browser's, else the instance's) and a hash of the words, for example `v1-draft/en/a05c68c3` | the wording is a draft; the language is not proof of the page shown; see "The consent wording and its id" |
| `sign_link` | the link's hash as its id, the request, the expiry, when it was used or revoked | the link itself is never stored |
| security log | `sign_link_issued`: who made the link, the first 12 characters of the link's id, when it ends, the first 16 characters of the document hash. `sign_signed`: the request, the link's first 12 characters, the document hash, the consent id, **a digest of the evidence**, the address, the peer address and the `X-Forwarded-For` lines it received (a line that is not text is shown with replacement characters, a `\|` the client wrote is shown as `/`, the lines are joined with ` \| `, and a text over 200 characters loses its beginning, so the proxy's own entry, the last, is kept); the typed name, the browser and the exact time are inside the digest and are not readable in the entry. `sign_refused`: written only when the door refuses a known link for one of these reasons: no held copy, held copy missing, Document gone, document changed, stale form, held copy tampered with, or a post on a link that is over; at most one entry per link and reason in ten minutes. A view of an expired or revoked link, a bad name, a missing tick and a rate-limit refusal write nothing | never the link; unknown links are counted and not logged |

The typed name, the address and the browser are **personal data**. They are kept with the request, and the address, the peer address and the forwarded header are also in the security log (`security_event`, which no command changes or erases). obop has no generic erasure tool for any of it yet and no automatic expiry (Q68). The `sign_signed` entry is written by the door in the same step as the signature. The security log has only read commands (get, list, search), so no caller can write or change an entry through a command; the entries come from server code paths (the signer door, link creation, administration, sign-in). That is a property of the command surface: nothing in the database stops someone who can write the database, and the digest is an unkeyed SHA-256 of fields stored next to it.

**The digest.** `digest` in a `sign_signed` entry is the lowercase hex SHA-256 of nine lines, each `key=value` followed by a line feed, in the alphabetical order of the keys: `consent_version`, `document_hash`, `link_id` (the full id of the `sign_link` that was used; the entry shows its first 12 characters), `request_id`, `signature_reference`, `signed_at`, `signed_name`, `signer_ip`, `signer_user_agent`, with the values stored on the request. No command, tool or page computes it; a developer can (`digest_of_request` in `obop-commands`, which the tests use). A request whose evidence was changed afterwards no longer hashes to the entry, but nothing in this draft checks that for you.

## What it does not do

- **It does not prove who signed.** See above. The page names the person the request is for and the consent sentence says "I am <that name>", but nothing checks it.
- **It is not tamper-proof and it does not claim to be.** After signing, the wrappers refuse the door-owned fields, and update and delete of a signed request, for everyone but a platform administrator (see D92); a platform administrator or anyone with database access can change anything, the log entry included. What exists is a log entry written at signing with a digest of the evidence. Nothing in this draft reads that digest back and says "matches"; do not describe the record as tamper-proof or as tamper-evident.
- **The address is only as good as the proxy.** Behind a trusted proxy `signer_ip` is the **last entry of the last `X-Forwarded-For` line**: a proxy that extends the client's line or adds its own line writes its entry last, and what precedes it is what the client sent. If the instance is reachable without the proxy, or the proxy does not append the address it saw, the value is chosen by whoever sends the request. An `ip:port` or `[ipv6]:port` entry is read as its address. The line is read lossily, so bytes that are not text in what the client sent before the proxy's entry do not hide that entry. When the last entry cannot be used (it is empty or not an address) the peer's address is used, as if there had been no header; behind a proxy that peer is the proxy, so the evidence then holds the proxy's address (`unknown` only where there is no socket at all). A signer therefore cannot blank the address or pick a rate-limit bucket by what they write **before** the proxy's entry. If the proxy itself writes nothing usable the address is the proxy's, the log line shows it (`address` equal to `peer`) and the evidence carries no marker for it: the proxy is what to check (step 3 of the preflight). The same rule, one function, serves the OAuth pages, passkeys, Microsoft sign-in and the public site. The audit event carries the peer address and the `X-Forwarded-For` lines it received next to the recorded value (see the table for how they are cleaned and cut), so the evidence can be reviewed.
- **Approval is of the request, not of the bytes.** An agent-proposed send runs on whatever file is attached when a person approves it. The evidence records the exact bytes that were sent.
- **Staff who see the link can sign in the signer's name.** The address and browser make it visible, not impossible.
- **A request about a restricted Document is listable.** `sign_request` has no row-level access of its own, so every person with `sign.user` can list requests (title, requested name) even for a restricted Document. The Document and its bytes stay restricted (PR 0, the blob row gate).
- **Who is refused a link.** `sign_link.create` refuses agent tokens, scoped tokens and the tokens of mobile apps ("a signing link is a secret; ask a person to create it") and it is listed on MCP. A user's own session token used from MCP, the CLI or a script is **not** refused: do not say "agents never get links", say "an agent token cannot create one". It does not count as MCP parity.
- **No email, no copy for the signer, no drawn signature, no evidence page, no pdf.js.** The signer gets nothing from obop after signing (Q69): the page says the document was signed and the PDF route stops. There is no signed copy and no export of the evidence; what staff can hand over is the original PDF and a note they write from the request (the typed name, the time in UTC, the address, the file's SHA-256 and the consent version). The page works from typed names only; a drawn signature is a later, additive field.

## The signer's page is not a command

Every capability of obop is a typed command on the CLI, REST and MCP. The signer's act is the one exemption D92 asks the owner to accept (Q66): `GET` and `POST /sign/<request>/<token>` and `GET /sign/<request>/<token>/document.pdf` are server-rendered public routes, like the OAuth pages and the payment webhooks, and every state change behind them is one typed, audited operation with one security event. **For a request about a Document no command signs for someone:** the action `sign` is refused while the request names a Document, holds the copy that was taken when it was sent, or holds a hash and has no template (the manual action stays for the requests that are none of these, which the by-hand and DocuSeal flows use, among them a request made from a template whose hash staff typed on 0.2.0), and so is an update that sets `state` to `signed`, which runs the same action first. Taking the Document off a request does not unlock it: once a request has left draft only a platform administrator can change, clear or add its `document_id`, whichever way it was sent, and for a request sent with `send_document` the hash and the copy stay besides (a template added to the request does not change that). A request that names a template and a Document and was sent with the old `send` (O32) holds no hash and no copy, so it can never get a link; while it names its Document it is refused the manual action too, and only an administrator can clear the Document, which makes it an ordinary template request that is signed by hand. **This refusal is an assertion of the package version 0.2.1**, not of the binary: on 0.2.0, or after a rollback to it, the manual action works for such a request (the guards on the evidence fields act from the binary). A platform administrator who is a person can still write the evidence fields of any request and change or delete a signed one: that is a rule against mistakes and against staff without the role, not against an administrator or the database. **The rule for the door-owned fields** (`document_hash`, `document_file`, `signed_at`, `signed_name`, `consent_version`, `signer_ip`, `signer_user_agent`, `signature_reference`): a caller who cannot read a field in clear (it does not hold the field's group, or it is an agent token that is shown the field as a mask token) is refused for that key whatever the value, so that a right guess is not answered differently from a wrong one; a caller who can read it may send back the value it was shown, unchanged, in an update, or an empty value in a new row (a form saves the whole record), and any other value is refused; the held copy `document_file` has a group that nobody holds, so only the door and a platform administrator who is a person may write it (a file id that the caller may not read is refused earlier, by the guard on files, with the answer for a file that does not exist). The door and a platform administrator who is a person are not held to this. An agent token is never an administrator for these guards, even when its scopes include `platform.admin`; it gets the guards of any agent. **What the guards do not cover:** they act in the command layer, so an action of another module that updates `sign_request` through its effects is not checked by them (no bundled package does that; O35). **A refused `update` that moves the state has already moved it:** `update {state: "declined", signed_name: ...}` is answered 400 and the request is declined (O33). The routes are not on `/api`, set no cookie and are refused as an admin prefix; every answer the door makes itself (the pages, the refusals, the PDF and the redirect after signing) carries `X-Robots-Tag: noindex, nofollow`, and the pages also a meta tag (the framework's own refusals for a wrong method, a body that is too large or a bad path encoding carry none of our headers); `robots.txt` disallows `/sign/` only when the instance runs with `--public-site` (the published image does). If the model `sign_link` is not registered (the package is not upgraded, or was rolled back) all three routes answer 404.

## Settings and preflight

Before a link goes to a real person:

1. **`OBOP_PUBLIC_URL`** is set to the external address (`https://acme.example.com`). The signer's POST is accepted only from the page's own origin; behind a TLS-terminating proxy that does not send `X-Forwarded-Proto` the derived address is wrong and every signing attempt would be refused. The link shown to staff also starts with this address.
2. **`OBOP_TRUST_PROXY=1`** (or `--trust-proxy`; the published image sets it), so that the address in the evidence is the client's and not the proxy's, and the rate limits count per client. Never set it on an instance that is reachable without the proxy.
3. **Check the recorded address on the real deployment**, with a throwaway request about a made-up PDF (never the real NDA): send it and make a link as usual, then post the form yourself with **two forged lines**, for example `curl -i -H 'Origin: https://<your instance>' -H 'X-Forwarded-For: 203.0.113.9' -H 'X-Forwarded-For: 203.0.113.10' --data-urlencode 'name=Test Person' --data 'agree=1' --data 'lang=en' --data 'doc=<the request's document_hash>' https://<your instance>/sign/<request id>/<token>` (the answer is a 303), and read `signer_ip` of that request. It must be the address your proxy saw (your own), neither `203.0.113.9` nor `203.0.113.10`. Read `consent_version` too: it must be `v1-draft/en/` and eight hex digits. The `sign_signed` entry in the security log shows the address, the peer and the `X-Forwarded-For` lines it received (cleaned, and cut at their beginning when over 200 characters). A proxy that appends its entry to the last line and one that adds a line of its own both pass (the last entry of the last line counts). **A proxy that edits only the first `X-Forwarded-For` line, or replaces the first and leaves the others as the client sent them, fails this check** (the second forged line is then the last one and is what is stored); a single forged line would not show it. If the stored address is one of the forged ones, the evidence has no value. A signed request cannot be reopened: do this on a request you do not need. The published image starts with `--public-site --trust-proxy`, and the Sliplane provisioner passes no command of its own, so an instance it makes trusts `X-Forwarded-For`; it sets no `OBOP_PUBLIC_URL` either, so set that yourself (step 1) or, when the proxy does not send `X-Forwarded-Proto`, every signing attempt is refused. Confirm what your instance runs with.
4. **No DocuSeal connection lists `sign_request.send`** in its events, or you accept that it fires for requests that use `send` (the document flow's `send_document` does not fire it).
5. **Proxy access logs contain the link** (it is in the path). Keep them as private as the link itself.

Rate limits count through the shared store and fail open if it is unavailable (the 256-bit link is the defence, not the limiter). **Per source** (the address; the peer's when the address cannot be read), in windows of **ten minutes**: 20 failed lookups, 120 views (the page and the PDF share one count) and 10 signing posts. **Per link**, in one **hour**: 10 signing posts, refused tries included, so ten bad tries (a name that is too short, a missing tick) lock that link for an hour and the fix is a new link. **Per person**, in one hour: 20 attempts to make a link (a refused try counts: twenty tries against a draft request lock that person out of link creation for an hour). A valid link is never refused for the number of failures from its source. The limits need a correct `OBOP_TRUST_PROXY` to count per client. The "busy" page says "wait a minute" whatever the wait; the `Retry-After` header has the real number of seconds.

## Upgrade runbook (an instance that has sign 0.2.0)

**Commands on the command line.** `obop` reads the database from `OBOP_DATABASE_URL` (or `--db URL`, before the command). `obop call ...` also needs a token in `OBOP_TOKEN` (or `--token TOKEN`) and stops with "no valid token" without one: a person's session token where a person is required (making a link, the administrator's revoke), since `obop agent-token` makes an agent token, which cannot make a link. **Get that token** from the sign-in call of the REST API: `POST /api/auth/login` with `{"username": "...", "password": "..."}` answers `{"token": "..."}`; for a person with a second factor (an administrator by default, D53) it answers `{"mfa_required": true, "mfa_token": "..."}` instead, and `POST /api/auth/login/mfa` with that `mfa_token` and the `code` answers the token. An administrator who has **not enrolled** a second factor gets `{"token": "...", "mfa_enrolment_required": true}` instead (on an instance with `OBOP_SECRET_KEY` set, which the Sliplane provisioner does): that token can only enrol (enrol in the back office, or `POST /api/auth/mfa/begin` and `/api/auth/mfa/confirm`), and `obop call` with it answers only `Forbidden`. A code works once, so after enrolling wait for the next 30 seconds before `login/mfa`. **Make the link with the address in it:** `obop call sign_link create ...` prints only the path `/sign/<request id>/<64 hex characters>` unless `OBOP_PUBLIC_URL` is set in the environment of that command (the same variable as the server's); with it the answer starts with `https://<your instance>`. `obop backup run` needs a place for the file, `--out DIR` or `OBOP_BACKUP_DIR`, and writes an **unencrypted** backup unless `OBOP_BACKUP_KEY` (or `OBOP_SECRET_KEY`) is set; this feature's backups hold the signer's name and address, so set a key. The key is 64 hexadecimal digits (`openssl rand -hex 32`). **Keep it in a place that is not the backup's volume and in at least two places: every backup sealed with it is unreadable without it, and there is no recovery** (docs/DEPLOY.md, "Backups", "Which key" and the table that follows it).

**Deploying the new binary already changes `sign` 0.2.0.** The new model is not installed and the three routes answer 404, but the wrappers of D92 act on the old package from the first start: a person without `platform.admin` can no longer type `document_hash`, `signer_ip`, `signer_user_agent` or `signature_reference` on a request (in 0.2.0 a field group restricted reading only, so staff could), can no longer change or delete a request that is `signed`, and `sign_request.send` refuses a request that has no template. A person in the middle of the manual by-hand workflow is refused with "written by the signing process" or "a signed request cannot be changed or deleted; ask an administrator". The blob row gate (PR 50) is active at once too. A request created before otherwise keeps working.

1. Read the installed version of `documents` (Customize, Modules). The bundled `sign` 0.2.1 needs `documents` 0.3 or later, below 1. An instance without `documents` gets it installed by the upgrade with nobody in its groups but administrators: give the staff who send and make links `documents.user` (and `documents.manager` for restricted Documents they do not own) before they try, or `send_document` and link creation answer "was not found, or you may not see it".
2. **Take a backup first:** `OBOP_BACKUP_DIR=<dir> OBOP_BACKUP_KEY=<key> obop backup run` (a database URL in `OBOP_DATABASE_URL`). An additive module update takes no automatic backup (docs/DEPLOY.md, "Migration gates").
3. `obop modules plan sign` and read it. Expected: the model `sign_link` added, five optional fields added to `sign_request`, a new dependency on `documents` (already installed), one action added to `sign_request` (`send_document`) and no data migration. The plan lists added and removed actions only: it does not show that `template_id` and `signer_email` are no longer required, nor the new assertion on the action `sign` (below), nor that `signature_reference` changes class (from none to internal, as personal data): from the upgrade on, an agent token reads the typed name inside the `signature_reference` of old requests as a mask token.
4. `obop modules update sign` (an administrator; an agent can only propose it). Old requests and templates keep working; the new fields are empty.
5. Set the settings above and run the browser checks below.

**The manual action.** From 0.2.1 the action `sign` is refused for a request about a Document (an assertion on the action): such a request is signed only at the door. Requests without a Document (templates, DocuSeal) are signed by hand as before.

**Rollback** (`obop modules rollback sign`) keeps the data and returns to 0.2.0. Requests about a Document then lack the `template_id` and `signer_email` that 0.2.0 requires, so `sign`, `decline` and `expire` all refuse them (the first missing field is named) and **staff cannot close a sent document request** until **both** fields are set on it: first `template_id` (any template: `obop call sign_request update id=<request id> template_id=<template id>`), then `signer_email` (any address; no mail is sent), after which `decline` or `expire` goes through (a test runs exactly these steps: the two updates as a plain `sign.user`, `sign`, `decline` and `expire` as a person who also holds `sign.manager`; `decline` and `expire` need only `sign.user`, `sign` needs `sign.manager`). Any person with `sign.user` can set the two fields, and an agent token with that group can too, so no administrator is needed **as long as a template exists** to name: making one needs `sign.manager`, so an instance that never had a template needs one person with that group once. That the fields are open to `sign.user` is also what makes the by-hand signature possible after a rollback. **0.2.0 has no assertion on `sign`:** with both fields set, `sign` marks a document request signed by hand with no evidence, so a rollback also removes the refusal of the manual signature (the guards on the evidence fields stay, they are in the binary). Their held copies stay as orphaned data; every `/sign` link answers 404. An older binary against the upgraded package sees `sign_link` as a generic model: inert rows and no route.

## A link is lost or may have leaked

The link is not stored and cannot be shown again. **Create another link** for the same request (the button on the request, or `obop call sign_link create ...`) and hand over the new one. If the old one may have been seen by someone it should not have been, **revoke it** as well (the button "Revoke" in the request's list of signing links, or `obop call sign_link update id=<link id> revoked_at=<the time now>`: for a person who is not a platform administrator the server replaces the time with its own and a link that was used cannot be revoked; an administrator who is a person writes the time as typed and is not refused for a used link, see "What staff do"). A used link cannot be used again: a second submit shows "already signed" and changes nothing. A request moved to `declined` or `expired` kills its links at once.

## Manual checks before a real signer is sent a link

Only one browser was tried, and only by the author. **Spike of 2026-11-03** (a made-up one-page PDF served by a throwaway local server, Chromium 152 in the Claude desktop app's browser pane, which has Chromium's PDF viewer): the PDF showed in `<object type="application/pdf">` when the page's content security policy had **`frame-src 'self'`** (and `child-src 'self'`), and when the PDF response carried any of `frame-ancestors 'self'` alone, `default-src 'none'; frame-ancestors 'self'`, no policy at all, or even `sandbox`. **Without `frame-src` the page's `default-src 'none'` blocks the viewer** ("Framing ... violates default-src 'none'. 'frame-src' was not explicitly set"): the box stayed empty and only the fallback text and the full-size link showed. So the page's policy must name `frame-src 'self'`, and the PDF response's policy must never contain `sandbox` even though this Chromium tolerated it (other engines were not tried). The viewer filled in a second or two after the page. Not tried: Firefox, Edge, desktop Safari, an iPhone, an Android phone, the production proxy. Twenty minutes with a **made-up PDF**: Chrome, Edge, Firefox, desktop Safari, an iPhone and an Android phone. On desktop the PDF shows in the page; on both phones the full-size link opens all pages; clicking an external link inside the test PDF does not send the signing address as the referrer; the form submits and the "Signed" page shows. If a desktop browser shows an empty box, the full-size link still works; the constant `INLINE_PDF_CSP` already is `frame-ancestors 'self'` alone, so there is nothing to loosen there. The next candidates, in this order, are the other headers of the PDF response: `Cross-Origin-Resource-Policy: same-origin`, then `X-Frame-Options: SAMEORIGIN`, then the policy itself (dropping it widens the exposure: the PDF is served from the same origin as the back office and the API, so a script-running flaw in a viewer would run next to the back office's stored session; the spike showed that `default-src 'none'; frame-ancestors 'self'` also rendered in Chromium 152, which is the narrower value to try for the first live use). The first live use must use the English page, the only original (add `?lang=en` to the link, see step 4: the browser's language otherwise wins); any other language, German included, is machine-drafted and should be read by someone who knows it before a signer gets it.

## The consent wording and its id

The consent sentence (`consent`, id `v1-draft`) and the notice of what is recorded are **a draft for counsel, not legal advice**. The English text is the only original; German, French, Polish, Finnish, Swedish and Spanish (page and package labels) are **machine-drafted and not reviewed by a native speaker**, German included. Who confirms the wording is Q67. **One gap for counsel:** the notice the signer reads (the text `records`) names the typed name, the date and time, the network address, the browser and the document's fingerprint; it does not mention the peer address and the `X-Forwarded-For` lines that the security log keeps beside the address (outside the digest, readable by anyone who reads the log). Counsel should say whether the notice must; decide it before the NDA goes out, because a change of the wording moves the consent id.

**What the stored id covers.** Each signature stores `consent_version` in three parts, for example `v1-draft/en/a05c68c3`: the id of the wording (the constant `CONSENT_VERSION` in `sign_text.rs`), the language, and eight hexadecimal digits that the code **derives from the words**: the first four bytes of the SHA-256 over `key`, a line feed, the text of that key in that language, a line feed, for each of eight texts in this order, the catalogue texts as they are, placeholders included: `consent`, `records`, `name_hint`, `submit` (the label of the button, which the consent sentence names), `no_viewer`, `err_agree`, `for` and `fingerprint` (a language without its own text for a key counts as English there). The id therefore moves whenever any of the eight moves, and pasting a hash cannot make an edited text keep its id. A unit test (`the_wording_the_signer_agrees_to_is_pinned_to_its_id`) also holds the seven full ids as literals, so an edit fails it until they are changed in the same commit, which shows in the diff; further tests check that editing each covered text in one language moves that language's id and nothing else. Texts outside the eight (the title, the refusal and "Signed" pages) are not covered and may change without moving the id. The part before the first slash is a constant a reviewer changes: **an id that a real signature carries is never reused for other words**, and when counsel confirms the English text the constant becomes `v1`.

**The language part is the client's.** The id's language is resolved the way a page's language is: the `lang` field of the signer's POST when it is one of the seven; when the post has no `lang` field at all, the `lang` of the post's address (the link's `?lang=`); otherwise (a `lang` field that is present but empty or not one of the seven does not fall back to the address) the browser's `Accept-Language`, then the instance default (`OBOP_DEFAULT_LANGUAGE`), then `en`. It is not a record of the page that was shown: a client can read the English page and post `lang=de`, and the evidence then says `v1-draft/de/...`; and a post whose `lang` is nonsense is recorded in the browser's language, not necessarily `en`. The hash part is the server's. **The id is worked out when the form is posted**, from the texts the running image holds for the post's language; the page does not carry it, and the form carries only `doc` (the fingerprint the signer saw) and `lang`. If the image is replaced between the moment the signer opened the page and the moment they post, the stored id is that of the new image's wording, not of the page that was read (`doc` guards the file, nothing guards the wording): do not deploy a change of those eight texts while a real link is out. **What to keep for a stored id.** The id is a hash of words and cannot be turned back into them. For the real NDA keep, with the signature (a line in the hand-over note), the **image tag or the commit** that was deployed when the link was sent and the signature made, and the texts themselves at that commit: the catalogue in `crates/kernel/obop-http/src/sign_text.rs` (the eight keys above, in the language of the id) and the unit test that holds the seven full ids. With them the exact page can be rebuilt and the id recomputed; the stored id and the test only narrow it down, they do not replace the commit.

## Known limits (not fixed in this draft)

Each is a row in docs/ISSUES.md, section O, with its fix.

- **Any `sign.user` can end or reword a sent request.** `decline` and `expire` are open to the model's write group, so a plain user can close someone else's sent request (its links stop at once); a plain user can also change the title, message and requested name that the signer reads (the Document of a request that has left draft is fixed for everyone but an administrator), and can delete a draft, sent, declined or expired request that has no link (one that has a link is refused by the reference check until an administrator deletes its links; a signed request is an administrator's). The signed hash stays bound to the file; the wording the signer saw is not part of the digest (O19).
- **The Document's id and its file's SHA-256 are visible through `sign_request`**, the id to `sign.user` and `sign.manager`, the SHA-256 to `sign.manager`, also for a restricted Document they cannot open; the bytes stay locked by the blob row gate (O20).
- **Staff changes and the door's write are not serialised.** The door's batch checks its conditions at commit; a `decline`, `expire` or `update` by staff reads and then writes without one, so a stale write can land on a request that was just signed. It was reproduced, with threads released together on one machine (measurements, not rates to rely on): 16 simultaneous posts over two links against three simultaneous `decline` calls ended `declined` while holding the evidence and one `sign_signed` entry in 4 of 6 trials, and in 3 of 6 and 3 of 4 in two later runs; one post against three declines in 4 of 28 trials; one post against one decline in 3 of 30. In each of those the post that won was answered 303 and the link then answers "closed". One signer clicking once is not safe from a staff `decline` or `expire` that lands in the same instant. **No command moves a request out of `declined` or `expired`, an administrator's included** (the state rule has no exception, and `sign`, `send`, `send_document` and `expire` all refuse): the signature stays recorded on the request and in the log, the remedy is a new request, and putting the state back means editing the database (O21).
- **A page view reads no bytes.** The fingerprint on the page is the one recorded on the request, not one computed from the file; the page checks ids and sizes only. The PDF route hashes the held copy again before it serves it, and so does the post, so a copy that was changed in the store is refused with a `sign_refused` entry (reason `tampered`) at the download and at the post rather than shown (O31).
- **Expiry edges.** The end of a link is checked before the PDF is read and the signing time is taken after, so a signature can land by that processing time after the end; a clock before 1970 means nothing expires; the day in `expires_on` ends at 23:59:59 **UTC** whatever the instance's time zone (O22).
- **The log line carries text from the client** (the peer and the forwarded header, outside the digest); semicolons are replaced so that they cannot start a second field (O23).
- **A wrong approver burns an agent's proposal.** A person who cannot see the Document and approves an agent's `send_document` makes it fail, and the right approver then gets a 404 (O24).
- **Leaving the page with an unkept link (the back office).** Leaving the page is guarded for route changes and, while the link is unkept, for reload and tab close. The guard does not cover signing out, switching account or any unmount that is not a route change. Browsers show only their own generic prompt on reload and tab close, and only after the person has interacted with the page. "Kept" means the link was copied to the clipboard once; it does not prove it was pasted, and a later clipboard overwrite loses it. If the person confirms leaving while the server is still making the link, that link is orphaned; a toast says so and it can be revoked. If the server's answer to making a link is not one this page can show, the person is told that a link was made, that nobody has it, and that it is to be revoked in the Signing links table. Partial or caret copy, and a real reload prompt, were tested only in jsdom or with a synthetic event, not in a real browser.
- **Masking is not a secrecy boundary against an agent that can write (O37).** See "Read the evidence": an agent token can write a mask token it was shown back into a plain field and read the real value there.
- **A stalled request body is never timed out (O38).** The server has no read timeout for a body that does not arrive; the signer routes are open to the world, so the proxy in front must end such a connection.
- **Guards that are not there (O33 to O36).** A refused `update` that moves the state has already moved it; `sent_on` and `signed_on` are not guarded; the guards do not cover the action effects of another module; the security log is not masked.
- **Names:** look-alike letters (Cyrillic), fullwidth angle brackets and up to about a hundred combining marks are accepted in a typed name; the joiners U+200C and U+200D are kept (some names need them); the typed name is never compared with the requested name (O8, O28).
