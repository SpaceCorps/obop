# Signing a Document through a link (sign, D92)

- **Status:** PROPOSED (D92), built in a draft pull request (PR 51, branch `feat/sign-signer`). The blob row gate it relies on is PR 50 (merged); the preview in the Documents record view is PR 52 (a separate draft). **Nothing here is ratified, deployed or run on a live instance.** It was tested by the repository's tests (synthetic bytes, the real router) and by one manual spike in Chromium 152 (see "Manual checks"). It has not been tried in the other browsers of the matrix at the end of this page, on a phone, or behind the production proxy.
- **Scope:** how a person in staff has a Document (a PDF kept in the Documents app) signed by one other person who has no account, through a link. For the package format see [MODULES.md](MODULES.md); for signing through an outside service see [SIGN-DOCUSEAL.md](SIGN-DOCUSEAL.md); for the decision record see D92 in [DECISIONS.md](DECISIONS.md).

## What it is

A **simple electronic signature**: the signer opens a long random link, reads the PDF, types their full name, ticks "I have read and agree" and presses Sign. obop records the typed name, the time, the address and the browser the request came from, and the SHA-256 of the exact file, in one step. There is no account, no email, no cookie and no script on the signer's page.

**The link is the only authentication.** Whoever holds the link can sign with it, and the typed name is whatever they typed. The record shows that someone who held the link typed this name, ticked the box, at this time, from this address as reported by the proxy chain and with this browser. **It does not show who that person was.** It is not an advanced or a qualified signature (D39) and it carries no trusted timestamp (the time is the server clock). Whether a simple electronic signature is enough for a given contract depends on the law that governs it; ask counsel before relying on it.

## The flow

1. **Install.** `sign` 0.2.1 needs `documents` (Q65 below). See "Upgrade runbook" for an instance that has `sign` already.
2. **Make the request.** A person with `sign.user` creates a `sign_request` with a title, the requested signer's name (`signer_name`) and the Document (`document_id`). No template and no email address are needed for a request about a Document; `expires_on` is optional.
3. **Send it.** The action `send_document` (group `sign.user`; an agent can only propose it, a person approves, D18) takes the SHA-256 of the Document's file, which is its blob id. The file must be a PDF of at most 25 MiB. obop **holds an exact copy** for the request (`document_file`, a content-addressed blob), so replacing or deleting the Document's file later cannot change what was sent. The request moves to `sent`. **If the Document's file is replaced, or the Document is deleted, after the request was sent, signing stops** (the signer's page answers 409 "the document changed", and no new link can be made): the held copy keeps what was sent but is no longer offered, and a new request is needed. The action `send` of the DocuSeal path is unchanged; the document flow has its own action so that a DocuSeal connection subscribed to `sign_request.send` does not fire (it would send the signer's name to DocuSeal).
4. **Create the link.** A person with `sign.manager` creates a signing link for the request (`sign_link.create`, or the button "Create signing link" on the request in the back office). Minting a link is **the same right as recording a signature**, because whoever holds the link can sign: it needs `sign.manager`, not `sign.user` (and the sender needs `documents.user` and to be allowed to see the Document: a person without a role in Documents is refused with "was not found, or you may not see it"). The link is shown **once** and is never stored; only a hash of it is. Hand it over yourself (obop sends no email). The link looks like `https://<your instance>/sign/<request id>/<64 hex characters>`.
5. **The signer signs.** The page shows the request title, the requested name, the Document title, the first 16 characters of the file's SHA-256, the held PDF (the browser's own viewer, plus a link that opens it in full size) and the form. On a phone the full-size link is the way to read the whole document. One atomic step then marks the link used, marks the request `signed` with the evidence, and appends a `sign_signed` event to the security log. A second submit, with the same or another name, changes nothing. **Nothing else happens:** no event reaches connector subscriptions or automations, and nobody is notified or emailed; staff open the request to see that it was signed. The PDF is not modified and there is no signed copy: the held copy and the Document's file are the original, and the evidence is the request record and the log entry.
6. **Read the evidence.** `sign_request.get` shows `signed_at`, `signed_name`, `signer_ip`, `signer_user_agent`, `signature_reference`, `document_hash` and `consent_version` to a person with `sign.manager` (REST, CLI and the back office; a plain `sign.user` sees none of them). An agent token, also over MCP, sees the personal fields (typed name, address, browser) masked (D10). **How to tell a signature made at the door from one marked by hand:** a door signature has `signed_at`, `signed_name`, `signer_ip` and `consent_version` and a `sign_signed` entry in the security log whose digest can be recomputed from them; a request marked `signed` by hand (only possible for a request that is not about a Document) has none of these. The Document's related-records panel lists every request that refers to it, so two signers of one NDA are two requests.

**Several links per request are allowed.** Creating a new link does not cancel an older one: revoke an old link yourself if it may have been seen by someone it should not have been. A link is valid for 14 days by default, never longer than the end of the request's `expires_on` day, and works once.

## What is recorded

| Where | What | Notes |
|---|---|---|
| `sign_request.document_hash` | SHA-256 of the file, lowercase hex | set at send; equals the blob id |
| `sign_request.document_file` | the held copy of the PDF | the request gives access to the copy only through the group `sign.system`, which nobody holds (an administrator satisfies every group); **while the Document still holds the same file, everyone who may read the Document can read these bytes through the Document** |
| `sign_request.signed_at` | the time of signing, UTC, server clock | |
| `sign_request.signed_name` | what the signer typed | personal data; `signer_name` stays the name that was requested |
| `sign_request.signer_ip` | the address as reported by the proxy chain, or `unknown` | the last entry of the last `X-Forwarded-For` line behind a trusted proxy, else the peer; read as an IP address (an `ip:port` entry is read as its address); see "Settings and preflight" |
| `sign_request.signer_user_agent` | the browser, cut to 300 characters | |
| `sign_request.signature_reference` | `typed:<name>` | |
| `sign_request.consent_version` | the id of the consent wording and the page language, for example `v1-draft/de` | the wording is a draft, see below |
| `sign_link` | the link's hash as its id, the request, the expiry, when it was used or revoked | the link itself is never stored |
| security log | `sign_link_issued`: who made the link, the first 12 characters of the link's id, when it ends, the first 16 characters of the document hash. `sign_signed`: the request, the link's first 12 characters, the document hash, the consent id, **a digest of the evidence**, the address, the peer address and every `X-Forwarded-For` line (cut to 200 characters, lines joined with ` \| `); the typed name, the browser and the exact time are inside the digest and are not readable in the entry. `sign_refused`: written only when the door refuses a known link for one of these reasons: no held copy, held copy missing, Document gone, document changed, stale form, held copy tampered with, or a post on a link that is over; at most one entry per link and reason in ten minutes. A view of an expired or revoked link, a bad name, a missing tick and a rate-limit refusal write nothing | never the link; unknown links are counted and not logged |

The typed name, the address and the browser are **personal data**. They are kept with the request, and the address, the peer address and the forwarded header are also in the security log (`security_event`, which no command changes or erases). obop has no generic erasure tool for any of it yet and no automatic expiry (Q68). The `sign_signed` entry is written by the door in the same step as the signature; no command writes or changes a security log entry. That is a property of the command surface: nothing in the database stops someone who can write the database, and the digest is an unkeyed SHA-256 of fields stored next to it.

## What it does not do

- **It does not prove who signed.** See above. The page names the person the request is for and the consent sentence says "I am <that name>", but nothing checks it.
- **It is not tamper-proof and it does not claim to be.** After signing, the wrappers refuse the door-owned fields, and update and delete of a signed request, for everyone but a platform administrator (see D92); a platform administrator or anyone with database access can change anything, the log entry included. What exists is a log entry written at signing with a digest of the evidence. Nothing in this draft reads that digest back and says "matches"; do not describe the record as tamper-proof or as tamper-evident.
- **The address is only as good as the proxy.** Behind a trusted proxy `signer_ip` is the **last entry of the last `X-Forwarded-For` line**: a proxy that extends the client's line or adds its own line writes its entry last, and what precedes it is what the client sent. If the instance is reachable without the proxy, or the proxy does not append the address it saw, the value is chosen by whoever sends the request. An `ip:port` or `[ipv6]:port` entry is read as its address; an entry that is not an address is stored as `unknown`, and the limits then count that signer under the peer's address (behind a proxy, the proxy's). The audit event carries the peer address and every `X-Forwarded-For` line next to the recorded value, so the evidence can be reviewed.
- **Approval is of the request, not of the bytes.** An agent-proposed send runs on whatever file is attached when a person approves it. The evidence records the exact bytes that were sent.
- **Staff who see the link can sign in the signer's name.** The address and browser make it visible, not impossible.
- **A request about a restricted Document is listable.** `sign_request` has no row-level access of its own, so every person with `sign.user` can list requests (title, requested name) even for a restricted Document. The Document and its bytes stay restricted (PR 0, the blob row gate).
- **Who is refused a link.** `sign_link.create` refuses agent tokens, scoped tokens and the tokens of mobile apps ("a signing link is a secret; ask a person to create it") and it is listed on MCP. A user's own session token used from MCP, the CLI or a script is **not** refused: do not say "agents never get links", say "an agent token cannot create one". It does not count as MCP parity.
- **No email, no copy for the signer, no drawn signature, no evidence page, no pdf.js.** The signer gets no copy (Q69): staff send the signed PDF by hand. The page works from typed names only; a drawn signature is a later, additive field.

## The signer's page is not a command

Every capability of obop is a typed command on the CLI, REST and MCP. The signer's act is the one exemption D92 asks the owner to accept (Q66): `GET` and `POST /sign/<request>/<token>` and `GET /sign/<request>/<token>/document.pdf` are server-rendered public routes, like the OAuth pages and the payment webhooks, and every state change behind them is one typed, audited operation with one security event. **For a request about a Document no command signs for someone:** the action `sign` is refused for it (the manual action stays for requests without a Document, which the by-hand and DocuSeal flows use), and so is an update that sets `state` to `signed`, which runs the same action first. A platform administrator can still write the evidence fields of any request and change or delete a signed one: that is a rule against mistakes and against staff without the role, not against an administrator or the database. The routes are not on `/api`, set no cookie and are refused as an admin prefix; the pages carry `noindex` (a header and a meta tag), while the PDF answer and the redirect after signing set no `X-Robots-Tag`; `robots.txt` disallows `/sign/` only when the instance runs with `--public-site` (the published image does). If the model `sign_link` is not registered (the package is not upgraded, or was rolled back) all three routes answer 404.

## Settings and preflight

Before a link goes to a real person:

1. **`OBOP_PUBLIC_URL`** is set to the external address (`https://acme.example.com`). The signer's POST is accepted only from the page's own origin; behind a TLS-terminating proxy that does not send `X-Forwarded-Proto` the derived address is wrong and every signing attempt would be refused. The link shown to staff also starts with this address.
2. **`OBOP_TRUST_PROXY=1`** (or `--trust-proxy`; the published image sets it), so that the address in the evidence is the client's and not the proxy's, and the rate limits count per client. Never set it on an instance that is reachable without the proxy.
3. **Check the recorded address on the real deployment**: send a request to the page with a forged `X-Forwarded-For` (for example `203.0.113.9`) and confirm that the address stored for the request is the one your proxy appended after it, not the forged one; the log entry shows every line it received. A proxy that merges into one line and one that adds a second line are both handled (the last entry of the last line counts). If the stored address is the forged one, the address in the evidence is not worth anything. The Sliplane provisioner passes no `--trust-proxy` of its own: confirm what your instance runs with.
4. **No DocuSeal connection lists `sign_request.send`** in its events, or you accept that it fires for requests that use `send` (the document flow's `send_document` does not fire it).
5. **Proxy access logs contain the link** (it is in the path). Keep them as private as the link itself.

Rate limits count through the shared store and fail open if it is unavailable (the 256-bit link is the defence, not the limiter). **Per source** (the address; the peer's when the address cannot be read), in windows of **ten minutes**: 20 failed lookups, 120 views (the page and the PDF share one count) and 10 signing posts. **Per link**, in one **hour**: 10 signing posts, refused tries included, so ten bad tries (a name that is too short, a missing tick) lock that link for an hour and the fix is a new link. **Per person**, in one hour: 20 links made. A valid link is never refused for the number of failures from its source. The limits need a correct `OBOP_TRUST_PROXY` to count per client. The "busy" page says "wait a minute" whatever the wait; the `Retry-After` header has the real number of seconds.

## Upgrade runbook (an instance that has sign 0.2.0)

**Deploying the new binary already changes `sign` 0.2.0.** The new model is not installed and the three routes answer 404, but the wrappers of D92 act on the old package from the first start: a person without `platform.admin` can no longer type `document_hash`, `signer_ip`, `signer_user_agent` or `signature_reference` on a request (in 0.2.0 a field group restricted reading only, so staff could), can no longer change or delete a request that is `signed`, and `sign_request.send` refuses a request that has no template. A person in the middle of the manual by-hand workflow is refused with "written by the signing process" or "a signed request cannot be changed or deleted; ask an administrator". The blob row gate (PR 50) is active at once too. A request created before otherwise keeps working.

1. Read the installed version of `documents` (Customize, Modules). The bundled `sign` 0.2.1 needs `documents` 0.3 or later, below 1. An instance without `documents` gets it installed by the upgrade with nobody in its groups but administrators: give the staff who send and make links `documents.user` (and `documents.manager` for restricted Documents they do not own) before they try, or `send_document` and link creation answer "was not found, or you may not see it".
2. **Take a backup first:** `obop backup run`. An additive module update takes no automatic backup (docs/DEPLOY.md, "Migration gates").
3. `obop modules plan sign` and read it. Expected: the model `sign_link` added, five optional fields added to `sign_request`, a new dependency on `documents` (already installed), one action added to `sign_request` (`send_document`) and no data migration. The plan lists added and removed actions only: it does not show that `template_id` and `signer_email` are no longer required, nor the new assertion on the action `sign` (below).
4. `obop modules update sign` (an administrator; an agent can only propose it). Old requests and templates keep working; the new fields are empty.
5. Set the settings above and run the browser checks below.

**The manual action.** From 0.2.1 the action `sign` is refused for a request about a Document (an assertion on the action): such a request is signed only at the door. Requests without a Document (templates, DocuSeal) are signed by hand as before.

**Rollback** (`obop modules rollback sign`) keeps the data and returns to 0.2.0. Requests about a Document then lack the `template_id` and `signer_email` that 0.2.0 requires, so `sign`, `decline` and `expire` all refuse them and **staff cannot close a sent document request**; an administrator unblocks one by setting its `template_id`. Their held copies stay as orphaned data; every `/sign` link answers 404. An older binary against the upgraded package sees `sign_link` as a generic model: inert rows and no route.

## A link is lost or may have leaked

The link is not stored and cannot be shown again. **Create another link** for the same request (the button on the request, or `obop call sign_link create ...`) and hand over the new one. If the old one may have been seen by someone it should not have been, **revoke it** as well. A used link cannot be used again: a second submit shows "already signed" and changes nothing. A request moved to `declined` or `expired` kills its links at once.

## Manual checks before a real signer is sent a link

Only one browser was tried, and only by the author. **Spike of 2026-11-03** (a made-up one-page PDF served by a throwaway local server, Chromium 152 in the Claude desktop app's browser pane, which has Chromium's PDF viewer): the PDF showed in `<object type="application/pdf">` when the page's content security policy had **`frame-src 'self'`** (and `child-src 'self'`), and when the PDF response carried any of `frame-ancestors 'self'` alone, `default-src 'none'; frame-ancestors 'self'`, no policy at all, or even `sandbox`. **Without `frame-src` the page's `default-src 'none'` blocks the viewer** ("Framing ... violates default-src 'none'. 'frame-src' was not explicitly set"): the box stayed empty and only the fallback text and the full-size link showed. So the page's policy must name `frame-src 'self'`, and the PDF response's policy must never contain `sandbox` even though this Chromium tolerated it (other engines were not tried). The viewer filled in a second or two after the page. Not tried: Firefox, Edge, desktop Safari, an iPhone, an Android phone, the production proxy. Twenty minutes with a **made-up PDF**: Chrome, Edge, Firefox, desktop Safari, an iPhone and an Android phone. On desktop the PDF shows in the page; on both phones the full-size link opens all pages; clicking an external link inside the test PDF does not send the signing address as the referrer; the form submits and the "Signed" page shows. If a desktop browser shows an empty box, the full-size link still works; the constant `INLINE_PDF_CSP` already is `frame-ancestors 'self'` alone, so there is nothing to loosen there. The next candidates, in this order, are the other headers of the PDF response: `Cross-Origin-Resource-Policy: same-origin`, then `X-Frame-Options: SAMEORIGIN`, then the policy itself (dropping it widens the exposure: the PDF is served from the same origin as the back office and the API, so a script-running flaw in a viewer would run next to the back office's stored session; the spike showed that `default-src 'none'; frame-ancestors 'self'` also rendered in Chromium 152, which is the narrower value to try for the first live use). The first live use must use the English or German page: all other languages are machine-drafted.

## Wording and translations

The consent sentence (`consent`, id `v1-draft`) and the notice of what is recorded are **a draft for counsel, not legal advice**. The English text is the original; German, French, Polish, Finnish, Swedish and Spanish (page and package labels) are **machine-drafted and not reviewed by a native speaker**. The id of the wording is stored with each signature (`v1-draft/de`) and is pinned by a test; the wording itself is not pinned by a hash until counsel has seen it, so it may still change, and a change after the real NDA went out is possible only because the stored id says which version the signer saw. Who confirms the wording is Q67.

## Known limits (not fixed in this draft)

Each is a row in docs/ISSUES.md, section O, with its fix.

- **Any `sign.user` can end or reword a sent request.** `decline` and `expire` are open to the model's write group, so a plain user can close someone else's sent request (its links stop at once); a plain user can also change the title, message and requested name that the signer reads and re-point `document_id` of a sent request (the link then answers 409 until it is repaired). The signed hash stays bound to the file; the wording the signer saw is not part of the digest (O19).
- **The Document's id and its file's SHA-256 are visible** to `sign.user` and `sign.manager` through `sign_request`, also for a restricted Document they cannot open; the bytes stay locked by the blob row gate (O20).
- **Staff changes and the door's write are not serialised.** The door's batch checks its conditions at commit; a `decline`, `expire` or `update` by staff reads and then writes without one, so in the same instant a stale write could land on a request that was just signed (O21).
- **Expiry edges.** The end of a link is checked before the PDF is read and the signing time is taken after, so a signature can land by that processing time after the end; a clock before 1970 means nothing expires; the day in `expires_on` ends at 23:59:59 **UTC** whatever the instance's time zone (O22).
- **The log line carries text from the client** (the peer and the forwarded header, outside the digest); semicolons are replaced so that they cannot start a second field (O23).
- **A wrong approver burns an agent's proposal.** A person who cannot see the Document and approves an agent's `send_document` makes it fail, and the right approver then gets a 404 (O24).
- **Names:** look-alike letters (Cyrillic), fullwidth angle brackets and up to about a hundred combining marks are accepted in a typed name; the joiners U+200C and U+200D are kept (some names need them); the typed name is never compared with the requested name (O8, O28).
