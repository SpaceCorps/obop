# The public website (`web/apps/site`)

The public website of obop: multi-page, statically generated, fully server-rendered, localised in seven languages, with Markdown copies of every page for people's tools and for AI agents. It replaces the single-page landing app (`web/apps/landing`, removed). The sign-up and instances app stays a React SPA under `/app/` (`web/apps/platform`), which a control plane serves with the site (`deploy/build-site.sh`). No page of the site links to it: SpaceCorps hosts no obop for other people today (OR-11); a sandbox and paid hosting are planned, not offered (OR-20, OR-22, D83); the owner confirmed in chat on 2026-11-11 that the hosted beta is not live. So the site's calls to action lead to Getting started, and the app itself names no domain: whether obop.dev takes sign-ups is a matter of that deployment, which the owner closes, not of the app's text.

- **Status:** working document, 2026-10-16. Written against the code in the repository.
- **Owner decisions it relies on:** D38 (docs on VitePress inside Vite+), D14 (no Node in production: the site is built once and served as plain files), F2 (JS tooling only through `vp` and pnpm).

## Architecture in one picture

```text
content/<locale>/**.md   authored Markdown (en at content/en, translations beside it)
i18n/<locale>.ts         every non-prose string: navigation, footer, home, pricing, app strings
data/apps.ts             hand-written "what it is for" text per app
data/builtin/*.toml      snapshot of the six built-in modules (same format as packages/*.toml, with the D55 metadata; connectors.toml is regenerated by a test)
packages/*.toml          the bundled marketplace packages (read at build time; the 22 that APP_COPY lists get an app page)
docs/MODULES.md          the module guide, included at build time as docs/reference/module-manifest/
git log                  the changelog (data/changelog.snapshot.json where there is no .git)
design/ascii-field.js    the hero's ambient field (copied, not forked)
        |
        v  scripts/assemble.ts
.src/                    the VitePress source tree (generated, not committed)
.generated/              JSON for the theme, the page manifest, the Markdown mirrors
        |
        v  VitePress (.vitepress/config.ts, .vitepress/theme)
dist/                    HTML, one file per route: /docs/agents/mcp/index.html
        |
        v  scripts/postbuild.ts
dist/                    + .md mirrors, search indexes, social cards, sitemaps, robots.txt, llms.txt
        |
        v  deploy/build-site.sh
web/site/                dist/ at the root and the platform app under /app/  (served by the control plane)
```

`vp build` inside `web/apps/site` runs all of that: `vite.config.ts` gives Vite an empty virtual entry and runs the pipeline when it finishes, so the one command CI and the Dockerfile run for every app also builds the site. `vp run build` runs the same script directly and `vp run dev` serves a preview on `http://127.0.0.1:5180` (restart it after editing content).

### Why VitePress 2.0.0-alpha.20

D38 names "VitePress 2 inside Vite+". The newest stable VitePress, 1.6.4 (2025-08), depends on Vite 5; the repository's toolchain is Vite 8. `vitepress@2.0.0-alpha.20` (2026-09-04, more than a month old, so inside the pin policy of D23) depends on `vite ^8.2.1` and `shiki ^4`, and installs against Vite+ 1.0.0 (Vite 8.3.4, Rolldown 1.2.14) without patches. The site builds with zero warnings and renders all 504 pages (72 per language) in about 10 to 15 seconds; the whole build, with the social cards, takes about half a minute (33 s measured). The risk of an alpha is accepted because the site is static output we can inspect, the theme is ours (we use almost nothing of VitePress beyond its Markdown pipeline, routing and build), and a fall back to 1.6.4 would need only the Vite pin. Revisit when 2.0 is stable.

### Design decisions

- **Custom theme, no default VitePress look.** `.vitepress/theme` has its own layouts and components on `@obop/ui` tokens, logo, icons and app tiles (rendered to HTML with `@obop/ui/static`). Light and dark come from the tokens (`data-theme` or the system preference). Geist is self-hosted by `@obop/ui`; the latin variable file is preloaded and `font-display: swap` comes from fontsource.
- **No client framework on the page.** The site is static HTML. `transformHtml` removes VitePress's Vue runtime and router, so nothing hydrates. What needs script is a few kilobytes of plain JavaScript in `client/` (served from `/site/`): the theme toggle, copy buttons, search, the language hint, and on the home page only the ASCII field (`/site/home.js`). Everything else is HTML and CSS: the mobile menu and language list are `<details>`, the home page's apps filter is radio buttons and `:has()`, the FAQ and the "For developers" part of an app page are `<details>`. Every page reads and navigates with JavaScript disabled (tested).
- **One Markdown pipeline.** Every page is Markdown (hand-written, or generated from data), so the Markdown mirror of a page is the same text as the page. Pages drawn from data (home, apps index, pricing) have a mirror function in `scripts/lib/mirror.ts`.
- **Trailing-slash routes.** Each route is `.../index.html` (`/docs/agents/mcp/`). Mirrors are `.../mcp.md`.
- **Generated, honest app pages, in two layers.** For each of the 28 apps the page has a plain-words layer on top and the full technical page folded under it (see "The apps pages" below). Nothing is invented: the structure comes from `packages/*.toml` and `data/builtin/*.toml`; what `data/apps.ts` writes by hand is the names, categories, taglines and "what it is for" paragraphs; the plain words of the cards whose manifest text a visitor cannot read (`cards`); the technical remainder that sits under "For developers" (`technical`); the caveats moved out of the plain text (`limit`, `limits`; see "Where a caveat goes"); the few plain model names (`modelNames`); and, where the manifest says more than the module does, corrections of the package text, a model's description or a field's (`packageText`, `modelText`, `fieldText`), each naming the sentence it replaces, and the models that have no `delete` command (`noDelete`; see the end of the CI paragraph). The package description is otherwise shown under "For developers" as the manifest has it.
- **The apps pages borrow restraint from app store pages, nothing else.** One idea per screen, one accent colour (the primary pill and links), large type, long calm vertical rhythm, soft rounded surfaces with hairline edges, touch targets of at least 44 px for every control the apps pages add (not the shared chrome: the header's icon buttons are 36 px and the footer's links are small, on every page, the home page included, so they wait for their own change; the heading permalinks in the folded technical part are small too), no decoration without meaning. No asset, text, icon or font of any store is used; the colours, Geist and the radii are the `@obop/ui` tokens. The CSS is `.vitepress/theme/apps.css` (index and shared tokens) and `app-page.css`, written mobile first with logical properties (a test reads both files for physical ones). The header's one button, "Get started" (to Getting started), is the plain (outlined) button on the index and on every app page alike, so the header does not change style between the two pages of one flow and no page has two filled pills on one screen. App icons are "fluid" tiles (`Tile.vue`, `scripts/lib/tile.ts`): the page's CSS sets their size in rem through `--icon-size`, so they follow the reader's text size, and their corners are the squircle's 22 percent, with no `!important`.

## Page, locale and app recipes

### Add a page

1. Create `content/en/<path>.md` (or `<dir>/index.md`) with front matter `title` and `description` (both required; `lead` and `eyebrow` optional). No H1 in the body: the layout draws the title. Docs pages (under `docs/`) get the docs layout; others get the plain page layout.
2. Link to other pages with site-absolute paths (`/docs/agents/mcp/`); the build adds the language prefix. A dead link fails the build.
3. For a docs page add its path to `data/docs-nav.ts` (sidebar order and previous/next).
4. Build. The page appears in every locale, as an English fallback with a visible notice in the languages that have not translated it. It is in the sitemap, `llms.txt`, the search index and the Markdown mirrors without further work.

Tokens you can put on their own line in a page: `%%catalog%%` (the bundled marketplace table), `%%changelog%%`, `%%moduleguide%%` (docs/MODULES.md).

### Add or change an app

The app pages are generated. To add a bundled package: add `packages/<id>.toml` (the Rust catalog in `crates/kernel/obop-pkg/src/marketplace.rs` must list it too), then add an entry to `APP_COPY` in `data/apps.ts` (name, category, English tagline, purpose, where something is too technical for the plain text, `technical`, and where a caveat is only for developers, `limits`, see "Where a caveat goes" below) and a tagline for it in every `i18n/<locale>.ts` (`apps.taglines`). On a translated page the app is called what its label file calls it (`[labels.<locale>.module] name` in `packages/labels/<locale>/<id>.toml`), so add that file too. The build fails if the copy is missing. The tile, the row, the cards and the facts of the new app need nothing else. To change a built-in module, edit `data/builtin/<id>.toml` to match the Rust module.

The two links in the Markdown copy of an app page lead to Getting started in the page's language in the same way (a unit test), and the test that no page links to `/app/` covers the app pages in HTML and in Markdown. **Works with and related apps** are a row of icons with their names under them. An item is as wide as its name needs (at least the icon, at most 11rem and the column), so a name is not cut in the middle of a word; `hyphens: auto` (de, fi, sv, pl) only helps beyond that. Right-to-left is not offered, but the two chevrons are already mirrored with `:dir(rtl)`.

**How it is made.** `scripts/lib/app-view.ts` builds one view model per app and language from the manifests (category, facts, whether the app is experimental, the two parts of the purpose, cards, the safe lines, dependencies with their names in the page language, the information rows, the install command). `assemble.ts` puts it in the front matter of the page, so `AppPage.vue` only draws it, and `appMirror` in `scripts/lib/app-page.ts` writes the Markdown mirror from the same model, which is why the two cannot drift. Everything technical is the Markdown body of the page (`developerBody`: package text, module details, models with their field tables, workflows, permission groups, approval steps, the agent view, dependencies, install, the link to the module guide; the package text is followed by the caveats that `data/apps.ts` moved out of the plain text, as one list, see "Where a caveat goes"), shown inside `<details id="developers">`, the closed row whose label is the "For developers" heading; its headings are one level below that heading (h3, h4) on the page and in the Markdown copy. Their text, and so their ids, are the ones the whole page had before the split; "What it is for" is drawn in the layout with the same id (`scripts/lib/slug.ts` is a copy of VitePress's slugify, pinned to it by a unit test that renders real headings through VitePress). The folded part is in the HTML, so crawlers, agents and the Markdown mirror see all of it, and search keeps the first 2,500 characters of the plain layer and the first 2,500 of the technical part (so a word only a field table uses, `website.user` say, still finds its app); `client/site.js` opens it when a link points at a heading inside it (Chrome also does this itself; the e2e test for the script closes the fold and sends a synthetic `hashchange`, so only the script can pass). The copy buttons show only after `site.js` has set `html.js-ready`, and carry their name in the markup, so a script that fails to load leaves no dead button; on a touch screen the install box's button is always visible and 44 px square.

**Words on the cards.** On a translated page the cards use the labels the product itself has in that language (`packages/labels/<locale>/<id>.toml`, D52: model name and description, action label and description; all 213 entries exist in all six languages), through `loadLabels` in `scripts/lib/apps.ts`; where a label is missing the card falls back to the English manifest and carries `lang="en"`. The purpose text, the package description and the field descriptions in the technical tables are English (they are not in the label files); they are marked `lang="en"`, and the purpose has one quiet line under it saying so (`apps.store.purposeEnglish`). The app itself is named by its label file in the same way (`appName`; English and any language without one use `data/apps.ts`), for the tile, the row, the H1, the title, the strip, the icons and the Markdown copy; the icon and the colour still come from the module id. A word wider than its card (Swedish "Integritetsförhandsgranskning" in a card 15 rem wide) cannot be kept whole by any rule: it breaks at the card's edge, with a hyphen where the browser has a hyphenation dictionary (`hyphens: auto` in de, fi, sv and pl) and without one where it has none; every other word stays whole and no text leaves its card (the test switches hyphenation off, so the result is the same on every browser). Where the manifest's text for a card is not plain words (a group name, a hash, a claim the module does not keep, such as "Send the scheduled campaign to the whole list" for a step that only records that it was sent), `data/apps.ts` has plain words of its own for that card (`cards`: `model.action` for an action card, the model's name for a model card). They say the same or less, never more than the manifest supports, and a translated page shows such a card in English, marked as such, because the product's translation says the old words. A unit test (`cards.test.ts`) reads every card a visitor sees without opening a fold (the ones `splitCards` shows: every marked card, then the first three of the others beside fewer than three marked cards, or the first one beside three or more; a fold is only made for two cards or more) against the words in `scripts/lib/plain.ts` (API, hash, payload, allowlist, widget, SLA, a group or field name). An older test in `app-view.test.ts` reads the lines about AI agents, the strip and the taglines against the same words; its card check still uses `plain.ts` `visible` (the first six, or all of seven), which is no longer what the page draws. The browser test reads the cards the page draws outside a fold (`#can-do ~ .app-cards > .app-card`, the same for `#keeps`), the lines about AI agents and the sentence above them. A few English model names read oddly (`party`, `bom`, `move`), so `data/apps.ts` gives them plain names (`modelNames`: Contact, Bill of materials, Journal entry, ...).

**Where a caveat goes (`limit`, `limits`).** The plain text on top (the purpose, a card's `text`) keeps what a person needs in order to use the app safely: a step that does not do what its name suggests ("By itself, this does not notify anyone"), what can still be edited after a step, a legal or privacy limit, what the app does not connect to. A caveat that only a developer or an operator needs (how a check is made, what is not tested against a live service, a field nothing reads, a template that nothing links) goes under "For developers", in the package part under "What the package does and does not do", and is not shown on the card: on a card as `limit` (a field of its `cards` entry in `data/apps.ts`, next to `text`), for the app as a whole as an entry of `limits`. The header comment of `data/apps.ts` repeats the rules below. `app-view.test.ts` checks, for every card or app that carries a limit, only the form (one sentence a Markdown list can hold; the text left on top has at least three words and does not contain the limit) and that the limit is in the part for developers of the Markdown copy and not above it, and it pins the wording of a few cards. That a caveat is only for a developer, that the text left on top is true on its own, and that a sentence the fold already has is not copied into a limit are judgements no test makes. The rules: a limit is one sentence (no full stop is followed by another sentence; a semicolon may join two halves) that ends with a full stop and has no `<`, `>`, `*` or `|` and no `-` or `#` at its start (it is written into a Markdown list); the text left on top is not empty, is at least three words and is true on its own (a reader who never opens the fold is not misled by it); the sentence is moved, so it is taken out of `text` or `purpose` and not copied; a sentence that the fold already has (`technical`, `packageText`, a `fieldText`) is deleted from the top and not copied into a limit; a card may carry a `limit` only through its `cards` entry, whose `text` is then the plain top sentence. `limitsOf(app)` in `scripts/lib/app-view.ts` lists them (the app's own first, then the action cards in the order of the cards, then the model cards; one model card carries a limit today, Fleet's driver, and a unit test with a synthetic app also tries a titled model card), and `developerBody` writes them after `technical` as list items, headed by the card's name as the card is headed ("Order: refund") or with no head for the app's own, in one `eng()` block: so the page and the Markdown copy have the same list, a translated page marks it as English (`class="en-note"`), no heading and so no id is added, and nothing about `AppView`, the Vue components or the strings changes. Print keeps a list item whole (`.app-dev .prose li`). Eight limits are moved today, seven on cards and one for the app (the Stripe refund test status of eCommerce, on its two refund cards; Point of Sale's payments, which are checked only when the sale is paid, and its uncounted drawer; the lines of an accounting entry; that Fleet does not check a driver's status or licence expiry when a vehicle is assigned; when an AI agent's placeholders are forgotten after a contact is erased: 24 hours after the last change over REST, 2 hours after the last request for an MCP session over HTTP, and when the command stops for `obop mcp`; and, for the app as a whole, that no action creates a shift from a Planning template and a shift has no field that names one); a unit test lists them, so a new one is a deliberate change. The sign-off of Field Service is not one: its field text in the technical tables already says a job can be finished without it. On a translated page the Planning template card is the English card of `cards` (marked `lang="en"`), because the label file's own sentence says the template is copied into shifts; a unit test checks it in all seven languages.

**Strings.** Everything the plain-words layer adds is in `apps.store` of `i18n/<locale>.ts` (the page also uses `apps.h`, `apps.meta`, `apps.categories`, `apps.installNote` and `ui.copy`); the six translations are machine-drafted like the rest (the heading "Comes with obop" of the index, its lead, the approval mark and the lines about AI agents were rewritten so that nothing says "ready to use" or "safe" where the FAQ says obop is not ready for production) (`translation-status.json`, key `apps`). Keep the English short so the translations stay short. Strings with a count use `{n}`; the fold labels avoid a noun after the number where the language needs a plural form (Polish), and a fold is only made for two cards or more, so such a count is never 1; the strip's count (`worksCount`) has a form for each plural category. `vp run i18n:check` also fails a translation that drops or adds a `{placeholder}`. The Get box names the Customize app and its Marketplace as the back office calls them in each language (Anpassen and Marktplatz, Mukauta and Moduulikauppa, ...).

### Add a locale

1. Add the code to `LOCALES` in `i18n/types.ts` and a file `i18n/<code>.ts` (copy `en.ts`, translate it, set `htmlLang`, `ogLocale` and `langName`).
2. Register it in `i18n/index.ts`.
3. Create `content/<code>/` with the translated pages and a `translation-status.json`.
4. Run `vp run i18n:check <code>` until it is clean, then build. VitePress locale config, sitemaps, hreflang, the language switcher and the Markdown mirrors pick it up from `LOCALES`.

RTL is out of scope; the CSS uses logical properties so adding it later is a layout review, not a rewrite.

## Translation workflow

**All translations are machine-drafted** (written by a language model, 2026-10-16) and have not been reviewed by a native speaker. They are marked as such in `content/<locale>/translation-status.json`, which maps each translated page to `machine-drafted` or `reviewed`. The build fails if a translated page has no entry, or an entry has no page.

What is translated: all interface strings (navigation, footer, buttons, banners, search), the home page, the apps index, the headings and labels of every app page and the one-line summary of each app, pricing, Getting started, the Agents overview, Create an agent token and Connect over MCP, Platform and About. The cards of an app page (what it can do, what it keeps) are in the page language, from the product's own label files, except a card that `cards` in `data/apps.ts` writes in plain English and a card whose label file lacks the model's name, the action's label or its description; those are English and marked with `lang="en"`. The longer "what it is for" paragraphs, package descriptions and field descriptions on app pages are English, marked with `lang="en"`, because they come from the manifests. Every other page falls back to English with a banner ("This page is not translated yet") and is not listed in `hreflang` alternates or the sitemap of that language; its canonical URL is the English page.

To review a language: read `i18n/<locale>.ts` and the files in `content/<locale>/`, fix them, and change the page's entry in `translation-status.json` to `reviewed`. To translate another page: copy `content/en/<path>.md` to `content/<locale>/<path>.md`, translate it (keep code blocks, links and front matter keys; `vp run i18n:check` enforces this), and add its path to `translation-status.json`.

The root `/` never redirects by `Accept-Language`, so crawlers always see the English page. If the browser's preferred language is one of ours and differs from the page, a small dismissible bubble at the bottom of the page (fixed position, so nothing shifts) offers the translated version of the same page. Dismissal is remembered in local storage, not a cookie.

## Server requirements

The control plane serves `web/site` with a plain static file server. The site works with that today, because every route exists as a file. These are the changes it needs, in order of importance:

1. **A real 404.** For a path with no file, answer status **404** with the body of `/404.html` (`Content-Type: text/html`). Today unknown paths fall back to `index.html` with status 200, which makes every typo a "soft 404" that search engines and agents misread. Do this for the website only, not for `/app/` (the SPA needs its fallback to `/app/index.html`).
2. **Directory routes.** `/docs/agents/mcp` (no slash) should redirect with 301 to `/docs/agents/mcp/`; `/docs/agents/mcp/` serves `index.html`. (`ServeDir` already serves the directory index; the redirect is the addition.)
3. **Markdown negotiation.** For a page URL (`/docs/agents/mcp/`) with `Accept: text/markdown`, answer with the file at the same address with `.md` instead of the trailing slash (`/docs/agents/mcp.md`; the home page is `/index.md`, `/de/` is `/de/index.md`) and `Content-Type: text/markdown; charset=utf-8`. Add `Vary: Accept` to the HTML responses of those URLs, and `Link: </docs/agents/mcp.md>; rel="alternate"; type="text/markdown"` is optional because every page already has the `<link>` in its head.
4. **Content types.** `.md` as `text/markdown; charset=utf-8`, `.txt` as `text/plain; charset=utf-8`, `.xml` as `application/xml`, `.webmanifest` not used, `.png` and `.svg` as usual.
5. **Caching.** `/assets/*` (hashed file names) and `/site/*` may be `Cache-Control: public, max-age=31536000, immutable` if the files under `/site/` get hashed names later (they do not today: give them a short max-age, for example 3600). HTML: `no-cache` or a short max-age with revalidation. `ETag` or `Last-Modified` on everything.
6. **Compression.** gzip or brotli for HTML, CSS, JS, JSON, XML, SVG and text.
7. **Reserved paths.** The forum (`/community/*`) and the status page (`/status*`) are mounted by the control plane before the static files. The website therefore keeps its own pages for them at `/about/community/` and `/about/status/`, which describe them as parts of a control plane and not as live services of the website (the community page says a control plane includes a forum at `/community/`, does not link it, and sends questions to GitHub issues; `/about/status/` describes what a control plane's status page checks and does not link a live one; the 404 page links the two `/about/` pages). `/community/sitemap.xml` must exist for the sitemap index, unless the site is built with `OBOP_SITE_FORUM=0` (a site served on its own, below), which leaves it out of the index and out of `robots.txt`. `/app/*` is the sign-up app's: the website's 404 handling (item 1) must not answer under it.
8. **Security headers** (optional, good practice): `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, a `Content-Security-Policy` of `default-src 'self'; img-src 'self' data:; style-src 'self' 'unsafe-inline'; script-src 'self' 'unsafe-inline'; base-uri 'self'; frame-ancestors 'none'`. The site uses two small inline scripts (the theme setter in `<head>`, the language-hint data block) and inline `style` attributes on app tiles.
9. **Origin.** Canonical links, the sitemap and social cards need the public origin. Set `OBOP_SITE_URL` when building (default `https://obop.dev`, the known Sliplane address); a custom domain needs a rebuild with that variable.

## Build integration

It is what obop.dev runs while SpaceCorps offers no hosted obop (OR-40): `docker build -f deploy/site.Dockerfile -t obop-site .` and `docker run --rm -p 8080:8080 obop-site`. It builds with `OBOP_SITE_FORUM=0` (no `/community/sitemap.xml`) and `OBOP_SITE_URL` (build argument, default `https://obop.dev`). The server does what `website.rs` does for items 1 to 6 and the headers of item 8 except the `Content-Security-Policy`: a real 404, slash redirects, `Accept: text/markdown`, content types, caching, gzip, `GET` and `HEAD` only. The e2e suite runs against the control plane's server, not against this one; `deploy/site-image-test.sh` runs the same requests against the image.
- `deploy/build-site.sh` builds the site and the platform app and assembles `web/site`.
- The `Dockerfile` web stage builds the same with `pnpm --filter @obop/site exec vp build`. The site reads `packages/`, `design/` and `docs/MODULES.md`, so the stage copies them (the `.dockerignore` re-includes `docs/MODULES.md`). There is no `.git` in the image, so the changelog comes from `data/changelog.snapshot.json`; refresh it with `vp run changelog:snapshot` (in `web/apps/site`) before a release.
- **CI.** The `web` job of `.github/workflows/ci.yml` runs `vp check`, `vp test` and `vp build` in `web/apps/site` in the loops it runs for the other apps, and `vp run i18n:check` there; the platform app gets `vp check` and `vp build`, not `vp test`.

## Maintenance notes

- The category of an app on this site (its row in the Information list, its group on the index, its related apps) is written by hand in `data/apps.ts`; it is not the manifest's list of categories, which the technical part shows as "Categories" (Helpdesk is "Customers" here and "Services" there). A unit test pins the site's grouping.
- The six built-in modules are described twice: in Rust and in `data/builtin/*.toml` (a snapshot). Only `connectors.toml` is checked against the Rust module (the connectors test `the_website_snapshot_matches_the_module` fails when it is stale and regenerates it with `OBOP_UPDATE_SNAPSHOT=1`); the other five are kept by hand. A test that compares those five with their modules would remove the drift risk.
- Social cards are rasterised with `@resvg/resvg-js` (prebuilt binaries, no native build). Geist is a WOFF; the build unwraps it to TrueType in memory for resvg.
- Search is a small script over JSON indexes (`/search/<locale>.json`), built from the page text at build time. It is plain substring scoring: good enough for a few hundred pages, not a full-text engine.
- The site has 7 x 72 = 504 routes (every language, English included); the fallbacks are copies of the English text, generated, not stored.
