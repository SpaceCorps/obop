# obop — one business, one platform

Open-source operating system for businesses: an Odoo-class modular suite (ERP, CRM, accounting, inventory, manufacturing, HR, projects, POS, e-commerce, website, marketing, helpdesk, documents) on one shared data model. Clean-room re-implementation of Odoo's concepts and behaviour, not a code port.

## Hard tech constraints (set by the owner)

- **Backend:** exclusively the latest stable Rust.
- **Frontend and tooling:** exclusively the latest Vite+ (`vite-plus`).
  - All JS/TS tooling goes through the **`vp` CLI** (dev, build, test, lint, format, tasks, environment).
  - The package manager is **pnpm**. Never use `npm`, `npx`, `yarn` or `bun`. The only JavaScript lockfile that may exist is `pnpm-lock.yaml` (`Cargo.lock` is committed as usual); `package-lock.json`, `npm-shrinkwrap.json`, `yarn.lock`, `bun.lock` and `bun.lockb` must never be committed (CI fails on them). "No npm" means the CLI; pnpm still installs from the public npm registry.
  - Research files that describe Vite+ as supporting several package managers are describing the tool, not obop policy. obop uses pnpm only.
- Pending owner ruling: whether two narrow cases are allowed as named exceptions to "vp only": the nightly exit drill, which runs upstream Vite tools without `vp` (I-4), and the JavaScript SBOM and licence scan (`pnpm sbom`, `pnpm licenses list`, run through `vp env exec` or a `vp run` task, because `vp pm sbom` and `vp pm licenses` do not exist in vite-plus 1.0.0; I-2). See `docs/DECISIONS.md` (I-2, I-4, Q10). Until ruled, do not add other exceptions.
- Pin policy (D23, I-3, PROPOSED, Q10): "latest" is provisionally the newest release that passes the pin policy, so the toolchain intentionally runs up to about three weeks behind the newest release until the owner ratifies it. See `docs/DECISIONS.md` section 1.1.

## Layout

- `README.md` — entry point and document map.
- `docs/PRODUCT.md` — master product description. `docs/DECISIONS.md` — binding decision register (wins over the research where they differ).
- `docs/CONVENTIONS.md` — naming and contract authority (identifiers, events, permission groups, data classes, ports); it ranks below `docs/DECISIONS.md` and above every other document.
- `docs/ARCHITECTURE.md`, `docs/ROADMAP.md`, `docs/BUSINESS.md`, `docs/LOCALIZATION.md`, `docs/ENGINEERING.md`, `docs/GLOSSARY.md`.
- `docs/spec/` — per-domain product specifications.
- `docs/research/` — the fact-checked research corpus (index: `docs/research/README.md`).
- Status: early code. A Cargo workspace (`crates/kernel/*`, `crates/modules/*`, `crates/obop`) and a Vite+ backoffice (`web/apps/backoffice`) exist. Storage is SQLite locally and PostgreSQL for deployments (D44), via `obop-storage`; records are JSON documents until the schema manager exists.
- Code map: `obop-registry` (model/field/command metadata and the D41 install gate), `obop-commands` (the one `Dispatcher` behind REST, MCP and CLI: permissions, masking, approvals, generated get, list, search, create, update and delete, guards for governed state fields D48, server-side list queries D49), `obop-masking` (D40), `obop-http` (axum), `obop-mcp` (stdio), modules `base`, `product`, `crm`, `sales`, `invoicing`. A module declares models in the registry and gets all surfaces generated; every field needs a data class, permission group and description (`obop modules check`, or `obop modules check FILE...` for package files, no database needed). A select field that an action moves is governed (D48): `create` starts at its first option and `update` may only change it as an implicit run of a declared action, with that action's group and approval.
- Operations (D59, docs/DEPLOY.md): `obop-keys` (the key ring, the sealed envelope, `reseal` for rotation), `obop-migrate` (schema version and ordered migration steps), `obop-ops` (backup, restore, verify, `secrets rotate`); `obop-storage` also holds the cross-process lock, counters, expiring values and compare-and-set that make several server processes on one PostgreSQL database behave as one. CLI: `obop migrate|backup|restore|secrets`, `obop platform upgrade-instances`; `deploy/restore-drill.sh`; `.github/workflows/image.yml` publishes `ghcr.io/spacecorps/obop`.
- Modules and platform: `obop-pkg` (obop.toml X1 packages: parse, gate, semver and SPDX checks, dependency resolution and install plans, runtime install/uninstall, marketplace; admin commands `module.*`, `module_plan.preview` and `marketplace_listing.*`; D55: one core version `obop_types::CORE_VERSION`, module metadata, versioned dependencies), `obop-platform` (control plane: accounts, instances, provisioners local/sliplane/fake). `packages/*.toml` is the bundled catalog; translations (D52) are `[labels.<lang>]` tables in a package document, bundled as `packages/labels/<lang>/<id>.toml` (de, fr, pl, fi, sv, es; also for the built-in modules), checked by `obop modules check --complete FILE`, templated by `obop modules labels TARGET LANG`. See `docs/DEPLOY.md`; Sliplane project `obop` (`project_2x9d8q51m9lt`, account `spacecorps`) exists and is empty.
- Updates (D63, `docs/DEPLOY.md` "Updating from inside"): every package declares `requires_core` and a range per dependency; `module.upgrade|upgrade_all|rollback` (atomic batch, `[[migration]]` data steps in `obop-pkg::migrate`, D59 lock, audited, agents propose); `obop-update` (release feed, core compatibility of installed modules, `instance_update.check|status|start|rollback`, `obop update ...`) asks the control plane (`obop-platform::update`: per-instance update token, `GET /api/releases`, rollback to the previous image when the new one does not start).
- OAuth sign-in for MCP clients (D64, `docs/DEPLOY.md` "Connecting Claude"): `obop-oauth` (the authorization server: dynamic registration of public clients, authorization code with mandatory PKCE S256 and the RFC 8707 resource, rotating refresh tokens with reuse detection, revocation, the server-rendered sign-in and consent pages in 7 languages; state in the shared storage as `oauth_client`, `oauth_grant`, `oauth_refresh` records and expiring codes and flows, everything secret stored as SHA-256 hashes), `obop-http::oauth` (routes under `/oauth/*`, `/.well-known/oauth-authorization-server`, `/api/auth/oauth/grants`), the `OAuthTokens` trait of `obop-commands` implemented by `obop-auth` (access tokens are one hour scoped agent tokens bound to the `/mcp` audience: refused on `/api`), the Connected apps table in Customize, Security, and `security_event` kinds `oauth_*`. Not yet tried against the real Claude apps.
- Connectors (D54, `docs/CONNECTORS.md`): `obop-connectors` (the egress and ingress gate with treatment by data class, the one hardened outbound client, signed webhooks, OAuth2 with PKCE, sealed secrets, retention and erasure) and the built-in module `connectors`; every flow in or out is recorded, minimised and revocable, and the docs say plainly that this supports GDPR compliance and is not legal advice. Credentials are sealed with `OBOP_SECRET_KEY`; `OBOP_CONNECTORS_ALLOW_LOOPBACK=1` allows loopback targets and is for tests only; `obop connectors purge` applies retention.
- UI: `web/apps/backoffice` renders from `/api/meta` (D46): app launcher, control panel, list/kanban, record side panel, Customize app (theme, apps, the Modules page with cards, dependency panel and plan dialog, module builder). `web/apps/platform` is the sign-up app, `web/apps/site` the multi-page website (VitePress, docs, 7 languages; see docs/site/SITE.md); `deploy/build-site.sh` assembles the site and the sign-up app into `web/site`. Forum and status (`obop-community`, docs/COMMUNITY.md) and each instance's public shop (`obop-site`, docs/STOREFRONT.md, `obop serve --public-site`) are server-rendered Rust.
- Tests: `cargo test` (Rust, add `OBOP_TEST_POSTGRES_URL` for PostgreSQL), and `web/packages/e2e` (Playwright over the real built app, 50 tests; see its README; CI runs it). 12 bundled marketplace packages live in `packages/*.toml` (typed fields, D47).
- Auth: `obop-auth` (Argon2id passwords, SHA-256-hashed bearer tokens, 12 h sessions, login lockout, scoped agent tokens that can only narrow the owner's groups; TOTP two-factor, D53: sealed under `OBOP_SECRET_KEY`, required for `platform.admin` by default, the e2e suite sets `OBOP_REQUIRE_MFA_FOR_ADMINS=0`, break-glass `obop admin reset-mfa USER --db URL` (also removes passkeys), audit log model `security_event`; passkeys, D65: WebAuthn in `obop-auth` (`webauthn/`: strict CBOR, ES256/EdDSA/RS256 over `ring`, attestation `none`; `passkey.rs`), a second factor that satisfies the same policy and optional passwordless sign-in, RP id and origin from `OBOP_PUBLIC_URL` or the request (`--trust-proxy`), challenges single use in the shared store, routes `/api/auth/passkeys*` and `/api/auth/login/passkey*`, the same on the OAuth pages with one script allowed by hash; tests use the software authenticator `obop_auth::webauthn::soft` (feature `test-support`) and Chrome's virtual authenticator in `web/packages/e2e/tests/passkeys.spec.ts`, which runs a second instance reached as `localhost`). First user: `echo "<12+ chars>" | cargo run -- admin create NAME --all-groups`; `cargo run -- serve --static web/apps/backoffice/dist` after `cd web/apps/backoffice && vp build`; agents: `cargo run -- agent-token NAME --scopes base.user`. `--dev-auth` swaps in fixed dev tokens (`dev-admin`, `dev-sales`, `dev-agent`) and refuses non-loopback binds. Tests: `cargo test` (set `OBOP_TEST_POSTGRES_URL` to include PostgreSQL).
