# obop — one business, one platform

Open-source operating system for businesses: an Odoo-class modular suite (ERP, CRM, accounting, inventory, manufacturing, HR, projects, POS, e-commerce, website, marketing, helpdesk, documents) on one shared data model. Clean-room re-implementation of Odoo's concepts and behaviour, not a code port. Apache-2.0 and completely free to use and to self-host.

## Hard tech constraints (set by the owner)

- **Backend:** exclusively the latest stable Rust.
- **Frontend and tooling:** exclusively the latest Vite+ (`vite-plus`).
  - All JS/TS tooling goes through the **`vp` CLI** (dev, build, test, lint, format, tasks, environment).
  - The package manager is **pnpm**. Never use `npm`, `npx`, `yarn` or `bun`. The only JavaScript lockfile that may exist is `pnpm-lock.yaml` (`Cargo.lock` is committed as usual); `package-lock.json`, `npm-shrinkwrap.json`, `yarn.lock`, `bun.lock` and `bun.lockb` must never be committed (CI fails on them). "No npm" means the CLI; pnpm still installs from the public npm registry.
  - Research files that describe Vite+ as supporting several package managers are describing the tool, not obop policy. obop uses pnpm only.
- Pending owner ruling: whether two narrow cases are allowed as named exceptions to "vp only": the nightly exit drill, which runs upstream Vite tools without `vp` (I-4), and the JavaScript SBOM and licence scan (`pnpm sbom`, `pnpm licenses list`, run through `vp env exec` or a `vp run` task, because `vp pm sbom` and `vp pm licenses` do not exist in vite-plus 1.0.0; I-2). See `docs/DECISIONS.md` (I-2, I-4, Q10). Until ruled, do not add other exceptions.
- Pin policy (D23, I-3, PROPOSED, Q10): "latest" is provisionally the newest release that passes the pin policy, so the toolchain intentionally runs up to about three weeks behind the newest release until the owner ratifies it. See `docs/DECISIONS.md` section 1.1.

## Licence, price and contributions (set by the owner, RATIFIED)

- **Licence and price** (OR-1, OR-2; D1, D2): the whole project is Apache-2.0 and completely free, with no proprietary layer. No open-core, no enterprise tree, no paid list, plans or price list, no paid marketplace or partner programme, no AGPL layer, no CLA. `LICENSE` and `NOTICE` ("Copyright 2026 SpaceCorps contributors") are at the repository root; every crate (`license.workspace = true`), bundled package (`license = "Apache-2.0"`) and JavaScript manifest declares `Apache-2.0`. A new dependency must be under a licence compatible with Apache-2.0 (no copyleft-only components).
- **Publisher** (OR-10): SpaceCorps is the publisher, copyright holder and trademark holder. The repository `SpaceCorps/obop` is public.
- **Contributions** (OR-1, OR-18): DCO sign-off on every commit (`git commit -s`); no CLA. The owner signs off every commit and agents are recorded with a `Co-Authored-By` trailer; agents never add a `Signed-off-by` line.
- Older text in `docs/` and `docs/research/` that mentions the AGPL, an Application Exception, a CLA, an `ee` tree, paid plans or prices is superseded by `docs/DECISIONS.md`, section "Owner rulings (2026-10-01): licence and publisher". The owner's other rulings of that day are not recorded yet (see that section).

## Layout

- `README.md` — entry point and document map. `LICENSE`, `NOTICE` — Apache-2.0 text and attribution (OR-1).
- `docs/PRODUCT.md` — master product description. `docs/DECISIONS.md` — binding decision register (wins over the research where they differ).
- `docs/CONVENTIONS.md` — naming and contract authority (identifiers, events, permission groups, data classes, ports); it ranks below `docs/DECISIONS.md` and above every other document.
- `docs/ARCHITECTURE.md`, `docs/ROADMAP.md`, `docs/BUSINESS.md`, `docs/LOCALIZATION.md`, `docs/ENGINEERING.md`, `docs/GLOSSARY.md`.
- `docs/spec/` — per-domain product specifications.
- `docs/research/` — the fact-checked research corpus (index: `docs/research/README.md`).
- Status: early code. A Cargo workspace (`crates/kernel/*`, `crates/modules/*`, `crates/obop`) and a Vite+ backoffice (`web/apps/backoffice`) exist. Storage is SQLite locally and PostgreSQL for deployments (D44), via `obop-storage`; records are JSON documents until the schema manager exists.
- Code map: `obop-registry` (model/field/command metadata and the D41 install gate), `obop-commands` (the one `Dispatcher` behind REST, MCP and CLI: permissions, masking, approvals, generated get, list, search, create, update and delete, guards for governed state fields D48, server-side list queries D49), `obop-masking` (D40), `obop-http` (axum; `ops.rs`: `/healthz`, `/readyz`, `/metrics`, D67; `cors.rs`: validated `OBOP_ALLOWED_ORIGINS`, D68), `obop-mcp` (stdio), modules `base`, `product`, `crm`, `sales`, `invoicing`. A module declares models in the registry and gets all surfaces generated; every field needs a data class, permission group and description (`obop modules check`, or `obop modules check FILE...` for package files, no database needed). A select field that an action moves is governed (D48): `create` starts at its first option and `update` may only change it as an implicit run of a declared action, with that action's group and approval.
- Operations (D59, docs/DEPLOY.md): `obop-keys` (the key ring, the sealed envelope, `reseal` for rotation), `obop-migrate` (schema version and ordered migration steps), `obop-ops` (backup, restore, verify, `secrets rotate`); `obop-storage` also holds the one PostgreSQL connector with TLS (`obop_storage::tls::PgConnector`, D66: `sslmode` and `sslrootcert` in the URL, rustls, plain when unset; every PostgreSQL connection goes through it) and the cross-process lock, counters, expiring values and compare-and-set that make several server processes on one PostgreSQL database behave as one. CLI: `obop migrate|backup|restore|secrets`, `obop platform upgrade-instances`; `deploy/restore-drill.sh`; `.github/workflows/image.yml` publishes `ghcr.io/spacecorps/obop`.
- Operations since D73 (`docs/DEPLOY.md` "Backups" and "Upgrades", `docs/RUNBOOK-RECOVERY.md`): `obop-keys::stream` (the chunked ChaCha20-Poly1305 seal of format 2 backups), `obop-migrate` (the checksummed migration ledger `obop_migration`, drift refusal at start, adoption of older databases, the database id `obop_meta/instance`, stored plans, the token-based DDL classifier `ddl.rs`, `RunOptions::before` where a self-migrating server takes its backup under the migration lock), `obop-ops` (`backup` formats 1 and 2 with a MAC'd manifest and refusal of plain backups where a key is configured, `fsutil` crash-safe private file publishing, `schedule` and `retention`, `sink` (`BackupSink`, `FsSink`), `catalog` (records `obop_backup`, `obop_restore_drill`, `obop_storage_attestation`), `gates` (strict and relaxed migration gates, rehearsal receipts tied to the database id, rollback in one transaction), `drill`, `doctor` for `obop storage check`, `pgadmin` (`ServerInfo`)); `obop-pkg` has the `MigrationGate` port implemented by `backup_cli::ModuleGate`. CLI: `obop migrate status|verify|plan|run|rehearse|rollback`, `obop backup [run|list|prune|verify]`, `obop restore`, `obop drill`, `obop storage check|attest|show` (CLI-only; D73 asks the owner for that exemption); stable exit statuses 3 (`restore_key_required`), 4 (`backup_not_sealed`), 5 (`restore_files_failed`). Settings: `OBOP_BACKUP_DIR|KEY|KEY_PREVIOUS|SCHEDULE|COPY_DIR|COPY_DELETE|KEEP_*|MAX_AGE_DAYS`, `OBOP_HOST_ID`, `OBOP_MIGRATION_GATES`, `OBOP_INSTANCE_BACKUP_DIR` (control plane).
- Decimal and datetime kinds (D72): `obop-values` (leaf crate: `Decimal` as i128 units with strict parser, checked arithmetic with a 256-bit division, `Round`; `Instant` in microseconds, RFC 3339 in and canonical UTC out; `Bucket`; the bundled IANA time zone database via `jiff`, `ZoneDb::fixture` for tests; the one source of the examples and patterns the surfaces print). `FieldKind::Decimal{precision,scale,round}` and `Datetime` live in `obop-registry`; every write path calls `kinds::canonicalise` (`obop-commands/src/kinds.rs`) and the stores accept canonical text only; queries use `Key::Dec`; aggregates are exact (`avg` takes `scale` and `round`); filters and `group_by` take `bucket` (day, week, iso_week, month, year) and `zone`; `OBOP_ZONE` (default UTC) is read only by `App::set_zones_from_env`; a changed decimal scale or smaller precision is a breaking package change that needs a `[[migration]] op = "reformat_field"`. Backoffice: `decimals.ts`, `instants.ts`. Not in the backoffice views yet: decimal measures and datetime or iso_week or year dimensions in pivot, graph, kanban, calendar and dashboards (D72 Not delivered).
- Modules and platform: `obop-pkg` (obop.toml X1 packages: parse, gate, semver and SPDX checks, dependency resolution and install plans, runtime install/uninstall, marketplace; admin commands `module.*`, `module_plan.preview` and `marketplace_listing.*`; D55: one core version `obop_types::CORE_VERSION`, module metadata, versioned dependencies), `obop-platform` (control plane: accounts, instances, provisioners local/sliplane/fake). `packages/*.toml` is the bundled catalog; translations (D52) are `[labels.<lang>]` tables in a package document, bundled as `packages/labels/<lang>/<id>.toml` (de, fr, pl, fi, sv, es; also for the built-in modules), checked by `obop modules check --complete FILE`, templated by `obop modules labels TARGET LANG`. See `docs/DEPLOY.md`; Sliplane project `obop` (`project_2x9d8q51m9lt`, account `spacecorps`) exists and is empty.
- Updates (D63, `docs/DEPLOY.md` "Updating from inside"): every package declares `requires_core` and a range per dependency; `module.upgrade|upgrade_all|rollback` (atomic batch, `[[migration]]` data steps in `obop-pkg::migrate`, D59 lock, audited, agents propose); `obop-update` (release feed, core compatibility of installed modules, `instance_update.check|status|start|rollback`, `obop update ...`) asks the control plane (`obop-platform::update`: per-instance update token, `GET /api/releases`, rollback to the previous image when the new one does not start).
- OAuth sign-in for MCP clients (D64, `docs/DEPLOY.md` "Connecting Claude"): `obop-oauth` (the authorization server: dynamic registration of public clients, authorization code with mandatory PKCE S256 and the RFC 8707 resource, rotating refresh tokens with reuse detection, revocation, the server-rendered sign-in and consent pages in 7 languages; state in the shared storage as `oauth_client`, `oauth_grant`, `oauth_refresh` records and expiring codes and flows, everything secret stored as SHA-256 hashes), `obop-http::oauth` (routes under `/oauth/*`, `/.well-known/oauth-authorization-server`, `/api/auth/oauth/grants`), the `OAuthTokens` trait of `obop-commands` implemented by `obop-auth` (access tokens are one hour scoped agent tokens bound to the `/mcp` audience: refused on `/api`), the Connected apps table in Customize, Security, and `security_event` kinds `oauth_*`. Not yet tried against the real Claude apps.
- Connectors (D54, `docs/CONNECTORS.md`): `obop-connectors` (the egress and ingress gate with treatment by data class, the one hardened outbound client, signed webhooks, OAuth2 with PKCE, sealed secrets, retention and erasure) and the built-in module `connectors`; every flow in or out is recorded, minimised and revocable, and the docs say plainly that this supports GDPR compliance and is not legal advice. Credentials are sealed with `OBOP_SECRET_KEY`; `OBOP_CONNECTORS_ALLOW_LOOPBACK=1` allows loopback targets and is for tests only; `obop connectors purge` applies retention.
- UI: `web/apps/backoffice` renders from `/api/meta` (D46): app launcher, control panel, list/kanban, record side panel, Customize app (theme, apps, the Modules page with cards, dependency panel and plan dialog, module builder). `web/apps/platform` is the sign-up app, `web/apps/site` the multi-page website (VitePress, docs, 7 languages; see docs/site/SITE.md); `deploy/build-site.sh` assembles the site and the sign-up app into `web/site`. Forum and status (`obop-community`, docs/COMMUNITY.md) and each instance's public shop (`obop-site`, docs/STOREFRONT.md, `obop serve --public-site`) are server-rendered Rust.
- Tests: `cargo test` (Rust, add `OBOP_TEST_POSTGRES_URL` for PostgreSQL), and `web/packages/e2e` (Playwright over the real built app, about 190 tests; see its README; CI runs it). 23 bundled marketplace packages live in `packages/*.toml` (typed fields, D47).
- Auth: `obop-auth` (Argon2id passwords, SHA-256-hashed bearer tokens, 12 h sessions, login lockout, scoped agent tokens that can only narrow the owner's groups; TOTP two-factor, D53: sealed under `OBOP_SECRET_KEY`, required for `platform.admin` by default, the e2e suite sets `OBOP_REQUIRE_MFA_FOR_ADMINS=0`, break-glass `obop admin reset-mfa USER --db URL` (also removes passkeys), audit log model `security_event`; passkeys, D65: WebAuthn in `obop-auth` (`webauthn/`: strict CBOR, ES256/EdDSA/RS256 over `ring`, attestation `none`; `passkey.rs`), a second factor that satisfies the same policy and optional passwordless sign-in, RP id and origin from `OBOP_PUBLIC_URL` or the request (`--trust-proxy`), challenges single use in the shared store, routes `/api/auth/passkeys*` and `/api/auth/login/passkey*`, the same on the OAuth pages with one script allowed by hash; tests use the software authenticator `obop_auth::webauthn::soft` (feature `test-support`) and Chrome's virtual authenticator in `web/packages/e2e/tests/passkeys.spec.ts`, which runs a second instance reached as `localhost`). Bulk create, D70: every model has `bulk_create` (`obop-commands/src/engine/bulk.rs`: up to 1,000 rows from `rows` or `csv`, each through the checks of `create`, one `apply_checked` batch, `mode` all_or_nothing or partial, `dry_run`, `idempotency_key` stored in the `bulk_idempotency` table, `OBOP_BULK_PER_MINUTE`), `obop import MODEL FILE.csv`, the Import dialog `web/apps/backoffice/src/ImportDialog.tsx`; no id remapping, no images or files; decimal columns round on import only where the field declares `round` (D72). People administration, D69: `obop-auth/src/admin.rs` (create user, edit groups, offboard, import; the `AccountsApi` port of `obop-commands`), REST `/api/auth/users*` and `/api/auth/groups`, the `user_account` commands of the Customize module (agents only propose; `obop-pkg/src/accounts.rs`), CLI `obop admin users|groups|offboard|disable|enable|import FILE.csv [--dry-run] [--out FILE]`, the People panel `web/apps/backoffice/src/People.tsx`; the strict CSV reader is `obop_commands::csv`. First user: `echo "<12+ chars>" | cargo run -- admin create NAME --all-groups`; `cargo run -- serve --static web/apps/backoffice/dist` after `cd web/apps/backoffice && vp build`; agents: `cargo run -- agent-token NAME --scopes base.user`. `--dev-auth` swaps in fixed dev tokens (`dev-admin`, `dev-sales`, `dev-agent`) and refuses non-loopback binds. Tests: `cargo test` (set `OBOP_TEST_POSTGRES_URL` to include PostgreSQL).
